# AI-Native는 책임을 재배치한다

STEP 03 §§41–50의 결론은 **AI-Native Development를 “AI가 개발을 대신하는 최종 상태”가 아니라, 개발자가 목표·판단·검증·책임을 유지한 채 Agent가 일할 환경과 feedback system을 설계하는 운영 방식**으로 제한해야 한다는 것이다. OpenAI와 산업·학술 자료는 AI-native, AI-assisted, SE 3.0 같은 표현을 서로 다른 범위에서 사용하므로, 이 교육은 외부 용례와 자체 operational usage를 분리해야 한다([OpenAI Codex guide](https://developers.openai.com/codex/guides/build-ai-native-engineering-team), [Hassan et al., ACM TOSEM](https://doi.org/10.1145/3807901), [Google DORA 2025](https://cloud.google.com/blog/products/ai-machine-learning/announcing-the-2025-dora-report)). 2026-09-25 기준 공식 OpenAI 문서는 Business/Enterprise/Edu data handling, Codex local/cloud execution, Apps/Plugins/MCP controls를 설명하지만, 회사 내부 소스코드나 고객 데이터를 넣어도 된다는 허용 판단은 제공하지 않는다([OpenAI business data](https://openai.com/business-data/), [Codex cloud environments](https://learn.chatgpt.com/docs/environments/cloud-environment), [Admin controls for plugins and apps](https://help.openai.com/en/articles/11509118)). Demo는 agent 실패를 조롱하거나 인과를 과장하는 장면이 아니라, 조건을 고정하고 한계를 표시한 evidence surface여야 한다. 비용과 복잡도 역시 최종 insight의 일부다. “Minimum Effective Harness”는 공식 taxonomy가 아니라, 관찰된 Failure/Friction에 대응해 필요한 최소 구조를 추가한다는 이 프로젝트의 bounded heuristic이다. 이 보고서는 STEP 03 §§41–50만 합성하며, STEP 03 후속 구간·Curriculum·Demo 설계·Slide 제작은 아직 별도 작업이다.

## AI-Native는 표준 목적지가 아니라 교육용 운영 정의다

검토한 자료에서 “AI-Native Development”는 단일 표준 정의로 고정되어 있지 않다. OpenAI의 AI-Native Engineering Team guide는 Codex를 계획, 설계, 구현, 테스트, 리뷰, 배포, 유지보수에 연결하고, 사람이 strategy와 final decision을 소유하는 `Delegate / Review / Own` 구조를 제안한다([OpenAI Codex guide](https://developers.openai.com/codex/guides/build-ai-native-engineering-team)). Gartner의 공개 초록은 AI-native software engineering을 developer creativity, agentic workflow, fast feedback loop와 연결하지만, 공개 초록 범위에서는 효과 크기나 표준 정의를 확인할 수 없다([Gartner](https://www.gartner.com/en/documents/6076795)). ACM TOSEM의 SE 3.0 논문은 intent-first, conversational development, AI teammate를 제안하는 비전/로드맵 성격의 글이며, 모든 조직이 같은 도착점으로 이동했다는 관찰 연구가 아니다([Hassan et al., ACM TOSEM](https://doi.org/10.1145/3807901)).

따라서 이 교육의 표현은 외부 사용과 내부 사용을 나눠야 한다. **External usage**는 제품 가이드, 산업 분석, 학술 비전에서 쓰이는 넓은 말이다. **Our training usage**는 `Chatbot → Prompt → Context → Harness → Loop → AI-Native Development` Story의 마지막 요약으로, 개발자가 AI에게 단발 질문을 던지는 상태에서 벗어나, repository context, reusable workflow, tools, verification, feedback loop를 갖춘 작업 환경을 설계하는 관점을 뜻한다. 이 operational definition은 `MASTER_PLAN`의 교육 서사를 설명하기 위한 teaching model이지, 업계 합의나 모든 조직의 성숙도 종착점이 아니다.

개발자 역할 변화도 같은 방식으로 좁혀 말해야 한다. OpenAI guide는 agent가 first-pass implementation, tests, review를 도울 수 있어도, product behavior, spec ambiguity, architecture, performance, security, migration risk, maintainability, merge/release decision은 사람이 소유한다고 설명한다([OpenAI Codex guide](https://developers.openai.com/codex/guides/build-ai-native-engineering-team)). Barke et al.의 OOPSLA 2023 연구는 AI 보조 프로그래밍 사용을 “acceleration”과 “exploration”으로 나누며, 개발자가 의도와 선택을 계속 주도한다는 관찰 근거를 제공한다([Barke et al.](https://arxiv.org/abs/2206.15000)). 2026년 전문 개발자 설문 preprint는 코드 작성 시간이 줄었다는 자기보고와 verification 중심 shift를 보고하지만, 자기보고 설문이며 객관적 품질·시간·인과를 확정하지 않는다([Vella & Blincoe](https://arxiv.org/abs/2605.23135)).

“코딩 능력이 불필요해졌다”는 결론은 근거에 맞지 않는다. Anthropic 연구자들의 2026년 RCT는 처음 쓰는 Python library 과제에서 AI 지원군이 약간 빠르지만 이해도 퀴즈 평균은 직접 코딩군보다 낮았다고 보고했고, 평가 항목은 code reading, debugging, library concept 이해였다([Shen & Tamkin](https://arxiv.org/abs/2601.20245)). FSE Companion 2025 연구도 초급자가 LLM-generated code를 이해하는 데 어려움을 보였다고 보고했다([Zi et al.](https://arxiv.org/abs/2504.19037)). 생산성 수치 역시 맥락에 묶인다. Microsoft의 field experiment는 특정 code-completion assistant에서 task count 증가를 보고했지만, METR의 2025 RCT는 익숙한 OSS repository의 실제 task에서 초기 2025 AI tool 사용 조건이 평균 19% 느렸다고 보고했다([Microsoft Research](https://www.microsoft.com/en-us/research/publication/the-effects-of-generative-ai-on-high-skilled-work-evidence-from-three-field-experiments-with-software-developers/), [METR RCT](https://arxiv.org/abs/2507.09089)). 교육에서 안전한 정리는 **Goal / Judgment / Verification / Responsibility**다. 이 네 항목은 외부 표준 직무 모델이 아니라, 개발자가 목표와 요구를 정하고, trade-off를 판단하고, 검증 기준과 결과를 해석하며, 최종 risk와 accountability를 유지한다는 이 교육의 teaching model이다.

## 제품 보안 사실은 회사 허용 정책을 대신하지 않는다

2026-09-25 기준 OpenAI 공식 문서는 Business/Enterprise/Edu 및 API inputs/outputs를 기본적으로 model training 또는 model improvement에 사용하지 않는다고 설명한다([OpenAI business data](https://openai.com/business-data/), [Enterprise privacy](https://openai.com/enterprise-privacy/)). Help Center는 개인용 ChatGPT와 Codex에서는 content가 training에 사용될 수 있고 opt out이 가능하다고 구분하며, business users의 inputs/outputs는 기본적으로 training에 쓰지 않는다고 설명한다([How your data is used](https://help.openai.com/en/articles/5722486-how-your-data-is-used-to-improve-model-performance)). HIPAA configuration guide는 ChatGPT Enterprise와 Codex data를 training에 쓰지 않는다고 설명하고, Local Codex에서는 사용자 workstation이 inputs/outputs를 보관하며 prompts/files는 inference를 위해 OpenAI로 전송되고 결과가 돌아온다고 설명한다([HIPAA configuration guide for Codex](https://learn.chatgpt.com/docs/hipaa-configuration)). 이 문장은 제품 data handling 사실이지, 회사 내부 코드·고객 데이터·credentials를 사용할 수 있다는 허용이 아니다.

Local, Worktree, Cloud, self-hosted sandbox의 데이터 흐름도 구분해야 한다. Codex environments 문서는 Local이 현재 project directory에서, Worktree가 Git worktree에서, Cloud가 configured cloud environment에서 실행된다고 설명하며 Local과 Worktree는 사용자 컴퓨터에서 실행된다고 한다([Codex environments](https://learn.chatgpt.com/docs/environments/modes)). Cloud environment 문서는 selected branch 또는 commit SHA checkout, setup/maintenance script, internet settings, terminal command loop, diff display를 설명하고, secrets는 task execution 때 복호화되지만 setup script에만 제공되고 agent phase 전에 제거된다고 한다([Codex cloud environments](https://learn.chatgpt.com/docs/environments/cloud-environment)). Agents API self-hosted sandbox는 OpenAI가 agent harness를 운영하고 고객이 `codex exec-server`를 자기 환경에서 돌리는 구조를 설명하며, 같은 environment를 공유하는 agents가 같은 files, credentials, resources에 접근할 수 있다고 경고한다([Self-hosted sandboxes](https://developers.openai.com/api/docs/guides/agents-api/environments/self-hosted)). “local”은 files and commands의 실행 위치에 관한 말이지 model inference가 local-only라는 뜻이 아니다.

Retention과 residency도 하나의 문장으로 압축할 수 없다. ChatGPT data residency는 in-scope customer content의 storage at rest location을 정하고, inference residency는 eligible Enterprise/Edu customer의 supported region에서 GPU inference를 in-region으로 수행하게 하는 별도 기능이다. 같은 문서는 Apps & MCP, Web Search, external integrations, system data, routing, analytics, CPU processing이 selected region 밖에서 처리될 수 있다고 설명한다([Data residency and inference residency](https://help.openai.com/en/articles/9903489-data-residency-and-inference-residency-for-chatgpt)). ChatGPT Business content storage 문서는 Business data residency rollout이 gradual이고, non-US region을 선택해도 safety/abuse-monitoring data와 limited-time prompt/response copy가 US에 저장될 수 있다고 설명한다([Business content storage](https://help.openai.com/en/articles/20001418-where-your-chatgpt-business-content-is-stored)). ChatGPT chat/file retention 문서는 saved chat 삭제, GPT/project/file 삭제, Enterprise transient files, Library backup retention처럼 ChatGPT chat/file 범위의 feature-specific retention rule을 설명한다. 이 페이지는 deleted saved chat 및 GPT/project/file data를 30일 내 permanent deletion 대상으로 schedule하되 security/legal obligations 등의 예외를 둔다고 하고, Enterprise workspaces의 일부 transient files가 48시간 후 expire될 수 있으며, inactive Library file backups may be retained up to 30 additional days라고 설명한다([Chat and file retention](https://help.openai.com/en/articles/8983778-chat-and-file-retention-in-chatgpt)).

Workspace 기능은 plan, role, admin setting, provider permission의 교집합이다. Managed account 문서는 관리자가 prompts, uploaded files, outputs, conversation history, workspace content, usage/activity metadata를 access/export/audit/retain/delete하거나 data sharing opt-in을 설정할 수 있다고 설명한다([Managed account data access](https://help.openai.com/en/articles/20001067-data-access-for-your-managed-chatgpt-account)). Roles and workspace permissions 문서는 ChatGPT workspace RBAC, local client runtime policy, Codex cloud eligibility, API platform membership, connected service permissions를 분리한다([Roles and workspace permissions](https://learn.chatgpt.com/docs/enterprise/roles-and-workspace-permissions)). Plugins in ChatGPT and Codex는 plugin installation이 provider 또는 workspace permission을 우회하지 못한다고 설명하고, OpenAI Verified badge가 조직의 privacy/security/vendor review를 대체하지 않는다고 한다([Plugins in ChatGPT and Codex](https://help.openai.com/en/articles/20001256/)). Admin controls for plugins/apps는 plugin installation, underlying app access, action controls, OAuth scopes, workspace restrictions, approval settings를 별도 check로 나눈다([Admin controls for plugins and apps](https://help.openai.com/en/articles/11509118)). 따라서 교육에서는 “OpenAI 제품의 공식 보안 특성”과 “우리 회사의 허용 정책”을 반드시 분리하고, OQ-014는 unresolved로 남겨야 한다.

## Demo는 재현성보다 정직한 증거가 먼저다

Demo 재현성은 “같은 Prompt면 매번 같은 답”이 아니라, 시작 상태와 관찰 evidence를 추적할 수 있는 능력이다. Codex Cloud는 selected branch 또는 commit SHA checkout, runtime/package/setup script, agent internet access policy, cache/maintenance script 같은 설정을 제공하지만, Cloud cache가 최대 12시간 유지될 수 있고 재개 시 branch checkout과 maintenance가 적용될 수 있으므로 commit만으로 전체 실행 조건이 동일하다고 말하면 안 된다([Codex cloud environments](https://learn.chatgpt.com/docs/environments/cloud-environment)). Agents API Web Search의 live/cached/disabled mode는 external search result의 변동 가능성을 드러내며, API 기능을 Codex UI 전체로 일반화할 수는 없다([Agents API Web Search](https://developers.openai.com/api/docs/guides/agents-api/tools/web-search)). Agentic eval 연구는 SWE-Bench-Verified의 60,000 trajectory에서 single-run pass@1이 선택 run에 따라 2.2–6.0 percentage points 달라질 수 있고 temperature 0에서도 분산이 남는다고 보고했다([On Randomness in Agentic Evals](https://arxiv.org/abs/2602.07150)).

교육에서 고정할 수 있는 요소는 repository commit, clean/dirty state, prompt, test fixture, expected output, dependency lock/runtime, setup/maintenance script, working directory, verification command, tool/permission/network/search mode, 실행 시각과 product surface다. 고정했다고 주장할 수 없는 요소도 적어야 한다. 정확한 inference backend, UI에서 노출되지 않는 model snapshot, live web/search 결과, 외부 service 상태, agent의 탐색 경로는 변동될 수 있다. Recording, screenshot, pre-captured diff, saved logs는 Live Demo의 진정성을 훼손하는 장치가 아니라 교육 안정성을 위한 evidence fallback이다. 단, label이 정직해야 한다. “2026-09-25에 commit X, product surface Y, model display Z, command W로 실행한 녹화”라고 말할 수는 있지만, “지금 모든 환경에서 재현되는 결과”라고 말할 수는 없다.

Failure 후보 A–I도 실제 관찰이 아니라 **candidate**다. 모호한 Prompt로 scope가 넓어지는 A, repository rule 부재로 API가 바뀌는 B, verification 지시 누락으로 test가 실행되지 않는 D, 오래된 build instruction으로 command가 실패하는 E는 fixture와 oracle을 잘 만들면 교육 가치가 높다. 반면 oversized `AGENTS.md`의 C, 과도한 조사 context의 F, 오래된 Memory의 H, instruction bloat의 I는 현실성은 있지만 원인과 결과를 안정적으로 분리하기 어렵다. OpenAI Harness Engineering 사례는 큰 `AGENTS.md`와 stale rule 문제가 실제로 보고된 사례를 제공하지만, 길이 threshold나 보편 causal law를 제공하지 않는다([OpenAI Harness Engineering](https://openai.com/index/harness-engineering/)). AGENTS.md 연구들도 context file의 효과가 task, repository, context generation method에 따라 달라지고, cost 증가가 관찰될 수 있음을 보여줄 뿐 전역 규칙을 주지 않는다([Gloaguen et al.](https://arxiv.org/abs/2602.11988), [Khatri](https://arxiv.org/abs/2607.27250)).

Before/After 비교도 같은 원칙을 따른다. OpenAI evaluation best practices는 목표와 성공 기준, dataset, metric을 먼저 정하고 변경마다 continuous evaluation을 권한다([Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices), [Evaluate agent workflows](https://developers.openai.com/api/docs/guides/agent-evals)). 교육용 Before/After는 모든 학술 실험이 될 필요는 없지만, `Task`, `Repository state`, `Model`, `Environment`, `Verification`을 가능한 한 맞추고 무엇이 intervention인지 밝혀야 한다. Prompt 개선 전후를 비교하면서 prompt, repo, model, 환경, 검증 기준을 동시에 바꾸면 “Prompt 때문에 좋아졌다”고 말할 수 없다. 정확한 표기는 “원리 설명용 illustrative demo이며 일반 성능 우위를 증명하는 benchmark가 아니다”이다.

## 비용과 복잡도는 성숙도의 그림자를 만든다

Agent 비용은 prompt 한 덩어리의 비용이 아니다. OpenAI Agents API observability 문서는 한 task가 여러 model call을 만들 수 있고, input tokens에는 instructions, tool definitions, conversation history, user input, files/images, tool results가 포함되며, subagents도 별도 model calls를 만든다고 설명한다. 또한 retries, tool, sandbox compute, third-party charges를 함께 보라고 한다([Observability and usage](https://developers.openai.com/api/docs/guides/agents-api/observability)). Prompt caching은 matching prefix가 있을 때 latency와 input-token cost를 줄일 수 있지만, session 유지가 cache hit를 보장하지 않고, GPT-5.6 이후 cache write/read pricing rule처럼 model-specific rule이 존재한다([Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)). Latency guide는 output token generation이 latency의 큰 부분이며 output tokens를 50% 줄이면 latency도 대략 50% 줄 수 있다고 하면서, input prompt를 50% 줄이는 것은 보통 1–5% 정도의 latency 개선에 그칠 수 있다고 설명한다([Latency optimization](https://developers.openai.com/api/docs/guides/latency-optimization)).

Subagent와 parallelism도 free speedup이 아니다. Codex Subagents 문서는 subagent가 separate agent thread에서 일하고 main context의 noise를 줄이며 independent tasks를 병렬화할 수 있지만, 각자 model/tool execution을 하므로 tokens를 더 쓸 수 있고 simultaneous writes는 conflict와 coordination cost 때문에 조심해야 한다고 설명한다([Codex Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents)). Multi-agent inference-time parallelism 연구는 GAIA benchmark에서 일부 accuracy와 end-to-end latency 개선을 보고하면서 token consumption 증가를 함께 보고했다([Two-Tier Parallelism](https://arxiv.org/abs/2608.05791)). 이 연구는 Codex coding workflow를 직접 입증하지 않지만, 병렬화가 wall-clock과 compute를 교환한다는 trade-off를 설명하는 근거로 충분하다.

Evaluation loop도 비용이 든다. `On Randomness in Agentic Evals`의 workshop PDF는 60,000 trajectories가 **25.58B tokens와 1.88M tool calls**를 포함했다고 보고한다([OpenReview PDF](https://openreview.net/pdf/030b57388f7aa9e3a7ecb15e20541a8f2ed92f1b.pdf)). 이 수치는 반복 평가가 신뢰도를 높이는 동시에 운영 비용을 만든다는 좋은 사례다. OpenAI Skill eval guide도 Skill 변경이 trigger failure, required step omission, extra files 같은 regression을 만들 수 있으므로 trace와 artifacts 기준으로 평가하라고 한다([Testing Agent Skills](https://developers.openai.com/blog/eval-skills)). Build Skills 문서는 large skill set에서 initial list가 context window 일부만 쓰며, 너무 많으면 일부 skill이 omitted될 수 있다고 설명한다([Build skills](https://learn.chatgpt.com/docs/build-skills)). Codex Memories 문서는 mandatory team instructions를 `AGENTS.md`나 checked-in docs에 두고 Memory를 recall layer로 취급하라고 한다([Codex Memories](https://learn.chatgpt.com/docs/customization/memories)). Memory도 review, scope, refresh, retirement 비용이 있는 Harness 구성요소다.

이 근거들은 “더 높은 단계가 항상 좋다”는 메시지를 약하게 만든다. OpenAI Codex Goals guide는 one-line edit, simple explanation, short code review, one answer and stop이 필요한 질문에는 Goal을 쓰지 말라고 하며, Goals는 durable objective, evidence-based finish line, multi-turn path가 있을 때 강하다고 설명한다([Using Goals in Codex](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex)). OpenAI model guidance도 “smallest prompt that passes your evals”에서 시작하고 measured failure mode를 고칠 때만 block을 추가하라고 말한다([Model guidance](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-5.4)). 이 프로젝트의 “Minimum Effective Harness”는 바로 이 지점에 놓인다. 작은 일회성 질문은 Prompt가 더 효율적일 수 있고, 반복 project rule이 보이면 Context가, 반복 workflow와 검증 누락이 보이면 Harness가, 반복 failure와 regression 관리가 필요하면 Loop가 의미를 갖는다. 숫자 cutoff는 없다.

## 남은 결정은 Demo와 정책을 기다린다

이번 조사에서 `MASTER_PLAN`의 6시간 개발자 대상 교육, hands-on 없는 관찰형 Demo, 공유 역량 baseline, Story order를 바꿀 충돌은 보이지 않는다. 오히려 §37의 원칙이 더 강해진다. **Best Practice를 모두 먼저 설치하는 것이 아니라, 현재 Failure/Friction을 관찰하고 필요한 Engineering을 추가한다**는 말은 비용, latency, coordination, memory freshness, eval expense, security boundary를 모두 고려한 비례 설계 원칙이다. 이는 `INV-IDENTITY-001/002`, `INV-AUDIENCE-001`, `INV-NARRATIVE-001/002`, `INV-RESPONSIBILITY-001`, `INV-DEMO-001–004`, `INV-RESEARCH-001–005`, `INV-SOT-002/003`과 정합적이다.

| Open Question | 이번 보고서가 확정한 점 | 남은 상태 |
| --- | --- | --- |
| OQ-001 | Demo가 동일 repository의 점진적 진화로 설계되어야 한다는 원칙은 강화됐다. | 교육용 Demo repository 자체와 기술 stack은 아직 미정이다. |
| OQ-003 | Recording, screenshot, pre-captured diff, saved logs는 정직하게 labeled fallback이면 교육 안정성을 해치지 않는다. | 실제 Live Demo surface, 계정, OS, fallback package는 미정이다. |
| OQ-005 | 2026-09-25 기준 OpenAI 공식 문서로 Business/Enterprise, Codex, Apps/Plugins/MCP의 현재 제품 사실을 일부 확인했다. | 대상 training account/workspace/admin settings/feature availability는 Demo 직전 재확인해야 한다. |
| OQ-007 | 공정한 Before/After에는 task, repo state, environment, verification surface가 필요하다는 기준을 확보했다. | 실제 project verification command와 pass/fail oracle은 미정이다. |
| OQ-009 | Loop claim에는 failure, cause, change, re-evaluation, regression check가 필요하고 eval 비용이 있다는 근거를 확보했다. | 반복 failure와 evaluation criteria가 실제 관찰되기 전까지 Loop 개선 주장은 미확정이다. |
| OQ-014 | OpenAI product security/data handling은 조사했지만 회사 정책과 분리해야 한다. | 내부 source code/data, customer data, credentials, Cloud, plugin, connector 허용 여부는 전부 unresolved다. |

Source gap도 남아 있다. AI-Native Development의 업계 합의 정의는 확인하지 못했고, `Goal / Judgment / Verification / Responsibility`는 교육용 teaching model이지 검증된 외부 직무 모델이 아니다. A–I failure 후보는 아직 observed/reproduced failure가 아니며, Demo repository 없이 재현성·회복률을 정할 수 없다. Codex UI/Cloud에서 정확한 model snapshot, full environment digest, inference backend, exact cost/latency가 얼마나 고정·노출되는지도 표면별 확인이 필요하다. 회사 workspace plan, roles, data residency, retention, app policy, Compliance API coverage, Codex entitlement는 공개 문서만으로 알 수 없다.

## Conclusion

STEP 03 §§41–50은 마지막 메시지를 더 신중하게 만든다. AI-Native Development는 “AI가 모든 것을 알아서 한다”가 아니라, 개발자가 작업 목표와 품질 기준을 더 명확히 소유하고, agent가 안정적으로 일할 수 있는 context, tools, verification, feedback 구조를 필요한 만큼만 설계하는 방향이다. 이 전환은 코딩 지식의 폐기가 아니라 검증과 판단의 책임을 더 잘 보이게 만드는 변화다.

다음 단계에서 필요한 것은 더 큰 용어가 아니라 더 작은 증거다. Demo repository, target workspace, 회사 보안 정책, verification command, fallback 방식, 실제 failure 관찰이 정해질 때까지 이 보고서는 Evidence Base로 머문다. Slide, Demo, plan, decision은 아직 변경하지 않았다.
