# 긴 Context는 시스템 설계를 요구한다

STEP 03의 11–20절 근거는 MASTER_PLAN의 성숙도 서사를 유지하게 해 주지만, 각 용어와 주장의 범위를 더 좁고 정직하게 만든다. **Harness Engineering은 OpenAI가 실제 엔지니어링 사례에서 사용한 표현이지만, Codex 제품 기능명이나 업계 표준 정의는 아니다**([OpenAI Harness Engineering](https://openai.com/index/harness-engineering/)). **Loop Engineering은 IBM이 task 안의 action–observation 반복 설계로 정의한 용례와, 이 교육이 말하는 반복 실패 기반 Harness 개선 루프를 분리해야 한다**([IBM Think](https://www.ibm.com/think/topics/loop-engineering), [OpenAI Agent Improvement Loop](https://developers.openai.com/cookbook/examples/agents_sdk/agent_improvement_loop)). Long context와 Lost in the Middle 연구는 “정보를 많이 넣으면 자동으로 잘 쓴다”는 믿음을 약하게 만들지만, 현재 Codex의 모든 저장소 작업이 같은 실패를 낸다는 근거는 아니다([Liu et al., TACL 2024](https://aclanthology.org/2024.tacl-1.9/)). Verification 연구는 `Generated ≠ Done`을 강하게 뒷받침한다. 다만 이 보고서는 현재까지 전달된 STEP 03 자료 중 20절까지만 합성한 것이며, Demo 실행 결과나 회사 계정·보안 정책 확인을 포함하지 않는다.

## Harness는 기능 묶음보다 작업 환경 설계에 가깝다

OpenAI의 2026년 Harness Engineering 사례는 에이전트가 성공하려면 작업 의도, 저장소 구조, 도구, 검증, 피드백 경로가 함께 설계되어야 한다는 실무 근거를 제공한다. 이 사례에서 큰 AGENTS.md, 누락된 환경 정보, 검증하기 어려운 지식 구조가 문제로 등장했고, 팀은 짧은 진입점과 관련 문서로 이어지는 구조를 사용했다([OpenAI Harness Engineering](https://openai.com/index/harness-engineering/)). 동시에 OpenAI의 Codex agent loop 글은 `harness`를 모델 호출, 도구 실행, 결과 재투입을 다루는 런타임 층으로 설명한다([OpenAI Codex agent loop](https://openai.com/index/unrolling-the-codex-agent-loop/)). 따라서 수업에서는 `Agent Harness`를 런타임 또는 구성 층, `Harness Engineering`을 에이전트가 일하는 환경과 절차를 설계하고 개선하는 실천으로 설명하는 편이 근거에 맞다.

이 구분은 Anthropic과 Microsoft 자료를 함께 보면 더 중요해진다. Anthropic은 managed agents 문맥에서 harness를 모델 호출 루프와 도구 라우팅에 가까운 층으로 설명하고, Microsoft Agent Framework는 대화 상태, context provider, 도구, middleware, observability, 실행 루프를 결합하는 넓은 runtime scaffolding으로 설명한다([Anthropic Managed Agents](https://www.anthropic.com/engineering/managed-agents), [Microsoft Agent Harness](https://learn.microsoft.com/en-sg/agent-framework/concepts/harness)). 즉 `harness`는 조직과 문서에 따라 폭이 다르다. 이 교육의 안전한 운영 정의는 **“에이전트가 업무를 안정적으로 수행하도록 작업 환경과 실행 프로세스를 설계·구성·개선하는 일”**이다. 이 정의는 MASTER_PLAN의 Context → Harness 전환을 보호하지만, 표준 용어집처럼 제시하면 안 된다.

Loop도 같은 조심스러운 분리가 필요하다. IBM은 Loop Engineering을 에이전트가 행동하고 관찰하고 결정하고 반복하는 workflow 설계로 설명한다([IBM Think](https://www.ibm.com/think/topics/loop-engineering)). OpenAI 자료에는 Codex 런타임의 `agent loop`와 traces, evals, feedback, Codex를 묶어 harness 개선을 제안하는 `Agent Improvement Loop`가 따로 등장한다([OpenAI Codex agent loop](https://openai.com/index/unrolling-the-codex-agent-loop/), [OpenAI Agent Improvement Loop](https://developers.openai.com/cookbook/examples/agents_sdk/agent_improvement_loop)). 이 교육의 Loop Engineering은 단일 작업 안의 무한 반복이 아니라, 실행 결과와 반복 마찰에서 원인을 찾아 지시, Skill, Memory, 도구, workflow, 검증 방식을 개선하고 다음 실행에서 확인하는 구조다. “self-improving” 사례도 사람의 수정, trace, eval, Codex 반복을 포함한 시스템 개선으로 읽어야 하며, 에이전트가 무검토로 production harness를 스스로 고친다는 뜻으로 확장할 근거는 없다([OpenAI tax agents case](https://openai.com/index/building-self-improving-tax-agents-with-codex/)).

## Prompt와 Context는 질문의 층위가 다르다

Prompt Engineering은 목표, 지시, 제약, 형식, 예시를 명확히 작성해 모델의 응답을 유도하는 작업으로 설명할 수 있다. OpenAI Prompt Engineering 가이드는 지시를 명확히 하고, context와 예시를 제공하며, 실제 대상 모델에서 평가하라고 안내한다([OpenAI Prompt Engineering](https://developers.openai.com/api/docs/guides/prompt-engineering)). 반면 Anthropic은 Context Engineering을 추론 시점에 모델에 제공되는 최적의 토큰 집합을 선별하고 유지하는 실천으로 설명한다([Anthropic Context Engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). OpenAI Cookbook도 세션 기반 단기 기억 관리를 Context Engineering 사례로 다룬다([OpenAI Cookbook Session Memory](https://developers.openai.com/cookbook/examples/agents_sdk/session_memory)).

이 근거는 MASTER_PLAN의 `Chatbot → Prompt → Context` 전환과 잘 맞는다. Prompt는 “이 일을 어떻게 요청할 것인가”에 가깝고, Context는 “이 일을 하기 위해 지금 무엇을 알아야 하는가”에 가깝다. Harness는 그 Context 제공을 포함해 도구, 실행, 검증, 복구 경로를 업무 시스템으로 묶는다. 다만 이 세 용어는 상호 배타적인 제품 모듈이 아니다. 실제 Codex 작업에서는 system instruction, AGENTS.md, Skill, 저장소 파일, 검색 결과, session history, tool output이 서로 영향을 준다.

Progressive Disclosure는 이 Context 문제를 다루는 유용한 방법이지만, 성능을 자동 보장하는 마법은 아니다. UX 원칙으로는 처음부터 모든 옵션을 노출하지 않고 필요한 때 세부 사항을 드러내는 접근이며, agent 문맥에서는 Skill metadata, `SKILL.md`, references, scripts를 단계적으로 여는 방식으로 나타난다([Nielsen Norman Group](https://www.nngroup.com/articles/progressive-disclosure/), [OpenAI Codex Skills](https://developers.openai.com/codex/skills), [Anthropic Agent Skills](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview)). OpenAI의 GPT-6 Astra guidance도 긴 지시와 상충 지시가 모델을 방해할 수 있고, 작업마다 필요한 자료만 가리키는 편이 낫다고 권한다([OpenAI GPT-6 Astra guidance](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)). 하지만 2026년 장문 QA 프리프린트는 harness와 corpus에 따라 progressive disclosure의 이득이 작거나, 더 깊은 routing이 오히려 나쁠 수 있음을 보고했다([He et al., 2026](https://arxiv.org/abs/2607.17598)). 수업에서는 “필요한 정보를 필요한 때 찾게 하라”고 말해야지, “파일을 많이 쪼개면 좋아진다”고 말하면 안 된다.

## Long context는 용량이지 활용 품질이 아니다

Lost in the Middle의 핵심 근거는 특정 2023년 모델과 검색 과제에서 관련 정보의 위치가 성능에 영향을 주었다는 점이다. Liu 등은 NaturalQuestions 기반 다중 문서 QA와 합성 key-value 검색에서 답 문서가 시작이나 끝보다 중간에 있을 때 여러 모델의 정확도가 낮아지는 경향을 보고했다. GPT-3.5-Turbo는 20개·30개 문서 조건의 최악 위치에서 closed-book baseline 아래로 내려간 설정도 있었다([Liu et al., TACL 2024](https://aclanthology.org/2024.tacl-1.9/)). 이 결과는 현재 GPT-6, Codex, AGENTS.md, 저장소 편집 작업을 직접 평가한 결과가 아니다.

후속 연구는 “긴 Context”가 하나의 능력이 아니라 과제별 능력 묶음이라는 점을 강화한다. NoLiMa는 literal match가 약한 연관 회수에서 여러 long-context 모델이 긴 입력에서 크게 떨어질 수 있음을 보였고, RepoQA는 50개 공개 저장소의 함수 검색 과제를 평가했으며, SWE-QA와 RepoReasoner는 저장소 QA, cross-file reasoning, noise context의 효과가 모델과 과제에 따라 달라짐을 보여준다([NoLiMa](https://arxiv.org/abs/2502.05167), [RepoQA](https://arxiv.org/abs/2406.06025), [SWE-QA](https://aclanthology.org/2026.findings-acl.402/), [RepoReasoner](https://arxiv.org/html/2607.25996v1)). 특히 SWE-QA의 RAG 또는 agent 결과는 repository context가 없는 baseline 대비 향상을 보였지만, 그 수치만으로 “검색이 항상 전체 저장소 context보다 우월하다”고 말할 수는 없다([SWE-QA](https://aclanthology.org/2026.findings-acl.402/)). CoReQA도 retrieval과 전체 저장소 제공이 모두 제한적 개선만 보였다고 보고했다([CoReQA](https://arxiv.org/abs/2501.03447)).

OpenAI API 문서가 특정 GPT-6 model ID에 큰 context window를 표시하더라도, 그 값은 API model의 요청 용량이지 Codex App, CLI, IDE, ChatGPT UI의 effective budget이나 저장소 작업 성공률을 보장하지 않는다([OpenAI Models](https://developers.openai.com/api/docs/models), [Conversation State](https://developers.openai.com/api/docs/guides/conversation-state)). Compaction도 비용과 latency를 줄이며 상태를 보존하기 위한 기능으로 설명되지만, compacted item은 opaque이고 모든 세부가 손실 없이 보존된다고 문서가 보장하지 않는다([OpenAI Compaction](https://developers.openai.com/api/docs/guides/compaction)). 따라서 수업의 안전한 문구는 **“context window가 커지면 더 많이 담을 수 있지만, 관련 근거를 정확히 찾고 연결하는 능력은 task와 검증으로 확인해야 한다”**이다.

## Verification은 산출물과 과정 모두를 본다

Codex 문서는 좋은 요청에 원하는 결과, 관련 코드, 재현 정보, 제약, 검증 방법을 포함하라고 안내한다([Codex Prompting](https://developers.openai.com/codex/prompting)). Codex CLI는 로컬 프로젝트의 파일을 살피고 편집하며, 설치되어 있고 권한이 허용된 도구를 실행할 수 있다고 설명한다([Codex CLI](https://developers.openai.com/codex/cli)). Code Review 문서는 base branch, 미커밋 변경, 특정 commit 등을 대상으로 finding을 제시할 수 있음을 설명한다([Codex Code Review](https://developers.openai.com/codex/code-review)). 이 세 근거는 Codex가 build, test, lint, benchmark, review 같은 verification surface와 연결될 수 있음을 보여준다. 그러나 “실행 가능하다”는 말은 “실행했다”와 다르고, “테스트가 통과했다”는 말은 “요구사항 전체가 증명됐다”와 다르다.

Agent Evaluation은 일반 software test와 목적이 다르다. OpenAI Agent Evals 가이드는 trace 안의 모델 호출, 도구 호출, guardrail, handoff를 검사하고 workflow가 올바른 도구를 선택했는지와 정책을 따랐는지를 평가하는 방식을 설명한다([OpenAI Agent Evals](https://developers.openai.com/api/docs/guides/agent-evals)). Evaluation Best Practices는 생성형 모델 출력의 변동성 때문에 한두 예시나 전통적인 결정적 테스트만으로 agent system을 충분히 평가하기 어렵다고 안내한다([OpenAI Evaluation Best Practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices)). 단, 해당 문서의 Evals 플랫폼 수명 공지는 평가 원칙과 별도로 다뤄야 한다.

학술 연구도 `Generated ≠ Done` 메시지를 보강한다. SWE-bench Verified 연구는 benchmark에서 plausible 판정을 받은 패치 중 일부가 개발자 테스트 suite를 실패하거나 reference patch와 다르게 동작할 수 있음을 보고했다([Wang, Pradel & Liu](https://arxiv.org/abs/2503.15223)). AgentLens는 OpenHands trajectory에서 pass로 끝난 실행에도 blind retry, 검증 부족, 회귀와 연결된 “lucky pass”가 섞일 수 있다고 분석했다([AgentLens](https://arxiv.org/abs/2605.12925)). OpenAI의 SWE-bench Pro 감사 역시 benchmark task, prompt, test, gold patch가 항상 같은 신호를 주지 않을 수 있음을 보여준다([OpenAI coding eval audit](https://openai.com/index/separating-signal-from-noise-coding-evaluations/)). 이 근거는 test를 낮게 보라는 뜻이 아니라, 어떤 검증이 어떤 주장을 뒷받침하는지 분리해 말하라는 뜻이다.

`Investigate → Plan → Implement → Verify → Review`는 그래서 task-level workflow로 쓰기 좋다. Codex에는 큰 작업에서 먼저 조사와 접근을 제안하게 하는 `/plan` 흐름이 있고, 장기 작업 사례도 계획, 구현, 도구 실행, 관찰, 수정의 반복을 보여준다([Codex Prompting](https://developers.openai.com/codex/prompting), [Run long horizon tasks with Codex](https://developers.openai.com/blog/run-long-horizon-tasks-with-codex)). 그러나 이 순서는 OpenAI가 모든 변경에 강제하는 공식 표준 절차가 아니다. 작은 수정은 짧게 줄일 수 있고, 공용 API 변경이나 다중 모듈 작업처럼 영향이 큰 작업은 조사와 계획을 드러내는 편이 낫다는 위험 기반 heuristic으로 가르쳐야 한다.

## 실패 분류는 공식 빈도표가 아니라 수업용 렌즈다

코딩 agent 실패 연구는 context, instruction, execution, verification, coordination, memory, harness 문제를 나누어 설명할 재료를 준다. Zhao 등은 terminal coding-agent trajectory에서 wrong premise, output misreading, specification neglect 같은 trigger를 코딩했고, 예시에는 `cd` 실패를 성공으로 오독한 뒤 잘못된 디렉터리에서 build를 계속한 사례가 있다([Zhao et al., 2026](https://arxiv.org/html/2607.09510v1)). MAST는 multi-agent system에서 context loss, requirement neglect, role non-compliance, handoff 누락, 불완전한 검증 같은 failure mode를 분석했다([MAST, NeurIPS 2025](https://papers.nips.cc/paper_files/paper/2025/hash/b1041e52d3be19f0a9bc491657488e4a-Abstract-Datasets_and_Benchmarks_Track.html)). Xiong 등의 memory-agent 연구는 과거 경험 검색이 잘못 재사용되거나 오류를 전파할 수 있음을 보였지만, Codex Memory나 AGENTS.md를 평가한 것은 아니다([Xiong et al., ACL 2026](https://aclanthology.org/2026.acl-long.27/)).

따라서 이 교육의 일곱 실패 범주는 문헌의 공식 taxonomy나 Codex 실패 빈도표가 아니다. 수업에서는 `OBSERVED`, `POSSIBLE CAUSE`, `ENGINEERING RESPONSE`를 나눠 보여주는 편이 안전하다. 예를 들어 “wrong directory에서 build했다”는 관찰된 execution failure로 말할 수 있지만, “stale 문서가 Codex 실패의 주원인이다”라고 말하려면 별도 측정이 필요하다. 같은 방식으로 multi-agent handoff 누락은 연구 근거가 있지만, Codex subagent가 항상 같은 파일을 중복 편집한다는 제품 사실로 확장하면 안 된다([Codex Subagents](https://developers.openai.com/codex/multi-agents), [MAST](https://arxiv.org/html/2503.13657v2)).

Open Questions 상태도 이 경계에 맞춰 정리된다. OQ-005는 현재 제품 사실의 큰 윤곽을 공식 문서로 확인했지만, 실제 계정·Workspace·관리자 설정은 여전히 재확인이 필요하다. OQ-006은 Lost in the Middle과 long-context 연구의 bounded evidence를 확보했지만, 현행 Codex의 저장소 코딩 위치 민감성은 미실행이다. OQ-007은 verification 예시의 원칙 근거가 강화됐지만, 교육용 Demo repository와 실제 명령은 아직 정하지 않았다. OQ-009는 Loop 개선이 실제로 효과 있었는지 판단할 평가 기준 문제이며, 반복 실패의 관찰, 실제 결과, Demo 평가 근거가 생기기 전까지 unresolved로 남는다. OQ-011은 Harness/Loop 운영 정의 항목으로, 이번 연구가 후보 wording의 근거를 강화했지만 업계 합의나 최종 승인된 결정으로 취급해서는 안 된다. OQ-014 회사 보안 정책은 이번 근거로 해결되지 않는다.

## Conclusion

이번 확장 근거가 바꾸는 것은 Story가 아니라 Story를 말하는 정밀도다. Chatbot → Prompt → Context → Harness → Loop의 흐름은 유지된다. 다만 각 단계는 제품 기능명, 연구 결과, 기업 사례, 교육용 운영 정의를 구분해서 소개해야 한다. 특히 Harness와 Loop는 “고급 기능 목록”이 아니라 반복되는 마찰을 줄이는 작업 환경과 개선 루프의 관점으로 설명해야 한다.

다음 제작 단계에서는 이 보고서를 Curriculum이나 Demo 결정으로 곧장 바꾸지 말고, 각 주장을 slide와 demo에 넣을 때 근거 유형을 붙이는 것이 좋다. 현재 안전하게 쓸 수 있는 핵심 메시지는 **“Context를 늘리는 것보다 필요한 근거를 찾고, 실행 과정을 검증하고, 반복 실패를 시스템 개선으로 연결하는 능력이 중요하다”**이다. 아직 필요한 확인은 실제 Demo repository, 대상 계정의 Codex/ChatGPT 기능 노출, 회사 보안 정책, 그리고 현재 모델·표면에서의 재현 결과다.
