# C++ 밝기 통계 전환 실험

Experiment ID: `EXP-CPP-STATS-001` · 2026-11-05.

S68–S69의 밝기 통계 작업을 C++로 옮길 수 있는지 확인하는 별도 실험이다.
슬라이드·기존 Python Demo·State Tag는 변경하지 않는다. 이 실험은 기존
TRIAL-008의 재실행이나 새 Skill 호출 기록이 아니다.

## 측정 전 프로토콜

- 결과는 width, height, pixel_count, minimum, maximum, mean의6항목이다.
- 비어 있지 않은 직사각형 영상과1–65535의 최대 픽셀값을 보존한다.
  C++ 저장 자료형은16비트 부호 없는 정수이며 합계는64비트로 계산한다.
- 원래1024×768 합성 입력을 같은 값과 SHA-256으로 재사용한다. 입력 생성,
  검증·파일 읽기는 시간 측정 밖에서 수행한다.
- 기준 구현은 Python의 평탄화 전략을 C++로 옮겨 임시 vector에 복사한 뒤
  통계를 구한다. 실제 C++ 제품에서 발견한 기존 결함이라고 주장하지 않는다.
- 후보 A는 임시 복사 없이 행별 표준 min/max/sum 연산을 수행한다.
  후보 B는 임시 복사 없이 한 순회에서 최소·최대·합계를 함께 계산한다.
- 승자는 미리 정하지 않는다. 동일 출력, 실행시간, 임시 버퍼 할당을 비교한다.
  개선이 작거나 변동이 크면 선택 보류도 유효한 결과다.
- Mac의 동일 컴파일러·Release 최적화 조건에서 세 후보를 비교한다.
  Python 대비 속도 향상이나 Windows/MSVC 성능을 측정한 것이 아니다.
- 메모리는 별도 실행의 계측용 PMR resource를 통과한 임시 버퍼의 요청 횟수와
  최대 동시 요청 바이트다. 입력 영상·스택·전체 힙·RSS를 뜻하지 않는다.
- 손으로 확인한 작은 정답과 기존 Python 구현을 독립 정답 기준으로 사용한다.
  구현을 고정한 뒤 생성한 무작위 검증 입력의 seed와 해시를 남긴다.
- 시간 계측에는 메모리 계측을 넣지 않는다. 같은 입력의 세 후보 순서를
  순환하고 반복 호출을 묶어 측정한다. 원시 표본·반복 수·컴파일 옵션을 남긴다.

이하 결과는 위 프로토콜에 따른 로컬 관찰이며 교육 Demo 채택 결정과 구분한다.

## 관찰 결과

기능 이식과 세 후보의 로컬 비교를 완료했다. **이 Mac/컴파일 조건에서는 한 번에
집계하는 fused_pass가 가장 빨랐다.** 현재 S68의 Python 후보 순위와 다르므로,
기존의 “직접 반복은 제외” 결론을 C++에 그대로 옮길 수 없다.

주 입력: 동일한1024×768, 픽셀값0–255, C++ 저장형 uint16_t.
각 후보63표본(21순환 라운드 × 독립 프로세스3회)의 호출당 중앙값이다.
입력 생성·범위 검증·파일 읽기·메모리 계측은 시간에서 제외한다.

| 구현 | 중앙값 μs/호출 | 임시 버퍼 할당 횟수/호출 | 계측한 임시 버퍼 피크 B |
|---|---:|---:|---:|
| 임시 vector 복사 후 계산 | 1215.630 | 1 | 1,572,864 |
| 복사 없이 행별 표준 연산 | 1138.150 | 0 | 0 |
| 복사 없이 한 번에 집계 | 70.882 | 0 | 0 |

주 입력에서 기준선 대비 시간은 약94.2% 낮았고 중앙값 비율은 약17.15배였다.
이것은 이 비교용 기준선·입력·컴파일러·호스트에서의 관찰이다. Python 대비
속도, 실제 C++ 제품의 개선률, Harness/Skill의 인과 효과를 뜻하지 않는다.

### 다른 입력의 확인

| 입력 | 복사 기준선 μs | 행별 연산 μs | 한 번 집계 μs |
|---|---:|---:|---:|
| small_64x48 | 4.829 | 3.780 | 0.447 |
| large_2048x1536 | 5491.819 | 4621.533 | 279.092 |
| padded_1024x768 | 1239.229 | 1136.001 | 70.995 |
| wide16_1024x768 | 1213.808 | 888.252 | 70.687 |

다섯 입력 모두 같은 후보가 가장 빨랐다. 작은 영상,4배 픽셀 수, 행 여백7개,
16비트 픽셀 범위를 포함했다. 이것만으로 모든 영상·CPU·컴파일러의 순위를
보장하지 않는다.

### 분산과 컴파일러 점검

주 입력의 프로세스별 중앙값은 다음과 같다.

- 임시 vector 복사 후 계산: 1479.315 / 1214.170 / 1214.085 μs.
- 복사 없이 행별 표준 연산: 1138.150 / 1137.189 / 1138.861 μs.
- 복사 없이 한 번에 집계: 70.560 / 70.942 / 71.086 μs.

복사 기준선의 첫 프로세스와 이후 프로세스 사이 차이가 있다. CPU 배치·주파수·
온도·시스템 배경 작업을 고정하지 않았으며 정밀한 보편적 배수로 해석하지 않는다.
원시 표본은 [samples.csv](results/samples.csv)에 모두 보존한다.

차이가 큰 이유를 살피기 위해 같은 소스·Release 조건의 컴파일러 벡터화
remark를 별도로 확인했다. fused_pass의 반복문은 vectorization width8로
벡터화됐고, 이 libc++의 min_element/max_element 반복문에는 벡터화되지
않았다는 remark가 있다. accumulate 일부는 벡터화됐다. 이 기록은 컴파일러에
따라 판단이 바뀔 수 있음을 설명하는 근거이며 전체 시간 차이의 단독 원인을
분리한 실험은 아니다. [원문](results/compiler-vectorization.txt).

## 정확성·검증

- 먼저 빈 결과를 반환하는 임시 stub으로 계약 검사의 실패를 확인했다.
  [실패 기록](results/initial-red-test.txt).
- 작은 수동 정답,16비트 최대값,32비트 합계 초과, 최소 길이의 strided ROI,
  빈 입력·잘못된 stride·저장 길이·범위·차원 오버플로 거부 등20개 검사를
  Release와 AddressSanitizer/UndefinedBehaviorSanitizer에서 통과했다.
- 기존 Python image_statistics를 수정하지 않고 외부 정답으로 사용했다.
  수동 예제3개·측정 입력5개·고정 구현 뒤 생성한 무작위 입력48개, 총56개에서
  세 후보의168개 결과가6항목 모두 정확히 일치했다. 후보끼리 같다는 것만으로
  통과 처리하지 않았다.
- 주 입력 SHA-256은 기존값
  `26df8e7b296672840d97cf5d9273e6660003afd680c62c7751d382c2d067fec9`와
  일치한다. seed와 입력별 지문, 외부 정답은 [fixtures.json](results/fixtures.json),
  후보별 실제 반환값은 [correctness.json](results/correctness.json)에 남겼다.
- 총945개 원시 시간 표본,15개 프로세스 세션과 소스/정답 코드 해시를 보존했다.
  실행 후 소스 해시와 Demo 작업 트리가 측정 전과 같음을 확인했다.

C++ 합계는 uint64_t 범위 안에서만 지원하며 검증 입력의 합계는 정확히
표현 가능한 범위다. Python의 임의 정밀도 정수에 가능한 모든 거대 입력을
수학적으로 동등하게 증명한 것은 아니다.

## S68–S69에 대한 판단

C++ 예제로 기능을 유지하고 실제 측정 자료를 만드는 것은 가능하다. 현재의
두 장 구조와 각5분을 유지하면서, S68은 “복사 제거 후보를 측정해 선택”,
S69는 “선택한 변경의 시간·계측한 추가 버퍼·동작 확인”으로 구성할 수 있다.
이번 결과를 쓴다면 수동 반복 제외 대신 fused_pass 선택으로 설명해야 한다.

다만 이식 기준선은 Python의 전략을 C++로 옮긴 실험용 코드다. 현재 Python
Demo를 C++로 교체한 제품 이력이나 기존 Skill 실행의 C++ 성과로 표현하면
안 된다. S66의 실제 Skill 기록과 후속 Harness 설명의 출처 정렬, 채택 여부는
별도 사용자 판단으로 남긴다. 슬라이드·Notes·기존 Trial/State는 변경하지 않았다.
