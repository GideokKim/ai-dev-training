# ACT3→ACT4 — 반복 보정을 다음 작업의 개선으로 잇기

Decision: DEC-0092. Date:2026-10-25. Baseline:`29b4b24`.
Status: APPROVED CONTENT / local production evidence is recorded in the revision result.

## 수정 이유

이전 S74–S78은 권한·전역 지침·시작 경고의 구분에 집중했다. 이 사실들은 실행 조건을
설명하지만, 그것만으로 왜 다음 ACT의 개선 과정이 필요한지 드러나지 않았다.
이번 수정은 **사람이 매번 보정해도 다음 작업이 쓰는 체계는 그대로일 수 있다**는
문제를 화면에서 읽게 한다. 이미 구축한 Harness의 가치나 실제 성공을 부정하지 않는다.

S72는 검토한 수행 기반을 다른 프로젝트의 출발점으로 쓰는 설계 가치,
S73은 공통 기반에 프로젝트 기준을 연결하는 관계를 유지한다. S73의 마지막 Notes
질문만 운영 중 사람의 보정이 다음 작업에 남는지로 바꾼다. S74에서 실제 성공의
범위를 회수하고, S75–S77에서 하나의 교육용 가정을 이어간다.

## 화면과 다음 질문

### S74 — 이번 성공만으로 다음 작업까지 확인되지는 않는다

밝기 통계 작업의 성공은 기록된 명세·코드·입력·환경에서 확인한 결과다. 그 성공만으로 이후 모든 작업의 요구와 검증 범위를 확인한 것은 아니다.

화면: 왼쪽 실선은 실제 밝기 통계 변경과 명세·수행 방법·검증 근거, 오른쪽 점선은 다음 작업의 다른 요구·입력·검증 범위에 대한 물음표다. 수치나 새 성공/실패 판정을 만들지 않는다.

근거 경계: FROZEN WITH SCOPE / TEACHING MODEL — STATE-04-PERF의 성공 범위만 회수한다. 오른쪽 다음 작업은 질문이며 실제 후속 실패·반복 보정·새 Product State가 아니다.

다음: “그 기반으로 실제 작업을 하다가 사람이 추가로 확인할 부분을 찾는다면, 그 보정은 어디에 남을까요?”

### S75 — 작업 중 사람이 보정할 일이 생긴다면?

추가 확인이 필요하다는 점을 사람이 발견해 이번 요청을 보정하는 상황을 가정한다. 무엇이 이 빈틈을 만들었는지와 어느 출처를 바꿔야 하는지는 아직 판단하지 않는다.

화면: Agent 작업의 변경한 부분 확인→사람의 관련 동작 질문→관련 동작도 확인해 달라는 추가 요청의 세 영역이다. 개념 사례의 점선·라벨을 사용하며 실행 Screenshot이나 PASS/FAIL 결과를 만들지 않는다.

근거 경계: CONCEPTUAL — 추가 확인을 요청한다는 교육용 가정이다. 실제 graypipe의 검증 누락·실패나 새 Trial이 아니며 Agent·지침·제품 코드 중 어느 것이 원인인지 확정하지 않는다.

다음: “이번 요청에 그 말을 더하면, 다음에도 읽을 공통 수행 지침까지 바뀔까요?”

### S76 — 이번 요청은 보정해도, 공통 지침은 그대로다

이번 요청의 검증 범위를 보정해도 공통 지침을 따로 갱신하지 않은 상황이라면, 다음 작업이 읽는 수행 방법은 이전 상태로 남는다. 현재 Task 보정과 재사용 체계 개선은 별도다.

화면: 왼쪽 이번 요청에 관련 동작 확인 문장을 넣고 현재 작업의 검증 범위를 보정했다고 표시한다. 오른쪽 다음에도 읽을 공통 지침은 이전 수행 방법 그대로라는 별도 영역이다. 두 영역의 대상을 큰 제목으로 구분한다.

근거 경계: CONCEPTUAL — 공통 지침을 갱신하지 않은 경우의 비교다. 실제 요청·원본 지침 변경 이력이 아니며 지침이 누락 원인이라고 단정하거나 보정 성공을 주장하지 않는다.

다음: “공통 지침은 그대로인데, 다음 작업에서도 비슷한 확인이 필요하면 어떻게 될까요?”

### S77 — 다음 작업에서도 같은 보정이 반복된다면?

공통 수행 지침을 갱신하지 않은 교육용 상황에서 작업 A/B/C마다 사람이 같은 확인을 추가로 요청한다. 사람의 경험이 다음 작업에 쓸 체계의 개선으로 돌아오지 않는 문제가 남는다.

화면: 상단의 변하지 않은 공통 지침 아래에 시간상 이어지는 작업 A/B/C와 동일한 사람의 보정을 반복 배치한다. 대화의 반복과 공통 체계의 정체를 동시에 보이며 결과 수치나 성공 체크를 쓰지 않는다.

근거 경계: CONCEPTUAL — 작업 A/B/C는 반복을 설명하는 도식이며 실제 Trial·Subagent·비교 실험이 아니다. 반복 횟수·토큰·시간·성과를 측정하지 않았고 원인은 미확정이다.

다음: “이 경험으로 다음 작업의 체계를 바꾸려면, 무엇을 근거로 어디를 고칠지 판단해야 할까요?”

### S78 — 반복 보정을 개선으로 잇는 기록

원래 기준과 적용 지침, 실제 수행·검증 범위, 사람이 보정한 내용을 함께 남겨야 무엇이 달랐는지 비교할 수 있다. 그 기록을 근거로 원인과 변경 대상을 판단하고 다시 확인할 필요가 생긴다.

화면: 왼쪽 하나의 기록 틀에 기준과 지침/실제 수행/사람의 보정을 정렬한다. 오른쪽은 원인·변경 위치·재확인에 대한 세 질문이며 답을 미리 채우지 않는다. 상단은 보정 문장만으로 판단하기 어려움, 하단은 다음 작업의 체계 검토 필요다.

근거 경계: TEACHING MODEL — 개선 검토에 필요한 기록 틀이다. 실제 새 보고서·원인 확정·지침 갱신·재평가·품질 향상을 입증하지 않으며 AI 모델의 자동 학습을 뜻하지 않는다.

다음: “우리 업무에서 매번 사람이 보정하는 하나를 골라, 어떤 근거와 담당이 필요한지 생각해 보겠습니다.”

### S79 — 같은 보정을 되풀이하지 않으려면?

다시 알려주는 정보·다시 지시하는 절차·빠뜨린 확인 기준 중 반복 보정 하나를 고른다. 그 근거와 원래 출처, 검토·갱신·재확인 책임을 생각하고 다음 작업에 반영할 개선 과정이 필요한 이유를 회수한다.

화면: 세 후보에서 반복 보정 하나 선택으로 모은 다음 근거·출처와 검토·재확인 책임의 두 질문으로 나눈다. 하단에 다음 ACT의 원인 확인·체계 변경·재평가를 명시해 Loop가 필요한 이유를 화면에서 읽게 한다.

근거 경계: TEACHING MODEL — 개인 성찰이며 작성·실습·공개 답변을 요구하지 않는다. 실제 누락 원인·수정 대상·담당·재평가 결과를 확정하지 않는다. ACT4의 구성·시간·관찰/가상 경계를 유지한다.

다음: “만든 기반은 재사용할 수 있습니다. 이제 사람이 반복해서 보정한 경험을 다음 작업의 개선으로 되돌리는 방법을 보겠습니다.” ACT4 제목 S80을 거쳐 S81의 기존 실제 성공 회수와 별도 가상 유지 사례로 이어간다.

## ACT4와의 연결

S79 하단은 “다음 ACT: 기록으로 원인을 확인하고, 체계를 고친 뒤 다시 평가한다”다.
ACT4가 필요한 이유를 발표자 설명에만 맡기지 않는다. 현재 대화의 보정은 영속적인
출처 수정이나 검증된 개선을 뜻하지 않는다. 보정 문장을 무조건 규칙으로 추가하는
처방 대신, 원래 기준·실제 수행·사람의 보정으로 원인과 수정 범위를 판단해야 한다.

S80 제목 다음 S81은 기존 실제 밝기 통계 성공을 짧게 회수하고 유지할 문제를 연다.
이후 기존 DEMO-04A의 가상 프로젝트 변화는 반복 보정을 만드는 한 원인을 상세히
살펴보는 사례다. S75–S77이 바로 그 제품의 후속 실제 이력이 되는 것은 아니다.
기존 DEMO-04B S93–S97은 실제 Resize 조사에서 평가·보고 기준을 바꾼 Meta 사례다.
운영 경험을 체계에 반영하는 과정의 상세 설명은 이 ACT4 구간에 남긴다.

ACT4는 S80–S98/19장·81분, 순서·장별 시간/Mode·Notes·Evidence·Claim을 그대로 둔다.
가상 지침 변경의 평가 결과를 만들거나 실제 Meta 사례를 압축하지 않는다.
