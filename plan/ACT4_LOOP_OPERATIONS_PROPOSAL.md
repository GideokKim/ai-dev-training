## 두 사례의 역할

- **한 목표의 수정 루프.** ACT3에서 익힌 밝기 통계 함수를 다시 쓴다. 임시 할당을 줄이면서 기존 여섯 출력과 시간 조건을 지킨다. 목표와 완료 기준은 고정한다. 바뀌는 것은 코드 후보, 남은 지적, 검사 근거다. 실제 graypipe 기록은 문제 배경의 출처이고, 아래 두 모델의 대화·재시도는 교육용 설계다. [기존 개편 결정](DECISIONS.md#dec-0097--produce-the-approved-goal-directed-act4-review-loop)
- **팀 업무를 잇는 운영 사례.** 김기덕의 2026년 6월 16일 운영기에서 GitLab 이슈별 작업 공간, 구현 담당과 검토 담당, 병합 요청을 확인하는 팀원을 따라간다. 이 사례의 고유한 업무 접수 정책은 S88의 발표 Notes 배경으로 보존한다. [사내 Codex 운영기](https://gideokkim.github.io/codex/loop-engineering/)

## S83의 8단계 워크플로우 원문

| 단계 | 하는 일 | 남기는 결과 |
|---|---|---|
| 1. 목표와 범위 정의 | 무엇을 바꾸고 무엇을 유지할지, 완료 기준을 정합니다. | 목표·제약·완료 기준 |
| 2. 현재 상태 조사 | 코드·명세·기존 변경 사항을 읽고, 문제나 현재 성능을 확인합니다. | 조사 결과·재현 결과·기준선 |
| 3. 계획과 실행 환경 준비 | 변경 순서와 검증 방법을 정합니다. 필요하면 Worktree와 Subagent를 준비합니다. | 작업 계획·역할·실행 조건 |
| 4. 구현 | 정한 범위 안에서 코드를 변경합니다. | 변경 코드·테스트 |
| 5. 실행 검증 | 빌드·테스트·벤치마크 등을 실행하고 기존 결과와 비교합니다. | 실행 결과와 근거 |
| 6. 독립 검토 | 요구사항 누락, 회귀 가능성, 테스트 부족을 별도 관점에서 검토합니다. | 검토 의견·남은 문제 |
| 7. 다음 행동 판단 | 보완할지, 완료할지, 중단하고 사람에게 확인할지 결정합니다. | 계속·완료·중단 판단 |
| 8. 결과 정리와 인계 | 최종 변경, 검증 결과, 미실행 항목과 후속 작업을 정리합니다. | 사람이 확인할 결과 보고 |

보완할 때에는 4단계 구현으로 복귀해 5–7단계를 다시 거친다. 완료 보고에는 변경과 검증 근거를, 미완료 인계에는 미실행 항목과 후속 확인을 함께 남긴다.

## 연구 화면에 실을 비교

PairCoder의 HumanEval 코드 생성 실험은 반복 오류 때 역할을 교대할 수 있다. 표 2에서 초기 구현 담당을 GPT-3.5-turbo로 고정했다. pass@1은 단독 69.51%, 같은 모델로 쌍을 구성하면 81.16%, 초기 검토 담당이 GPT-4이면 90.01%, minimax-abab-chat이면 48.19%였다. 초기 역할·비교 대상·과제를 그래프에 함께 쓴다. 이 결과로 설명할 수 있는 범위는 해당 벤치마크에서 모델 조합에 따라 성과가 달랐다는 것이다. 팀의 GitLab 운영기는 역할 분리의 사례로 인용한다.
