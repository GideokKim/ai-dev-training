# ACT4 개편안 — 한 번 맡긴 목표의 구현·검토·수정

**ACT4 지적·수정·측정 DEC-0150 · ACT4 도입 DEC-0149 · ACT3 마무리 S77 DEC-0148 · 2026-11-03**

S77은 점심 전에 수정·테스트까지 맡긴 개발자와 점심 후 구현 시작을 되묻는 답을 나란히 보여준다. 작은 배지로 S76의 팀 지침·검증 도구를 이어받는다. S79는 “응, 시작해.”라는 답으로 점심 뒤 대화를 이어 간다. 첫 수정안이 나와도 개발자가 검토 지적을 다시 전달한다. S80은 그 검토 순간을 루프로 다시 보고, S81은 원래 요청과 완료 기준의 출처를 구분한다. S82에서 첫 후보의 목록 생성식을 확대하고, S83에서 근거 있는 지적을 선별해 S84에서 전체 복사와 행별 집계를 비교한다. S85에서 시간 근거가 없으면 같은 후보를 먼저 측정하고 그 결과로 다음 행동을 정한다. S88에서 GitLab 운영 사례를 처음 소개한다.

## 두 사례의 역할

- **한 목표의 수정 루프.** ACT3에서 익힌 밝기 통계 함수를 다시 쓴다. 임시 할당을 줄이면서 기존 여섯 출력과 시간 조건을 지킨다. 목표와 완료 기준은 고정한다. 바뀌는 것은 코드 후보, 남은 지적, 검사 근거다. 실제 graypipe 기록은 문제 배경의 출처이고, 아래 두 모델의 대화·재시도는 교육용 설계다. [기존 개편 결정](DECISIONS.md#dec-0097--produce-the-approved-goal-directed-act4-review-loop)
- **팀 업무를 잇는 운영 사례.** 김기덕의 2026년 6월 16일 운영기에서 GitLab 이슈별 작업 공간, 구현 담당과 검토 담당, 병합 요청을 확인하는 팀원을 따라간다. 이 사례의 고유한 업무 접수 정책은 S88의 발표 Notes 배경으로 보존한다. [사내 Codex 운영기](https://gideokkim.github.io/codex/loop-engineering/)

## 같은 지적을 S83–S85에서 따라가기

| 장면 | 교육용으로 설계한 연결 |
|---|---|
| S83 · 검토 | 목록 생성식에서 모든 픽셀을 별도 목록에 복사하는 위치를 짚는다. 수정에 넘기는 지적에는 추적 표식 R1을 작게 붙인다. |
| S84 · 구현 | 검토에서 넘겨받은 지적으로 전체 임시 목록을 없애고 행별로 집계한다. 여섯 출력 보존, 할당 피크 감소, 실행시간 유지를 같은 입력에서 확인해야 한다. |
| S85 · 재검토 | 가령 시간 기록이 빠졌다면 같은 후보를 먼저 측정한다. 실제 근거를 보고 검토에 제출하거나 확인된 위반을 다음 수정으로 보낸다. 측정 근거를 얻을 수 없거나 한도에 닿았으면 후보와 미확인 항목을 사람에게 넘긴다. |

R1, 두 후보와 측정 분기는 교육용 재구성이다. 원래 제품의 성능 수치를 이 후보들의 성과로 인용하지 않는다.

## 연구 화면에 실을 비교

PairCoder의 HumanEval 코드 생성 실험은 반복 오류 때 역할을 교대할 수 있다. 표 2에서 초기 구현 담당을 GPT-3.5-turbo로 고정했다. pass@1은 단독 69.51%, 같은 모델로 쌍을 구성하면 81.16%, 초기 검토 담당이 GPT-4이면 90.01%, minimax-abab-chat이면 48.19%였다. 초기 역할·비교 대상·과제를 그래프에 함께 쓴다. 이 결과로 설명할 수 있는 범위는 해당 벤치마크에서 모델 조합에 따라 성과가 달랐다는 것이다. 팀의 GitLab 운영기는 역할 분리의 사례로 인용한다. [PairCoder 표 2, §4.6](https://aclanthology.org/2026.findings-acl.149.pdf#page=7)
