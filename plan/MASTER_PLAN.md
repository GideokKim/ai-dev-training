# ChatGPT & Codex 개발자 교육 기획 원본

> 상태: 기획 기준 문서
>
> 이 문서는 요약 자료가 아니라 교육의 목표, 전달 방식, 서사, 단계별 설계,
> 반복 메시지와 미확정 사항을 보존하는 최상위 기획 명세다. 이후 교육
> 산출물은 이 문서를 기준으로 작성하고, 여기에 적힌 핵심 의도와 인과관계를
> 축약하거나 조용히 바꾸지 않는다.

## 0. 문서의 권위와 사용 원칙

### 0.1 Source of Truth

- `plan/MASTER_PLAN.md`를 curriculum, storyline, demo, slide, speaker notes,
  PPT를 포함한 모든 후속 교육 산출물의 최상위 기획 기준으로 사용한다.
- 후속 문서가 이 문서와 충돌하면 임의로 어느 한쪽을 고치지 않는다. 충돌을
  기록하고 기획 결정이 내려질 때까지 미확정으로 표시한다.
- 새 자료를 만들기 전 관련 `plan/` 문서를 먼저 확인한다.
- 이 문서의 핵심 기획 의도와 결정사항은 기존 문서를 고칠 때도 보존한다.
- 이 문서에서 정하지 않은 사항은 TODO 또는 미확정으로 남긴다. 빈칸을
  그럴듯한 가정으로 채우지 않는다.

### 0.2 제품 기능에 관한 사실 확인

- ChatGPT와 Codex의 현재 기능, UI, 지원 범위에 관한 사실을 교육 자료에
  넣을 때는 필요에 따라 최신 OpenAI 공식 자료를 우선 확인한다.
- 교육에서 다루는 개념적 설계와 특정 시점의 제품 기능을 구분한다. 개념을
  설명했다는 이유로 특정 기능이 모든 제품·계정·환경에서 지원된다고
  단정하지 않는다.
- `Lost in the Middle` 등 외부 연구나 효과에 관한 설명은 근거를 확인하고,
  연구가 뒷받침하는 범위를 넘어 일반화하거나 과장하지 않는다.
- 공식 자료 확인이 필요한 항목은 검증 전까지 TODO 또는 미확정으로 둔다.

### 0.3 산출물 범위

- 이 프로젝트는 교육 기획과 교육 자료 제작을 위한 것이다.
- 최종 PPT 제작은 별도 지시가 있기 전까지 시작하지 않는다.
- 교육생이 노트북으로 직접 수행하는 실습은 교육 방식에 포함하지 않는다.

## 1. 교육 기본 정보

### 1.1 주제

개발자를 위한 ChatGPT & Codex 활용 및 AI-Native Development.

### 1.2 교육 시간

- 순수 교육 내용 기준 총 6시간, 즉 교육 내용 360분을 구성해야 한다.
- 휴식 시간은 순수 교육 시간에 포함하지 않는다.
- 모듈별 시간 배분, 휴식 횟수와 길이는 아직 정해지지 않았다. 임의로
  확정하지 말고 TODO로 유지한다.

### 1.3 교육 방식

- 교육생은 노트북을 가져오지 않으며 직접 실습하지 않는다.
- 강의, 실제 사례, Before/After 비교, Codex 화면 시연, Live Demo를 중심으로
  진행한다.
- 기능 이름과 목록을 차례로 설명하는 기능 소개 교육으로 만들지 않는다.
- 개발자가 AI 활용을 바라보는 사고방식과 실제 업무에 적용할 인사이트를
  얻도록 설계한다.
- 시연과 사례는 설명을 보조하는 수단이다. 제품 기능의 나열이 교육의
  구조나 핵심 목표를 대신해서는 안 된다.

## 2. 교육생 특성 및 난이도 설계

### 2.1 교육생 분포

교육생은 모두 개발자지만 AI 활용 경험과 숙련도는 크게 다르다. 대표적인
수준은 다음과 같다.

| 수준 | 관찰되는 활용 방식 |
| --- | --- |
| Level 0 | AI를 거의 사용하지 않는다. |
| Level 1 | ChatGPT를 검색·질문용 챗봇처럼 사용한다. 에러 메시지를 붙여넣고 해결책을 묻는 정도다. |
| Level 2 | 코드를 붙여넣고 설명, 수정, 리팩터링 등을 요청한다. |
| Level 3 | Codex 등 Agent를 사용해 repository를 탐색하고 실제 개발 작업을 수행한다. |
| Level 4 | AGENTS.md, Context Engineering, Skills, Subagents, Memory, Harness 등을 구성해 사용한다. |

일부 개발자는 이미 높은 AI 활용 역량을 갖추고 있다. 한편 상당수는 현장
출장이 많아 AI 활용을 깊게 공부할 시간이 부족하고, ChatGPT를 단순 챗봇
수준으로 사용하는 비중이 높다.

### 2.2 한 교육 안에서의 난이도 원칙

- 교육생을 초급반과 고급반으로 나누지 않는다.
- 하나의 공통 Story를 따라가되, 각 수준의 개발자가 자기 현재 위치와
  다음 단계를 발견할 수 있도록 설계한다.
- 초급자만을 위해 내용을 단순화하여 고급자의 인사이트를 없애지 않는다.
- 고급 사용자만 이해할 수 있는 전제와 용어로 교육을 구성하지 않는다.
- 완성된 고급 시스템을 처음부터 제시하고 설명하지 않는다. 필요가 생기는
  순서대로 개념을 도입한다.

### 2.3 난이도별 다음 단계

교육생 수준을 바탕으로 각자가 다음 단계로 이동하도록 돕는 것이 설계
목표다. 제공된 원문은 다음 초급자 문구 도중 끝나므로, 나머지 수준별
문구와 구체적인 Level 0–4 교차표는 추가 원문 확인 전까지 미확정이다.

- 초급자에게 전달할 명시적 다음 단계: “ChatGPT에 코드만 붙여넣지 말고
  Codex로 repository를 보게 해야겠다.”
- Level 1–4 각각의 구체적인 다음 단계: TODO. 원문 후속 내용을 확인한 뒤
  보완한다.

## 3. 교육의 최우선 목표와 완료 시 역량

### 3.1 최우선 목표

교육의 최우선 목표는 **개발자 조직 전체의 AI 사용 역량 균질화**다.

이 교육은 AI 전문가를 양성하는 과정이 아니다. 조직 안에서 AI 활용 경험이
서로 다른 개발자들이 공통된 기본 관점과 업무 흐름을 공유하도록 돕는다.

### 3.2 교육 후 모든 개발자가 갖춰야 하는 최소 이해

교육이 끝났을 때 모든 개발자는 최소한 다음을 이해해야 한다.

1. ChatGPT와 Codex의 역할 차이를 설명할 수 있다.
2. 단순 질의응답에서 벗어나 AI에게 개발 업무의 문제 해결 과정을 맡기는
   사고방식을 이해한다.
3. Codex가 repository 안에서 필요한 정보를 직접 조사하도록 할 수 있다는
   점을 이해한다.
4. AI 개발에서 Context와 Verification이 중요한 이유를 이해한다.
5. `Investigate → Plan → Implement → Verify → Review` 흐름을 이해한다.
6. AGENTS.md를 비롯한 프로젝트 Context가 어떤 역할을 하는지 이해한다.
7. 자기 현재 활용 수준에서 시도할 다음 단계가 무엇인지 알 수 있다.

### 3.3 숙련 개발자에게 제공할 추가 인사이트

이미 AI를 능숙하게 사용하는 개발자도 다음 주제에서 새로운 관점을 얻어야
한다.

- Context Engineering: 필요한 정보를 적절한 시점에 찾고 제공하는 설계
- Harness Engineering: AI가 일하는 방법과 환경을 설계하는 관점
- Loop Engineering: 반복되는 실패를 관찰하고 제품 코드 또는 Harness를
  개선하는 반복 구조

## 4. 교육 전체의 핵심 Story

### 4.1 진화 과정

교육의 서사는 다음 진화 과정을 따라간다.

`Chatbot → Prompt Engineering → Context Engineering → Harness Engineering
→ Loop Engineering → AI-Native Development`

이 용어들을 첫 장에서 정의하고 사전식으로 설명하지 않는다. 각 개념은 앞
단계에서 드러난 문제를 해결하려는 자연스러운 시도로 등장해야 한다.

### 4.2 반복되는 Engineering Loop

모든 주요 전환은 다음 패턴으로 이야기를 전개한다.

1. Codex를 처음 쓰는 개발자가 자연스럽게 선택할 만한 방법을 시도한다.
2. 그 방법은 처음에는 실제로 잘 동작한다.
3. 사용 범위가 커지면서 문제가 나타난다.
4. 왜 문제가 생겼는지 분석한다.
5. 문제를 해결하기 위한 다음 Engineering 단계가 등장한다.
6. 개선된 방식으로 다시 작업한다.
7. 규모나 상황이 바뀌면서 새로운 문제가 나타난다.
8. 다시 개선한다.

이를 `Attempt → Works → Problem → Why → Improvement → New Problem →
Improvement`라는 스토리 구조로 반복한다. 개선의 필요성이 장면에서 먼저
보이고, 개념 이름은 그 다음에 소개한다.

## 5. 단계별 서사와 개념 도입 순서

### 5.1 Stage 0 — Chatbot Developer: AI를 코드로 데려가기

#### 출발점

가장 일반적인 개발자는 ChatGPT에 다음과 같이 요청한다.

- “이 에러 뭐야?”
- “이 코드 설명해줘.”
- “이 함수 리팩터링해줘.”

기존 작업은 다음과 같다.

`Developer → 필요한 코드/에러를 직접 수집 → ChatGPT에 복사 → 답변 → IDE에 복사`

#### 시연과 전환

이 흐름에서 Codex를 소개한다. 개발자가 코드를 일일이 AI에게 가져가는 대신,
AI를 repository로 데려온다. Codex가 repository 안에서
`search → read → trace → answer`하는 모습을 보여준다.

#### 고정 Insight

> 코드를 AI에게 가져가지 말고 AI를 코드로 데려가라.

Codex의 실제 화면, 명령, 제품별 지원 범위는 시연을 준비할 때 최신 공식
자료와 현재 사용 환경을 확인한다.

### 5.2 Stage 1 — Prompt Engineering: 요청을 구조화하기

#### 자연스러운 첫 시도

개발자는 Codex에게 바로 다음과 같은 짧은 요청을 할 수 있다.

> filter 모듈의 성능을 개선해줘.

결과가 기대에 미치지 못하면 Prompt에 작업의 중요한 조건을 더 명확히
포함하는 방향으로 발전한다.

#### 전달할 요청 요소

- **Goal:** filter 처리 시간 감소
- **Context:** 작업 대상과 현재 문제를 이해하는 데 필요한 정보
- **Constraints:**
  - public API를 변경하지 않는다.
  - 결과 정확도를 유지한다.
  - 새로운 dependency를 추가하지 않는다.
- **Process:**
  1. 관련 코드를 조사한다.
  2. 병목 후보를 분석한다.
  3. 변경 계획을 작성한다.
  4. 승인된 범위만 수정한다.
- **Verification:** unit test와 benchmark로 결과를 확인한다.

이 단계에서는 Prompt를 구체화하면 작업 결과와 범위가 나아질 수 있음을
보여준다. 다만 Prompt Engineering을 교육의 종착점처럼 다루지 않는다.

#### 다음 문제가 생기는 지점

작업을 거듭하면 개발자는 다음 내용을 매번 되풀이한다.

- build를 어떻게 하는지
- test를 어떻게 하는지
- API를 바꾸면 안 된다는 점
- 프로젝트의 style
- benchmark 방법

이때 자연스럽게 다음 질문을 제기한다.

> 왜 매번 같은 것을 설명하고 있지?

이 반복 문제에서 Context Engineering으로 넘어간다.

### 5.3 Stage 2 — Context Engineering: 반복 지시를 프로젝트에 두기

#### AGENTS.md를 처음 도입

반복되는 공통 지시를 repository에 저장하기 위해 AGENTS.md를 도입한다.
초기에는 프로젝트의 공통 정보를 한곳에 정리함으로써 잘 동작하는 경험을
보여준다.

초기 AGENTS.md에 담길 수 있는 항목은 다음과 같다.

- Project
- Architecture
- Build
- Test
- Coding Rules
- Performance Rules
- Git Rules
- Review Rules

#### 모든 내용을 한 파일에 넣을 때의 문제

처음에는 다음과 같은 생각을 자연스럽게 유도한다.

> AGENTS.md에 모든 걸 넣으면 되는 것 아닌가?

이 접근으로 파일이 `100 lines → 300 → 700 → 1500...`처럼 계속 커지는
상황을 보여준다. 이 숫자는 교육에서 파일 비대화의 진행을 설명하기 위한
예시이지, 보편적인 기준선이나 제품 제한으로 주장하지 않는다.

파일이 커지고 프로젝트가 변하면서 다음 문제가 발생한다.

- 중요한 규칙이 누락될 수 있다.
- 현재 작업과 관련 없는 Context까지 항상 포함될 수 있다.
- 오래된 규칙과 새로운 규칙이 충돌할 수 있다.
- Context와 Token 사용량이 불필요하게 늘 수 있다.
- 지시의 우선순위가 불명확해질 수 있다.
- 긴 Context에서 중간 정보가 어떻게 활용되는지 문제가 제기될 수 있다.

`Lost in the Middle` 등의 개념은 이 지점에서 소개한다. 근거를 확인하고
과장하지 않으며, 해당 근거가 말하는 범위와 한계를 구분한다.

#### 개선: 필요한 정보가 필요한 순간에 들어오게 하기

핵심 Insight는 다음과 같다.

> Context는 많을수록 좋은 것이 아니다. 필요한 순간에 필요한 Context가
> 들어가는 것이 중요하다.

따라서 하나의 거대한 AGENTS.md를 유지하는 대신 역할을 분리한다.

| Before | After |
| --- | --- |
| 모든 지식을 한 파일에 쌓는 거대한 AGENTS.md | 핵심 원칙과 관련 지식을 찾는 경로를 안내하는 AGENTS.md |
| 모든 세부 지침을 항상 함께 제공 | 세부 정보는 필요에 따라 docs/, rules/, skills/ 등에 둔다 |

AGENTS.md의 역할은 다음과 같이 발전한다.

`모든 지식을 담는 파일 → 필요한 지식을 찾도록 안내하는 Router`

Progressive Disclosure는 정보를 한 번에 전부 싣지 않고 필요한 때 필요한
정보를 드러내는 개념으로 이 흐름에서 설명한다.

### 5.4 Stage 3 — Harness Engineering: 지식에서 작업 환경과 방법으로

#### Context만으로 남는 문제

Context를 정리해 알려줘도 AI가 일하는 방식은 매 작업마다 달라질 수 있다.

- 어떤 경우에는 `search → edit` 순서로 움직인다.
- 다른 경우에는 `edit → test`로 움직인다.
- 어떤 경우에는 test 자체를 수행하지 않는다.

이 문제를 다음 문장으로 드러낸다.

> Context는 알려줬는데, 일하는 방식 자체가 안정적이지 않다.

#### Harness의 전환

이 시점에 Harness Engineering을 도입한다.

`AI에게 지식을 제공 → AI가 일하는 방법과 환경을 설계`

Skills는 필요한 작업에 필요한 절차와 지침을 선택적으로 제공하는 예로
소개한다. 예시 구조는 다음과 같다.

```text
skills/
├── build/
├── test/
├── benchmark/
└── code-review/
```

모든 절차를 상시 Context에 넣지 않고 작업에 맞는 Skill과 지침을 선택한다.

`Task → 필요한 Skill → 필요한 Instruction Load → Execute`

#### 고정 Insight

> AI에게 지식을 주는 것을 넘어 일을 수행하는 방법을 제공한다.

`Skills`라는 제품 또는 프로젝트별 기능의 현재 구체적 동작·설정 방법은
해당 시점의 공식 자료와 실제 교육 환경에서 확인한다. 이 명세는 필요한
업무 절차를 선택적으로 불러오는 설계 의도를 고정한다.

### 5.5 Subagent: 역할과 Context 복잡도를 분리하기

Subagent를 고급 기능 자랑으로 소개하지 않는다. 하나의 Agent가 큰 작업에서
Architecture, Performance, Tests, Documentation을 모두 조사하면 Context가
다시 커지고 역할도 복잡해지는 문제를 먼저 보여준다.

그 문제를 역할 분리로 해결하는 모습을 설명한다.

```text
Main Agent
├── Architecture Agent
├── Performance Agent
└── Test Agent
```

각 Agent는 자기 역할에 필요한 Context를 사용한다. 핵심은 Agent 수를 늘리는
것이 아니라 Context explosion과 역할 복잡도라는 문제를 줄이는 데 있다.
각 역할이 무엇을 조사하고 Main Agent가 결과를 어떻게 결합하는지는 데모
설계 시 구체화한다(TODO).

### 5.6 Memory: 세션 사이에 재사용할 사실을 기억하기

작업 중 중요한 사실이 계속 발견될 수 있다.

- “이 테스트는 flaky하다.”
- “이 모듈은 legacy라 변경하면 안 된다.”
- “benchmark는 release build에서 해야 한다.”
- “이 dependency는 제거 예정이다.”

새 작업이나 새 세션에서 같은 사실을 다시 조사하면 다음 문제가 생긴다.

> 왜 AI가 매번 같은 것을 다시 배우고 있지?

여기서 Memory를 소개하며 다음 구분을 전달한다.

- **Context:** “What does the agent need NOW?”
- **Memory:** “What should the system remember?”

Memory 역시 많이 저장하는 것이 목적이 아니다. 유효성, 최신성, 재사용성을
고려하고, 오래되거나 다시 쓸 수 없는 사실을 무조건 누적하지 않는다.
Memory의 실제 제품 구현과 지속성 범위는 교육 당시 공식 자료로 확인한다.

### 5.7 Harness 전체 구조: 모델과 시스템을 구분하기

앞의 문제 해결 단계를 거친 뒤 AI 개발 환경은 대략 다음 구성으로 확장된다.

```text
Developer
→ Main Agent
   ├── Context
   ├── Skills
   ├── Memory
   ├── Subagents
   └── Tools
        ├── Build
        ├── Test
        └── Benchmark
```

여기에서 전달할 핵심 Insight는 다음과 같다.

> 좋은 AI 모델을 사용하는 것과 좋은 AI 개발 시스템을 만드는 것은 다른
> 문제다.

이 구조는 출발점이 아니라 앞 단계들의 문제가 하나씩 해결된 뒤 도달하는
중간 결과로 제시한다.

### 5.8 Harness가 낡는 문제: 시스템에도 유지보수가 필요하다

Harness를 구축해도 프로젝트는 계속 변한다.

- CMake에서 Bazel로 빌드 시스템이 바뀐다.
- test command가 바뀐다.
- directory 구조가 바뀐다.
- coding convention이 바뀐다.
- benchmark 방법이 바뀐다.

그 결과 AGENTS.md에는 옛날 정보가 남고, Skill은 옛 command를 실행하며,
Memory는 더 오래된 정보를 담을 수 있다. Harness 자체가 Technical Debt가
되는 상황을 보여준다.

이 문제를 다음 문장으로 제시한다.

> AI를 위한 시스템도 유지보수가 필요하다.

이 지점에서 Loop Engineering으로 넘어간다.

### 5.9 Stage 4 — Loop Engineering: 실패를 다음 작업의 개선으로 바꾸기

AI가 제품 코드만 개선하는 데서 나아가 AI가 일하는 환경 자체를 관찰하고
개선하는 구조를 설명한다.

기본 Loop는 다음과 같다.

`Task → Execute → Verify → Observe → What failed? → Learn → Improve → Next Task`

개선 대상은 제품 코드와 Harness 둘 다일 수 있다.

- Product Code
- Harness

#### 반복 실패 사례

Codex가 test를 여러 번 잘못된 directory에서 실행한다고 가정한다.

일반적인 대응은 매번 개발자가 “거기서 실행하지 마.”라고 다시 알려주는
것이다. Loop Engineering에서는 실패를 다음처럼 처리한다.

`Failure → 원인 분석 → 반복 가능성 판단 → Harness 개선 → Skill/Instruction
업데이트 → 다음 작업에서 적용`

개발자가 같은 지시를 매번 반복하는 데서 끝내지 않고, 반복되는 실패를
다음 작업의 Context 또는 Harness 개선으로 전환한다.

#### 구조적 변화

```text
Developer → AI → Task
```

에서 다음과 같은 학습 피드백을 가진 구조로 발전한다.

```text
Developer → AI → Task
             ↑     |
             └ Learn
```

#### 고정 Insight

> 반복되는 실패를 다음 작업의 Context/Harness 개선으로 전환한다.

### 5.10 AI-Native Development: 처음과 끝을 연결하기

교육 마지막에는 출발점과 도달점을 비교한다.

처음:

```text
Developer
→ “이 코드 고쳐줘.”
→ ChatGPT
```

마지막:

```text
Developer
→ Agent
   ├── Context
   ├── Skills
   ├── Memory
   ├── Subagents
   └── Tools
        ↓
      Execute
        ↓
      Verify
        ↓
      Observe
        ↓
      Learn
        ↓
   Harness Improvement
        ↓
     Next Task
```

교육생이 “6시간 동안 완성형 시스템을 설명 들은 것이 아니라, 문제를 하나씩
해결하다 보니 이 구조까지 도달했다”고 느끼도록 해야 한다. 전체 여정은
처음부터 완성 구조를 보여주는 대신, 각 전환의 원인과 필요를 따라가야 한다.

## 6. 공통 개발 업무 Workflow와 검증 기준

### 6.1 기본 개발 Workflow

실제 개발 업무에 적용할 공통 Baseline으로 다음 흐름을 전달한다.

`Investigate → Plan → Implement → Verify → Review`

“바로 고쳐줘”라고 요청하기보다 먼저 조사하게 하는 습관을 강조한다.

### 6.2 완료 판단

AI가 “수정했습니다”라고 말한 것은 작업 완료의 증거가 아니다. 생성된 변경은
필요한 검증을 거쳐야 한다.

`Generated → Build → Test → (필요 시 Benchmark) → Review → Done`

Benchmark는 모든 작업에 무조건 요구하지 않고 필요할 때 수행한다. 실제
검증 명령과 프로젝트별 완료 조건은 후속 데모 또는 콘텐츠에서 해당
repository를 확인해 정한다(TODO).

### 6.3 고정 Insight

> AI 시대에는 코드를 생성하는 능력만큼 결과를 검증하는 능력이 중요하다.

## 7. 교육 전체에서 반복할 핵심 메시지

아래 메시지는 여러 단계와 자료에서 일관되게 유지한다. 표현을 더 짧게
만들더라도 핵심 주장을 바꾸거나 서로 다른 주장을 하나로 합치지 않는다.

1. “AI에게 질문만 하지 말고 문제 해결 과정을 맡겨라.”
2. “좋은 Prompt보다 충분하고 적절한 Context가 중요하다.”
3. “Context를 사람이 전부 수집해서 AI에게 가져오지 말고, AI가 필요한
   Context를 찾게 하라.”
4. “바로 구현시키지 말고 먼저 조사하게 하라.”
5. “Investigate → Plan → Implement → Verify → Review를 기본 개발 Loop로
   활용하라.”
6. “AI의 ‘완료했습니다’는 검증 결과가 아니다.”
7. “AI가 잘 일할 수 있도록 Repository와 개발 환경도 설계하라.”
8. “AI를 사용하는 방법에서 AI에게 일을 맡기는 방법으로 발전해야 한다.”
9. “좋은 AI 모델을 쓰는 것과 좋은 AI 개발 시스템을 만드는 것은 다른
   문제다.”
10. “반복되는 실패를 Harness 개선으로 연결하라.”

## 8. 강의, 사례, 시연 설계 기준

### 8.1 전달 수단

후속 교육 자료는 강의, 실제 사례, Before/After 비교, Codex 화면 시연,
Live Demo를 활용한다. 교육생 직접 실습이나 노트북 사용을 전제로 한
활동은 넣지 않는다.

### 8.2 시연의 서사상 역할

- Stage 0에서는 사람이 코드를 복사해 ChatGPT로 가져가는 흐름과 Codex가
  repository를 조사하는 흐름을 비교한다.
- Prompt 단계에서는 Goal, Context, Constraints, Process, Verification이
  없는 짧은 요청과 구체화된 요청의 차이를 보여준다.
- Context 단계에서는 거대한 단일 AGENTS.md와 핵심 규칙 및 별도 참조로
  구성한 방식을 비교한다.
- Harness 단계에서는 지식만 제공한 경우와 작업 절차를 제공한 경우의
  차이를 드러낸다.
- Subagent 단계에서는 한 역할에 모든 조사와 Context를 몰아주는 문제와
  역할별 분리 방식을 대비한다.
- Memory 단계에서는 재사용할 사실을 다시 조사하는 비용과 유효한 기억을
  재사용하는 의도를 비교한다.
- Loop 단계에서는 반복해서 잘못 실행한 test를 매번 구두로 교정하는 것과
  원인을 분석해 Harness를 고치는 흐름을 비교한다.

위 시연은 기획 의도다. 실제 repository, 코드 샘플, 화면, 제품 기능, 데모
순서와 실패 복구 계획은 아직 정해지지 않았으므로 TODO로 둔다.

### 8.3 기능 설명의 위치

기능은 서사를 위해 필요한 경우에만 소개한다. Skills, Subagents, Memory,
AGENTS.md 및 Codex의 화면·도구 동작은 문제와 개선을 보여주는 데 필요한
수준으로 다룬다. 기능을 빠짐없이 나열하는 것을 목표로 삼지 않는다.

## 9. 후속 산출물에 적용할 보존 기준

앞으로 만드는 curriculum, storyline, demo, slides, speaker notes와 PPT는
다음 기준을 지킨다.

- 6시간 순수 교육이라는 시간 범위를 유지한다.
- 노트북 없는 강의이며 교육생 직접 실습이 없다는 조건을 유지한다.
- 조직 전체의 AI 사용 역량 균질화를 최우선 목표로 둔다.
- 하나의 공통 진화 Story를 사용하고, 초급·고급 별도 코스로 나누지 않는다.
- 개념을 먼저 정의해 나열하지 않고, 문제를 해결하는 순서로 등장시킨다.
- 각 단계가 처음에는 작동한 뒤 규모가 커지며 문제를 낳고, 다음 개선으로
  이어지는 인과관계를 보존한다.
- Context, Verification, Investigate → Plan → Implement → Verify → Review,
  AGENTS.md, Skills, Subagents, Memory, Harness와 Loop의 역할을 흐리지 않는다.
- AI가 완료했다고 말하는 것과 검증이 끝난 것을 동일시하지 않는다.
- 제품 기능에 관한 현재 사실은 공식 자료 확인 전까지 확정해서 쓰지 않는다.
- 별도 지시 전 최종 PPT를 제작하지 않는다.
- 원문에 없는 세부 결정은 TODO 또는 미확정으로 표시한다.

## 10. 미확정 사항 및 TODO

다음 항목은 제공된 기획 원문에서 확정되지 않았다. 후속 결정이 있기 전까지
사실처럼 기술하거나 임의 배정하지 않는다.

1. **원문 누락 확인:** 제공된 텍스트가 17절의 초급자 설명 중간에서
   끝난다. 남은 난이도 설계와 추가 요구사항이 있는지 확인한다.
2. **6시간 편성:** 총 360분의 모듈별 분배, 휴식 배치와 길이를 정한다.
3. **실제 사례:** 사용할 실제 사례, 코드베이스, 공개/가상 repository를
   정한다. 사례 사용 허가와 민감 정보 처리도 확인한다.
4. **Live Demo 환경:** 사용할 Codex 환경, 계정·권한 조건, 화면 흐름,
   네트워크 의존성 및 장애 시 대체 화면을 정한다.
5. **단계별 산출물:** 각 Story 단계의 세션 제목, 세부 학습 포인트,
   예상 시간과 전환 문구를 설계한다.
6. **현재 제품 기능 검증:** 교육 시점에 사용할 ChatGPT/Codex의 기능과
   UI를 공식 자료로 확인한다.
7. **연구 근거:** Lost in the Middle 등 설명에 사용할 일차 자료와 적용
   한계를 확인한다.
8. **숙련도 교차표:** Level 1–4 학습자가 자기 다음 단계를 찾게 하는
   구체적 안내를 보완한다.
9. **검증 예시:** build, test, benchmark, review 예시를 보여줄 실제
   프로젝트의 명령과 완료 기준을 정한다.
10. **PPT 제작:** 최종 PPT는 별도 지시가 있을 때 진행한다.
