## 2. 교육생 특성 및 난이도 설계

### 2.1 교육생 분포

교육생은 모두 개발자지만 AI 활용 경험과 숙련도는 크게 다르다. 대표적인
수준은 다음과 같다.

| 수준 | 관찰되는 활용 방식 |
| --- | --- |
| Level 0 | AI를 거의 사용하지 않는다. |
| Level 1 | ChatGPT를 검색·질문용 챗봇처럼 사용한다. 에러 메시지를 붙여넣고 해결책을 묻는 정도다. |
| Level 2 | 코드를 붙여넣고 설명, 수정, 리팩터링 등을 요청한다. |
| Level 3 | Codex 등 Agent를 사용해 repository를 탐색하고 실제 개발 작업을 수행한다. |
| Level 4 | AGENTS.md, Context Engineering, Skills, Subagents, Memory, Harness 등을 구성해 사용한다. |

일부 개발자는 이미 높은 AI 활용 역량을 갖추고 있다. 한편 상당수는 현장
출장이 많아 AI 활용을 깊게 공부할 시간이 부족하고, ChatGPT를 단순 챗봇
수준으로 사용하는 비중이 높다.

### 2.2 한 교육 안에서의 난이도 원칙

- 교육생을 초급반과 고급반으로 나누지 않는다.
- 하나의 공통 Story를 따라가되, 각 수준의 개발자가 자기 현재 위치와
  다음 단계를 발견할 수 있도록 설계한다.
- 초급자만을 위해 내용을 단순화하여 고급자의 인사이트를 없애지 않는다.
- 고급 사용자만 이해할 수 있는 전제와 용어로 교육을 구성하지 않는다.
- 완성된 고급 시스템을 처음부터 제시하고 설명하지 않는다. 필요가 생기는
  순서대로 개념을 도입한다.

### 2.3 난이도별 다음 단계

교육생 수준을 바탕으로 각자가 다음 단계로 이동하도록 돕는다. 아래 문구는
교육생이 자신의 현재 위치에 따라 가져갈 수 있는 의도된 Insight다.

**초급자**

- “ChatGPT에 코드만 붙여넣지 말고 Codex로 repository를 보게 해야겠다.”
- “바로 고쳐달라고 하기보다 먼저 조사하게 해야겠다.”
- “AGENTS.md를 사용하면 반복적인 설명을 줄일 수 있겠다.”

**중급자**

- “AGENTS.md에 모든 것을 넣는 것이 정답은 아니구나.”
- “Context를 필요한 시점에 필요한 만큼 제공해야겠다.”
- “반복 작업을 Skill로 분리할 수 있겠다.”

**숙련자**

- “Context explosion을 Subagent와 역할 분리로 관리할 수 있겠다.”
- “Context와 Memory의 역할을 구분해야겠다.”
- “프로젝트에 맞는 Harness를 설계할 수 있겠다.”

**고급 사용자**

- “Harness 자체의 실패와 노후화를 관찰해야겠다.”
- “반복되는 실패를 Harness 개선으로 연결할 수 있겠다.”
- “실행 → 관찰 → 학습 → 개선의 Loop를 구축할 수 있겠다.”

이 내용은 초급/중급/고급의 별도 교육 과정이 아니다. 모든 교육생이 같은
Story를 따라가면서 자기 현재 수준 바로 다음 단계에서 가져갈 Insight를
발견하도록 한다.

필요하면 자료에 다음 난이도 표시를 사용할 수 있다.

- **BASIC:** 모든 개발자가 이해해야 하는 내용.
- **PRACTICAL:** 실무 적용을 적극 권장하는 내용.
- **ADVANCED:** 숙련 개발자가 추가로 가져갈 수 있는 내용.

난이도 표시는 교육의 하나의 Storyline을 분절해서는 안 된다.

## 3. 교육의 최우선 목표와 완료 시 역량

### 3.1 최우선 목표

교육의 최우선 목표는 **개발자 조직 전체의 AI 사용 역량 균질화**다.

이 교육은 AI 전문가를 양성하는 과정이 아니다. 조직 안에서 AI 활용 경험이
서로 다른 개발자들이 공통된 기본 관점과 업무 흐름을 공유하도록 돕는다.

### 3.2 교육 후 모든 개발자가 갖춰야 하는 최소 이해

교육이 끝났을 때 모든 개발자는 최소한 다음을 이해해야 한다.

1. ChatGPT와 Codex의 역할 차이를 설명할 수 있다.
2. 단순 질의응답에서 벗어나 AI에게 개발 업무의 문제 해결 과정을 맡기는
   사고방식을 이해한다.
3. Codex가 repository 안에서 필요한 정보를 직접 조사하도록 할 수 있다는
   점을 이해한다.
4. AI 개발에서 Context와 Verification이 중요한 이유를 이해한다.
5. `Investigate → Plan → Implement → Verify → Review` 흐름을 이해한다.
6. AGENTS.md를 비롯한 프로젝트 Context가 어떤 역할을 하는지 이해한다.
7. 자기 현재 활용 수준에서 시도할 다음 단계가 무엇인지 알 수 있다.

### 3.3 숙련 개발자에게 제공할 추가 인사이트

이미 AI를 능숙하게 사용하는 개발자도 다음 주제에서 새로운 관점을 얻어야
한다.

- Context Engineering: 필요한 정보를 적절한 시점에 찾고 제공하는 설계
- Harness Engineering: AI가 일하는 방법과 환경을 설계하는 관점
- Loop Engineering: 목표·완료 기준을 고정하고 구현·검토·수정을 반복해
  같은 기준의 근거로 목표 충족과 다음 행동을 판단하는 시스템 설계

## 4. 교육 전체의 핵심 Story

### 4.1 진화 과정

교육의 서사는 다음 진화 과정을 따라간다.

`Chatbot → Prompt Engineering → Context Engineering → Harness Engineering
→ Loop Engineering → AI-Native Development`

이 용어들을 첫 장에서 정의하고 사전식으로 설명하지 않는다. 각 개념은 앞
단계에서 드러난 문제를 해결하려는 자연스러운 시도로 등장해야 한다.

### 4.2 반복되는 Engineering Loop

모든 주요 전환은 다음 패턴으로 이야기를 전개한다.

1. Codex를 처음 쓰는 개발자가 자연스럽게 선택할 만한 방법을 시도한다.
2. 그 방법은 처음에는 실제로 잘 동작한다.
3. 사용 범위가 커지면서 문제가 나타난다.
4. 왜 문제가 생겼는지 분석한다.
5. 문제를 해결하기 위한 다음 Engineering 단계가 등장한다.
6. 개선된 방식으로 다시 작업한다.
7. 규모나 상황이 바뀌면서 새로운 문제가 나타난다.
8. 다시 개선한다.

이를 `Attempt → Works → Problem → Why → Improvement → New Problem →
Improvement`라는 스토리 구조로 반복한다. 개선의 필요성이 장면에서 먼저
보이고, 개념 이름은 그 다음에 소개한다.

## 5. 단계별 서사와 개념 도입 순서

### 5.1 Stage 0 — Chatbot Developer: AI를 코드로 데려가기

#### 출발점

가장 일반적인 개발자는 ChatGPT에 다음과 같이 요청한다.

- “이 에러 뭐야?”
- “이 코드 설명해줘.”
- “이 함수 리팩터링해줘.”

기존 작업은 다음과 같다.

`Developer → 필요한 코드/에러를 직접 수집 → ChatGPT에 복사 → 답변 → IDE에 복사`

#### 시연과 전환

이 흐름에서 Codex를 소개한다. 개발자가 코드를 일일이 AI에게 가져가는 대신,
AI를 repository로 데려온다. Codex가 repository 안에서
`search → read → trace → answer`하는 모습을 보여준다.

#### 고정 Insight

> 코드를 AI에게 가져가지 말고 AI를 코드로 데려가라.

Codex의 실제 화면, 명령, 제품별 지원 범위는 시연을 준비할 때 최신 공식
자료와 현재 사용 환경을 확인한다.

### 5.2 Stage 1 — Prompt Engineering: 요청을 구조화하기

#### 자연스러운 첫 시도

개발자는 Codex에게 바로 다음과 같은 짧은 요청을 할 수 있다.

> filter 모듈의 성능을 개선해줘.

결과가 기대에 미치지 못하면 Prompt에 작업의 중요한 조건을 더 명확히
포함하는 방향으로 발전한다.

#### 전달할 요청 요소

- **Goal:** filter 처리 시간 감소
- **Context:** 작업 대상과 현재 문제를 이해하는 데 필요한 정보
- **Constraints:**
  - public API를 변경하지 않는다.
  - 결과 정확도를 유지한다.
  - 새로운 dependency를 추가하지 않는다.
- **Process:**
  1. 관련 코드를 조사한다.
  2. 병목 후보를 분석한다.
  3. 변경 계획을 작성한다.
  4. 승인된 범위만 수정한다.
- **Verification:** unit test와 benchmark로 결과를 확인한다.

이 단계에서는 Prompt를 구체화하면 작업 결과와 범위가 나아질 수 있음을
보여준다. 다만 Prompt Engineering을 교육의 종착점처럼 다루지 않는다.

#### 다음 문제가 생기는 지점

작업을 거듭하면 개발자는 다음 내용을 매번 되풀이한다.

- build를 어떻게 하는지
- test를 어떻게 하는지
- API를 바꾸면 안 된다는 점
- 프로젝트의 style
- benchmark 방법

이때 자연스럽게 다음 질문을 제기한다.

> 왜 매번 같은 것을 설명하고 있지?

이 반복 문제에서 Context Engineering으로 넘어간다.

### 5.3 Stage 2 — Context Engineering: 반복 지시를 프로젝트에 두기

#### AGENTS.md를 처음 도입

반복되는 공통 지시를 repository에 저장하기 위해 AGENTS.md를 도입한다.
초기에는 프로젝트의 공통 정보를 한곳에 정리함으로써 잘 동작하는 경험을
보여준다.

초기 AGENTS.md에 담길 수 있는 항목은 다음과 같다.

- Project
- Architecture
- Build
- Test
- Coding Rules
- Performance Rules
- Git Rules
- Review Rules

#### 모든 내용을 한 파일에 넣을 때의 문제

처음에는 다음과 같은 생각을 자연스럽게 유도한다.

> AGENTS.md에 모든 걸 넣으면 되는 것 아닌가?

이 접근으로 파일이 `100 lines → 300 → 700 → 1500...`처럼 계속 커지는
상황을 보여준다. 이 숫자는 교육에서 파일 비대화의 진행을 설명하기 위한
예시이지, 보편적인 기준선이나 제품 제한으로 주장하지 않는다.

파일이 커지고 프로젝트가 변하면서 다음 문제가 발생한다.

- 중요한 규칙이 누락될 수 있다.
- 현재 작업과 관련 없는 Context까지 항상 포함될 수 있다.
- 오래된 규칙과 새로운 규칙이 충돌할 수 있다.
- Context와 Token 사용량이 불필요하게 늘 수 있다.
- 지시의 우선순위가 불명확해질 수 있다.
- 긴 Context에서 중간 정보가 어떻게 활용되는지 문제가 제기될 수 있다.

`Lost in the Middle` 등의 개념은 이 지점에서 소개한다. 근거를 확인하고
과장하지 않으며, 해당 근거가 말하는 범위와 한계를 구분한다.

#### 개선: 필요한 정보가 필요한 순간에 들어오게 하기

핵심 Insight는 다음과 같다.

> Context는 많을수록 좋은 것이 아니다. 필요한 순간에 필요한 Context가
> 들어가는 것이 중요하다.

따라서 하나의 거대한 AGENTS.md를 유지하는 대신 역할을 분리한다.

| Before | After |
| --- | --- |
| 모든 지식을 한 파일에 쌓는 거대한 AGENTS.md | 핵심 원칙과 관련 지식을 찾는 경로를 안내하는 AGENTS.md |
| 모든 세부 지침을 항상 함께 제공 | 세부 정보는 필요에 따라 docs/, rules/, skills/ 등에 둔다 |

AGENTS.md의 역할은 다음과 같이 발전한다.

`모든 지식을 담는 파일 → 필요한 지식을 찾도록 안내하는 Router`

Progressive Disclosure는 정보를 한 번에 전부 싣지 않고 필요한 때 필요한
정보를 드러내는 개념으로 이 흐름에서 설명한다.

### 5.4 Stage 3 — Harness Engineering: 지식에서 작업 환경과 방법으로

#### Context만으로 남는 문제

Context를 정리해 알려줘도 AI가 일하는 방식은 매 작업마다 달라질 수 있다.

- 어떤 경우에는 `search → edit` 순서로 움직인다.
- 다른 경우에는 `edit → test`로 움직인다.
- 어떤 경우에는 test 자체를 수행하지 않는다.

이 문제를 다음 문장으로 드러낸다.

> Context는 알려줬는데, 일하는 방식 자체가 안정적이지 않다.

#### Harness의 전환

이 시점에 Harness Engineering을 도입한다.

`AI에게 지식을 제공 → AI가 일하는 방법과 환경을 설계`

Skills는 필요한 작업에 필요한 절차와 지침을 선택적으로 제공하는 예로
소개한다. 반복 Workflow를 매번 설명하거나 불안정하게 수행하는 문제를
해결하고, 필요한 절차를 반복해서 사용할 수 있게 한다. 예시 구조는 다음과
같다.

```text
skills/
├── build/
├── test/
├── benchmark/
└── code-review/
```

모든 절차를 상시 Context에 넣지 않고 작업에 맞는 Skill과 지침을 선택한다.

`Task → 필요한 Skill → 필요한 Instruction Load → Execute`

#### 고정 Insight

> AI에게 지식을 주는 것을 넘어 일을 수행하는 방법을 제공한다.

`Skills`라는 제품 또는 프로젝트별 기능의 현재 구체적 동작·설정 방법은
해당 시점의 공식 자료와 실제 교육 환경에서 확인한다. 이 명세는 필요한
업무 절차를 선택적으로 불러오는 설계 의도를 고정한다.

### 5.5 Subagent: 역할과 Context 복잡도를 분리하기

Subagent를 고급 기능 자랑으로 소개하지 않는다. 하나의 Agent가 큰 작업에서
Architecture, Performance, Tests, Documentation을 모두 조사하면 Context가
다시 커지고 역할도 복잡해지는 문제를 먼저 보여준다.

그 문제를 역할 분리로 해결하는 모습을 설명한다.

```text
Main Agent
├── Architecture Agent
├── Performance Agent
└── Test Agent
```

각 Agent는 자기 역할에 필요한 Context를 사용한다. 핵심은 Agent 수를 늘리는
것이 아니라 Context explosion과 역할 복잡도라는 문제를 줄이는 데 있다.
각 역할이 무엇을 조사하고 Main Agent가 결과를 어떻게 결합하는지는 데모
설계 시 구체화한다(TODO).

### 5.6 Memory: 세션 사이에 재사용할 사실을 기억하기

작업 중 중요한 사실이 계속 발견될 수 있다.

- “이 테스트는 flaky하다.”
- “이 모듈은 legacy라 변경하면 안 된다.”
- “benchmark는 release build에서 해야 한다.”
- “이 dependency는 제거 예정이다.”

새 작업이나 새 세션에서 같은 사실을 다시 조사하면 다음 문제가 생긴다.

> 왜 AI가 매번 같은 것을 다시 배우고 있지?

여기서 Memory를 소개하며 다음 구분을 전달한다.

- **Context:** “What does the agent need NOW?”
- **Memory:** “What should the system remember?”

Memory 역시 많이 저장하는 것이 목적이 아니다. 유효성, 최신성, 재사용성을
고려하고, 오래되거나 다시 쓸 수 없는 사실을 무조건 누적하지 않는다.
Memory의 실제 제품 구현과 지속성 범위는 교육 당시 공식 자료로 확인한다.

### 5.7 Harness 전체 구조: 모델과 시스템을 구분하기

앞의 문제 해결 단계를 거친 뒤 AI 개발 환경은 대략 다음 구성으로 확장된다.

```text
Developer
→ Main Agent
   ├── Context
   ├── Skills
   ├── Memory
   ├── Subagents
   └── Tools
        ├── Build
        ├── Test
        └── Benchmark
```

여기에서 전달할 핵심 Insight는 다음과 같다.

> 좋은 AI 모델을 사용하는 것과 좋은 AI 개발 시스템을 만드는 것은 다른
> 문제다.

이 구조는 출발점이 아니라 앞 단계들의 문제가 하나씩 해결된 뒤 도달하는
중간 결과로 제시한다.

### 5.8 Harness가 낡는 문제: 시스템에도 유지보수가 필요하다

Harness를 구축해도 프로젝트는 계속 변한다.

- CMake에서 Bazel로 빌드 시스템이 바뀐다.
- test command가 바뀐다.
- directory 구조가 바뀐다.
- coding convention이 바뀐다.
- benchmark 방법이 바뀐다.

그 결과 AGENTS.md에는 옛날 정보가 남고, Skill은 옛 command를 실행하며,
Memory는 더 오래된 정보를 담을 수 있다. Harness 자체가 Technical Debt가
되는 상황을 보여준다.

이 문제를 다음 문장으로 제시한다.

> AI를 위한 시스템도 유지보수가 필요하다.

이 지점에서 Loop Engineering으로 넘어간다.

### 5.9 Stage 4 — Loop Engineering: 목표 달성까지 구현·검토·수정하기

ACT3에서 재사용할 방법·도구·환경을 구성한 뒤, 같은 목표의 다음 검토·수정을
사람이 매번 연결하는 문제를 드러낸다. 목표와 완료 기준을 고정하고, 구현 모델과
다른 검토 모델이 변경·검사 근거를 주고받으며 남은 문제를 다음 수정에 반영한다.

`Goal / Completion Criteria → Implement → Verify / Review → Revise → Re-verify / Review`

미충족이면 근거·남은 문제와 함께 다음 수정으로 돌아간다. 충족하면 확인한 범위를
보고하고 완료하며, 막힘·회귀·정체·한도 도달이면 미완료 상태를 보존해 사람에게
판단을 요청한다. 반복 횟수나 모델의 동의만으로 완료하지 않는다.

모델 A 구현과 모델 B 검토의 역할을 구분하고 ReConcile/CriticBench의 제한된
결과를 연결한다. 현재 모델·개발 작업의 일반적 우월성이나 이번 다중 모델 루프의
실측 효과는 주장하지 않는다. CASE-LOOP-01은 교육용 설계이며 실제 Trial이 아니다.

이전 Harness 개선 중심 기획과 실제 평가·보고 Meta 기록은 이력·보조 근거로
보존한다. 다음 작업의 지침 개선은 관련된 별도 범위이며 ACT4의 주 사례는
이번 목표를 완료하는 수정·검토 루프다. DEC-0096/0097의 사용자 승인으로 변경했다.

### 5.10 AI-Native Development: 처음과 끝을 연결하기

교육 마지막에는 출발점과 도달점을 비교한다.

처음:

```text
Developer
→ “이 코드 고쳐줘.”
→ ChatGPT
```

마지막:

```text
Developer
→ Agent
   ├── Context
   ├── Skills
   ├── Memory
   ├── Subagents
   └── Tools
        ↓
      Execute
        ↓
      Verify
        ↓
      Observe
        ↓
      Learn
        ↓
   Harness Improvement
        ↓
     Next Task
```

교육생이 “6시간 동안 완성형 시스템을 설명 들은 것이 아니라, 문제를 하나씩
해결하다 보니 이 구조까지 도달했다”고 느끼도록 해야 한다. 전체 여정은
처음부터 완성 구조를 보여주는 대신, 각 전환의 원인과 필요를 따라가야 한다.

## 6. 공통 개발 업무 Workflow와 검증 기준

### 6.1 기본 개발 Workflow

실제 개발 업무에 적용할 공통 Baseline으로 다음 흐름을 전달한다.

`Investigate → Plan → Implement → Verify → Review`

“바로 고쳐줘”라고 요청하기보다 먼저 조사하게 하는 습관을 강조한다.

이 Workflow는 Prompt → Context → Harness → Loop와 경쟁하는 별도의 Story가
아니다. 개발 업무를 AI에게 맡길 때 사용하는 실용적인 기본 실행 Pattern이다.

교육 초기에는 사람이 Prompt 안에서 조사, 계획, 구현, 검증, 리뷰를 요청할
수 있다. 필요한 경우 계획 뒤에 다음과 같은 사람 확인 단계를 둔다.

`Investigate → Plan → Human Check → Implement → Verify → Review`

Harness가 발전하면 Workflow의 일부를 Skill이나 Workflow로 구조화할 수 있다.
Loop Engineering에서는 이 Workflow에서 반복적으로 발생하는 실패를 관찰해
Harness 자체를 개선한다.

두 흐름의 관계를 분명히 구분한다.

| 관점 | 흐름 | 답하는 질문 |
| --- | --- | --- |
| Engineering Maturity | Prompt → Context → Harness → Loop | AI 개발 시스템이 어떤 문제를 해결하며 발전하는가? |
| Task Execution | Investigate → Plan → Implement → Verify → Review | 하나의 개발 작업을 어떤 순서로 수행하는가? |

### 6.2 완료 판단

`Generated ≠ Done`. AI가 “수정했습니다”라고 말한 것은 작업 완료의 증거가
아니다. 생성된 변경은 필요한 검증을 거쳐야 한다.

`Generated → Build → Test → (필요 시 Benchmark) → Review → Done`

Benchmark는 모든 작업에 무조건 요구하지 않고 필요할 때 수행한다. 실제
검증 명령과 프로젝트별 완료 조건은 후속 데모 또는 콘텐츠에서 해당
repository를 확인해 정한다(TODO).

### 6.3 Verification Demo 원칙

가능하면 Demo에서 Agent가 build, test, 필요 시 benchmark를 직접 실행하고,
그 결과를 근거로 판단하는 모습을 보여준다. “수정했습니다”, “문제를
해결했습니다”, “테스트를 통과할 것입니다”라는 Agent의 말과 실제 검증
결과를 구분한다.

### 6.4 고정 Insight

> AI 시대에는 코드를 생성하는 능력만큼 결과를 검증하는 능력이 중요하다.

## 7. 교육 전체에서 반복할 핵심 메시지

아래 메시지는 여러 단계와 자료에서 일관되게 유지한다. 표현을 더 짧게
만들더라도 핵심 주장을 바꾸거나 서로 다른 주장을 하나로 합치지 않는다.

1. “AI에게 질문만 하지 말고 문제 해결 과정을 맡겨라.”
2. “좋은 Prompt보다 충분하고 적절한 Context가 중요하다.”
3. “Context를 사람이 전부 수집해서 AI에게 가져오지 말고, AI가 필요한
   Context를 찾게 하라.”
4. “바로 구현시키지 말고 먼저 조사하게 하라.”
5. “Investigate → Plan → Implement → Verify → Review를 기본 개발 Loop로
   활용하라.”
6. “AI의 ‘완료했습니다’는 검증 결과가 아니다.”
7. “AI가 잘 일할 수 있도록 Repository와 개발 환경도 설계하라.”
8. “AI를 사용하는 방법에서 AI에게 일을 맡기는 방법으로 발전해야 한다.”
9. “좋은 AI 모델을 쓰는 것과 좋은 AI 개발 시스템을 만드는 것은 다른
   문제다.”
10. “반복되는 실패를 Harness 개선으로 연결하라.”

## 8. 강의, 사례, 시연 설계 기준

### 8.1 전달 수단

후속 교육 자료는 강의, 실제 사례, Before/After 비교, Codex 화면 시연,
Live Demo를 활용한다. 교육생 직접 실습이나 노트북 사용을 전제로 한
활동은 넣지 않는다.

교육생은 노트북을 사용하지 않으므로 다음 직접 실습은 포함하지 않는다.

- 교육생 각자가 repository를 연다.
- 교육생 각자가 Prompt를 작성한다.
- 교육생 각자가 Codex를 실행한다.
- 개인별 과제를 수행한다.
- 실습 결과를 발표한다.

대신 강사가 실제 ChatGPT/Codex를 사용하는 Demo와 사례를 보여준다. 교육생이
직접 따라 하지 않더라도 “내가 하던 방식보다 이렇게 하는 것이 낫겠구나”라는
생각과 Insight를 얻는 것이 중요하다.

기본 전달 패턴은 다음과 같다.

`Problem → 흔히 하는 방법 → 결과 → 문제 발견 → Why → 개선된 방법 → 실제
Demo → 결과 비교 → Insight`

가능한 경우 Before/After의 차이를 화면에서 확인할 수 있도록 한다.

### 8.2 시연의 서사상 역할

- Stage 0에서는 사람이 코드를 복사해 ChatGPT로 가져가는 흐름과 Codex가
  repository를 조사하는 흐름을 비교한다.
- Prompt 단계에서는 Goal, Context, Constraints, Process, Verification이
  없는 짧은 요청과 구체화된 요청의 차이를 보여준다.
- Context 단계에서는 거대한 단일 AGENTS.md와 핵심 규칙 및 별도 참조로
  구성한 방식을 비교한다.
- Harness 단계에서는 지식만 제공한 경우와 작업 절차를 제공한 경우의
  차이를 드러낸다.
- Subagent 단계에서는 한 역할에 모든 조사와 Context를 몰아주는 문제와
  역할별 분리 방식을 대비한다.
- Memory 단계에서는 재사용할 사실을 다시 조사하는 비용과 유효한 기억을
  재사용하는 의도를 비교한다.
- Loop 단계에서는 반복해서 잘못 실행한 test를 매번 구두로 교정하는 것과
  원인을 분석해 Harness를 고치는 흐름을 비교한다.

위 시연은 기획 의도다. 실제 repository, 코드 샘플, 화면, 제품 기능, 데모
순서와 실패 복구 계획은 아직 정해지지 않았으므로 TODO로 둔다.

각 Demo는 반드시 Story에서 발생한 질문에 답해야 한다. Demo의 목적은 Codex
기능 자랑이 아니다. 현재 계획된 질문과 Demo의 대응은 다음과 같다.

| Story에서 발생하는 질문 | Demo |
| --- | --- |
| 관련 코드를 사람이 찾아야 하나? | Repository investigation |
| 매번 같은 지시를 해야 하나? | AGENTS.md |
| AGENTS.md에 다 넣으면 되나? | Context overload 비교 |
| 반복 작업을 매번 설명해야 하나? | Skill |
| 한 Agent가 모든 걸 해야 하나? | Subagent |
| 지난번에 배운 걸 또 조사해야 하나? | Memory |
| Agent가 같은 실수를 반복하면? | Loop / Harness improvement |

### 8.3 Demo별 필수 설계 항목

각 Demo에는 최소한 다음 항목을 기록한다.

1. Demo가 답하려는 질문
2. 시작 상태
3. 사용 Prompt
4. 예상되는 Agent 행동
5. 관찰할 화면
6. 성공 조건
7. 실패할 경우의 fallback
8. Demo 이후 전달할 Insight

Live Demo는 실패 가능성을 고려한다. 교육 흐름상 중요한 Demo에는 사전에
검증된 결과, screenshot, recording 등 대체 수단을 준비할 수 있도록 한다.

### 8.4 기능 설명의 위치

기능은 서사를 위해 필요한 경우에만 소개한다. Skills, Subagents, Memory,
AGENTS.md 및 Codex의 화면·도구 동작은 문제와 개선을 보여주는 데 필요한
수준으로 다룬다. 기능을 빠짐없이 나열하는 것을 목표로 삼지 않는다.

## 9. 후속 산출물에 적용할 보존 기준

앞으로 만드는 curriculum, storyline, demo, slides, speaker notes와 PPT는
다음 기준을 지킨다.

- 6시간 순수 교육이라는 시간 범위를 유지한다.
- 노트북 없는 강의이며 교육생 직접 실습이 없다는 조건을 유지한다.
- 조직 전체의 AI 사용 역량 균질화를 최우선 목표로 둔다.
- 하나의 공통 진화 Story를 사용하고, 초급·고급 별도 코스로 나누지 않는다.
- 개념을 먼저 정의해 나열하지 않고, 문제를 해결하는 순서로 등장시킨다.
- 각 단계가 처음에는 작동한 뒤 규모가 커지며 문제를 낳고, 다음 개선으로
  이어지는 인과관계를 보존한다.
- Context, Verification, Investigate → Plan → Implement → Verify → Review,
  AGENTS.md, Skills, Subagents, Memory, Harness와 Loop의 역할을 흐리지 않는다.
- AI가 완료했다고 말하는 것과 검증이 끝난 것을 동일시하지 않는다.
- 제품 기능에 관한 현재 사실은 공식 자료 확인 전까지 확정해서 쓰지 않는다.
- 별도 지시 전 최종 PPT를 제작하지 않는다.
- 원문에 없는 세부 결정은 TODO 또는 미확정으로 표시한다.
- 각 Chapter가 같은 교육용 repository의 진화 과정에 연결되도록 우선
  설계한다. 각 Chapter를 독립적인 기능 소개로 분리하지 않는다.
- 강사의 Demo, 사례와 Visual Storytelling을 사용하고 교육생 직접 실습은
  넣지 않는다.
- Prompt, Context, Harness, Loop가 서로 대체하는 개념이라고 설명하지 않는다.
- AI가 모든 일을 맡는다고 말하지 않는다. 문제 정의, 목표와 요구사항 판단,
  trade-off, 중요한 architecture, verification 기준, 위험 판단, 최종 review와
  responsibility는 개발자가 계속 책임진다.

## 10. 미확정 사항 및 TODO

다음 항목은 제공된 기획 원문에서 확정되지 않았다. 후속 결정이 있기 전까지
사실처럼 기술하거나 임의 배정하지 않는다.

1. **실제 사례와 단일 교육용 repository:** 동일한 예제로 교육을 관통하는
   것을 우선하되, 사용할 코드베이스와 사례를 정한다. 사례 사용 허가와
   민감 정보 처리도 확인한다.
2. **Live Demo 환경:** 사용할 Codex 환경, 계정·권한 조건, 화면 흐름,
   네트워크 의존성 및 장애 시 대체 화면을 정한다.
3. **단계별 산출물:** 각 Story 단계의 세션 제목, 상세 학습 포인트,
   구체적인 전환 문구를 설계한다.
4. **현재 제품 기능 검증:** 교육 시점에 사용할 ChatGPT/Codex 기능과 UI를
   공식 자료로 확인한다.
5. **연구 근거:** Lost in the Middle 등 설명에 사용할 일차 자료와 적용
   한계를 확인한다.
6. **검증 예시:** build, test, benchmark, review 예시를 보여줄 실제
   프로젝트의 명령과 완료 기준을 정한다.
7. **교육자료 제작 Meta Example의 사용 범위:** 제작 repository의 실제
   문제와 개선을 기록하고 사례로 사용할지 구체화한다. 처음부터 교육용으로
   인위적인 Harness를 만들지 않는다.
8. **PPT 제작:** 최종 PPT는 별도 지시가 있을 때 진행한다.

## 12. 하나의 교육용 프로젝트가 계속 진화해야 한다

각 Chapter에서 완전히 다른 예제를 쓰기보다, 가능하면 하나의 동일한 교육용
software repository를 교육 내내 사용한다. 교육생은 같은 프로젝트가 AI 활용
수준에 따라 진화하는 과정을 본다.

가능한 진화 순서는 다음과 같다.

`단순 코드 질문 → Codex repository 조사 → Prompt 개선 → AGENTS.md 추가
→ AGENTS.md 비대화 → Context 분리 → Skills 추가 → Subagents 추가 → Memory
추가 → Harness 구성 → Harness 실패 관찰 → Loop Engineering 적용`

각 단계의 문제는 가능한 한 바로 앞 단계에서 자연스럽게 발생해야 한다.
다음 기술을 소개하기 위해 억지로 문제를 만들어낸다는 느낌을 피한다.

## 13. Prompt / Context / Harness / Loop의 개념 관계

### 13.1 Prompt Engineering은 계속 필요하다

Prompt Engineering을 낡거나 쓸모없는 기술처럼 설명하지 않는다. Prompt는
계속 필요하다. 교육은 해결 범위가 점진적으로 확장되는 과정을 보여준다.

`좋은 Prompt → 반복되는 Context 발견 → 지속적인 Context 관리 → 실행 환경
설계 → Feedback Loop`

Prompt Engineering, Context Engineering, Harness Engineering, Loop
Engineering은 서로 대체하는 기술이 아니라 더 넓은 문제를 해결하는 단계다.

### 13.2 Context Engineering

Context Engineering을 “많은 문서를 AI에게 넣는 것”으로 설명하지 않는다.
핵심 질문은 다음과 같다.

> What information does the agent need for this task, and when should it receive it?

### 13.3 Harness Engineering

Harness Engineering은 Context보다 한 단계 범위를 넓힌다.

> What environment and process does the agent need to perform the work reliably?

상황에 따라 Harness에는 다음 요소가 포함될 수 있다.

- Instructions
- Context routing
- Skills
- Tools
- Subagents
- Memory
- Verification
- Workflow

이는 절대적인 표준 구성요소 목록이 아니다. 프로젝트 문제를 해결하는 데
필요한 요소가 점진적으로 추가되는 것으로 설명한다.

## 14. Loop Engineering의 범위와 두 종류의 Loop

### 현재 중심 — DEC-0097

이 교육의 Loop Engineering은 목표·완료 기준을 유지하며 구현·검토·수정을
피드백으로 연결하고, 같은 기준의 재검증으로 다음 행동을 판단하는 시스템 설계다.
단순한 무한 반복, 모델 가중치 학습, 특정 제품의 자동 실행 기능명으로 설명하지 않는다.

**목표 기반 작업 수행 루프 — ACT4의 주제**

`목표·완료 기준 → 모델 A 구현 → 테스트·측정 + 다른 모델 B 검토 → 판단`

- 미충족·수정 가능: 남은 지적과 근거를 다음 수정에 전달하고 같은 기준으로 재검토.
- 기준 충족: 완료하고 확인 범위·남은 한계를 보고.
- 근거 부족·정체·회귀·한도 도달: 미완료 상태를 보존하고 사람에게 판단 요청.

검토 모델의 지적도 확인한다. 잘못된 지적은 기각 근거를 남길 수 있다.
검토자와 구현자가 동의했다고 객관적 검사 근거를 대체하지 않는다.

**작업 체계 개선 루프 — 관련 확장**

여러 실행의 반복 문제를 관찰해 지침·Skill·평가 기준 등 재사용 체계를 개선하고
영향을 재평가할 수 있다. 이 범위도 중요하지만 이번 ACT4의 목표 기반 반복을
대신하지 않는다. 두 범위는 실무에서 겹칠 수 있고 Harness와 Loop도 배타적이지 않다.

과거 §14와 DEC-0023/0094는 Harness Improvement Loop에 더 비중을 두었다.
최신 사용자가 수행 루프와 서로 다른 모델의 검토 연구를 중심으로 명확히 지시해
그 우선순위를 변경했다. 과거 결정·실제 근거는 삭제하거나 새 실행으로 해석하지 않는다.
[승인 설계와 원인 분석](ACT4_GOAL_LOOP_REPLAN.md)을 함께 보존한다.

## 15. 개발자의 역할과 책임

교육의 메시지가 “AI에게 모든 것을 맡겨라”가 되어서는 안 된다.

AI에게 적극적으로 맡길 수 있는 일:

- Search와 repository exploration
- Information gathering과 analysis
- Drafting과 code generation
- Repetitive modification
- Build/Test execution
- Initial review와 documentation

개발자가 계속 책임져야 하는 일:

- Goal 설정과 문제 정의
- 요구사항 판단과 trade-off 판단
- 중요한 Architecture 결정
- Verification 기준 정의와 결과 해석
- Risk 판단
- 최종 Review와 Responsibility

강조점은 개발자가 직접 코드를 타이핑하는 비중이 아니라, 문제를 정의하고
AI의 작업을 설계·검증하는 능력의 중요성이 커진다는 데 있다.

## 16. 교육자료 제작 과정을 보조 Meta Example로 활용

가능하면 이 교육자료를 만드는 과정 자체도 Harness / Loop Engineering의
보조 사례로 활용할 수 있다. 다만 이것이 교육의 핵심 Story를 대체해서는
안 된다.

제작 repository는 단순하게 시작한다. 자료 제작 중 실제 문제가 발생하면
필요에 따라 Context 분리, Skill, Review 역할 분리, Subagent, Memory,
Validation, Feedback Loop를 추가할 수 있다.

처음부터 교육에서 보여주기 위해 복잡한 Harness를 인위적으로 만들지 않는다.
실제 제작 과정에서 생긴 문제와 그에 따른 개선만 기록한다. 가능하면 Git
history와 Decision log를 사용해 “처음에는 이렇게 시작했고, 실제로 이런
문제가 생겨서, 이 구조를 추가했다”는 흐름을 나중에 설명할 수 있도록 한다.

## 17. Slide Storytelling 규칙

슬라이드는 기능 설명서처럼 구성하지 않는다. 가능한 한 다음 리듬을
유지한다.

`Situation → Current Approach → Works → Scale / Change → Problem → Why
→ Better Approach → Demo → Result → Insight`

모든 단계에 열 개 항목을 기계적으로 각각 한 장씩 만들 필요는 없다.
하지만 Story의 논리적 흐름은 지킨다. 다음 기술을 소개하기 전에 교육생이
“왜 이것이 필요한가?”를 먼저 생각하게 한다. Solution을 먼저 제시하고
Problem을 나중에 설명하지 않는다.

## 18. Insight Card

각 주요 전환점에서 짧고 기억하기 쉬운 Insight를 사용할 수 있다.
슬라이드 제작 과정에서 문장을 다듬어도 의미는 바꾸지 않는다.

1. “코드를 AI에게 가져가지 말고 AI를 코드로 데려가라.”
2. “좋은 Prompt보다 적절한 Context가 중요하다.”
3. “Context는 많을수록 좋은 것이 아니다. 필요한 순간에 필요한 Context가 중요하다.”
4. “AI에게 지식을 주는 것을 넘어 일을 수행하는 방법을 제공하라.”
5. “좋은 AI 모델과 좋은 AI 개발 시스템은 다른 문제다.”
6. “AI의 ‘완료했습니다’는 검증 결과가 아니다.”
7. “반복되는 실패를 Harness 개선으로 연결하라.”
8. “AI를 사용하는 방법에서 AI에게 일을 맡기는 방법으로 발전하라.”

## 21. 근거 확인 범위와 용어 정의

현재 ChatGPT 또는 Codex 기능을 설명할 때 기억만으로 단정하지 않고 최신
OpenAI 공식 문서 또는 공식 자료를 우선 확인한다. 확인 대상의 예는 다음과
같다.

- Codex Desktop/App
- CLI
- IDE integration
- AGENTS.md
- Skills
- Subagents
- Memory 관련 기능
- Worktree
- Cloud execution
- 기타 교육 시점의 현재 기능

기능이 버전이나 시점에 따라 달라질 수 있으면 교육자료에 적절한 범위에서
시점을 표시한다. Lost in the Middle처럼 연구 근거가 필요한 개념은 원 논문
또는 신뢰할 수 있는 기술 자료를 확인한다. 마케팅 문구나 블로그 표현을
검증된 일반 원칙처럼 확대 해석하지 않는다.

Harness Engineering과 Loop Engineering처럼 업계에서 용어 사용이 완전히
표준화되지 않았을 가능성이 있는 개념은 교육에서 사용하는 정의와 범위를
명확하게 설명한다.

## 22. 금지사항

교육자료가 다음과 같은 방향으로 변질되지 않도록 한다.

1. ChatGPT 기능 목록 교육
2. Codex 메뉴얼 교육
3. Prompt 작성 공식 암기 교육
4. AGENTS.md 작성법만 깊게 다루는 교육
5. Agent Framework 이론 교육
6. 초보자가 중간부터 따라갈 수 없는 고급 Agent 강의
7. 숙련자가 초반 몇 시간 동안 얻을 것이 없는 입문 강의
8. AI가 모든 개발 업무를 대신할 수 있다는 메시지
9. AI 결과를 검증 없이 신뢰하도록 유도하는 내용
10. 최신 기능을 확인하지 않고 단정하는 내용
11. 각 Chapter가 서로 독립된 기능 소개처럼 보이는 구성
12. Problem 없이 Solution부터 소개하는 구성
13. 처음부터 완성된 Harness Architecture를 보여주고 외우게 하는 방식

15. 교육을 위해 실제로 발생하지 않은 제작 과정의 문제를 실제 사례처럼 꾸미는 것
16. 교육생 직접 실습을 전제로 하는 구성
17. 6시간을 채우기 위해 불필요하게 이론을 늘리는 것
18. 현재 기획에 없는 새로운 핵심 메시지를 근거 없이 추가하는 것
19. 이후 작업 편의를 위해 MASTER_PLAN의 핵심 내용을 임의로 축약하는 것
20. Slide 수를 맞추기 위해 Story의 중요한 연결 과정을 삭제하는 것

## 23. 교육에서 특히 피해야 할 오해

다음 오해가 생기지 않도록 필요한 시점에 명시적으로 바로잡는다.

1. **“Prompt Engineering은 이제 필요 없다.”**
   Prompt Engineering은 Task를 명확하게 전달하는 기본 기술이다. 반복적인
   Context와 Workflow가 늘면 Prompt만으로 해결하기 어려운 문제가 생기며,
   해결 범위가 Context → Harness → Loop로 확장된다.
2. **“AGENTS.md를 크게 만들면 AI가 프로젝트를 더 잘 이해한다.”**
   항상 그렇지 않다. 관련성과 제공 시점이 중요하므로 공통 핵심 정보와
   Task별 정보를 구분한다.
3. **“Context Engineering은 문서를 많이 넣는 것이다.”**
   핵심은 어떤 정보를 어떤 작업에서 어떤 시점에 어떤 Agent에게 제공할지
   설계하는 것이다.
4. **“Subagent를 많이 쓰면 더 좋은 결과가 나온다.”**
   역할 분리, Context isolation, parallel investigation이 실제로 필요할 때
   사용한다. 불필요한 분리는 coordination overhead, 중복 조사, 결과 통합
   비용과 추가 Context를 만든다.
5. **“Memory는 많이 저장할수록 좋다.”**
   오래되거나 잘못된 정보를 유지할 수 있으므로 재사용 가치, 최신성,
   신뢰성과 Scope를 관리한다.
6. **“Harness를 구축하면 문제가 해결된다.”**
   Harness도 software system이다. 프로젝트 변경으로 낡을 수 있고 잘못된
   Rule, Skill, Memory가 Agent 성능을 떨어뜨릴 수 있으므로 관찰과 개선이
   필요하다.
7. **“Loop Engineering은 Agent를 계속 자동 실행하는 것이다.”**
   이 교육에서의 Loop Engineering은 단순 반복 실행이 아니라
   `Execution → Feedback → Learning → System Improvement`다.
8. **“Agent가 Build/Test를 실행했으므로 코드는 안전하다.”**
   어떤 Verification을 수행할지 정의하는 일은 중요한 Engineering 판단이다.
   Test가 있다는 사실만으로 필요한 Test coverage가 보장되지는 않는다.

## 24. 질문형 Chapter 전환

가능하면 강사가 해결책을 바로 말하기보다 질문을 던져 교육생이 다음 단계의
필요를 먼저 느끼게 한다. 다음 문구는 Slide 제목이나 Chapter transition으로
활용할 수 있다.

| 전환 | 질문 |
| --- | --- |
| Chatbot → Prompt Engineering | “같은 모델인데 왜 사람마다 결과가 이렇게 다를까?” |
| Prompt → Context | “그런데 왜 우리는 매번 같은 설명을 하고 있을까?” |
| 초기 AGENTS.md → Context 분리 | “그러면 모든 것을 AGENTS.md에 넣으면 되는 걸까?” |
| Context → Harness | “AI가 프로젝트를 잘 이해하면 항상 같은 방식으로 잘 일할까?” |
| Skill → Subagent | “하나의 Agent가 이 모든 역할을 동시에 수행해야 할까?” |
| Context → Memory | “지난번에 이미 알아낸 사실을 왜 또 조사하고 있을까?” |
| Harness → Loop | “이렇게 만든 Harness가 6개월 뒤에도 여전히 맞을까?” |
| Loop Engineering | “Agent가 같은 실수를 세 번째 반복했다면 문제는 Agent에게 있을까, 아니면 우리가 만든 시스템에 있을까?” |

## 25. Demo에서 실패를 다루는 원칙

성공 Demo만 보여주지 않는다. Story상 의미 있는 실패를 보여주되, Agent를
조롱하거나 AI가 멍청하다는 것을 보여주는 Entertainment로 사용하지 않는다.
각 실패는 `Failure → Cause → Engineering Response`를 이해시키는 재료다.

계획 가능한 실패 예시는 다음과 같다.

1. 모호한 Prompt로 Agent가 예상과 다른 범위까지 수정한다.
2. Context가 부족해 프로젝트 규칙을 모르고 잘못 가정한다.
3. AGENTS.md가 과도하게 커져 필요한 Rule과 불필요한 Rule이 뒤섞인다.
4. Verification을 생략해 코드 수정은 되었지만 Test가 실패한다.
5. 오래된 Skill이 변경된 Build command 대신 과거 command를 사용한다.
6. 오래된 Memory가 현재 Architecture와 맞지 않는 정보를 제공한다.
7. 같은 Failure가 반복되어 Harness 개선의 필요성이 드러난다.

실제 Demo에서 어떤 실패를 재현할지는 교육용 Repository와 환경을 설계할
때 결정한다. 실패는 재현 가능성과 설명 가치를 검토하고, 원인과 대응을
보여줄 수 있을 때 사용한다.

## 26. 같은 문제를 서로 다른 Maturity에서 비교

가능하면 같은 개발 문제를 AI 활용 성숙도에 따라 반복해서 보여준다. 예를
들어 “특정 입력에서 이미지 처리 결과가 잘못된다”는 문제를 다음과 같이
다룰 수 있다.

| 비교 단계 | 업무 방식 |
| --- | --- |
| Level 1 | 개발자가 관련 코드를 찾아 ChatGPT에 붙여넣고 질문한다. |
| Level 2 | 좋은 Prompt에 문제, 환경, 제약, 검증 조건을 넣는다. |
| Level 3 | Codex가 repository에서 관련 코드와 test를 직접 조사한다. |
| Level 4 | Project Context와 Skill을 사용해 정해진 Workflow로 조사·수정·검증한다. |
| Level 5 | 실행 중 반복 Failure가 Harness 개선으로 이어지고 다음 Task에 반영된다. |

이 Level 1–5는 하나의 문제를 점점 성숙한 방식으로 다루는 Demo용 비교
축이다. 교육생 분포를 설명하는 Level 0–4 표(2.1절)와 같은 분류 체계로
단정하거나 서로 일대일 대응시키지 않는다. 목적은 기술 목록이 아니라
업무 방식의 변화를 보여주는 것이다.

## 27. 교육용 Demo Repository 요구사항

별도 설계 단계에서 교육용 Demo Repository를 만든다. MASTER_PLAN 단계에서는
이 Repository를 구현하거나 구조를 추가하지 않는다. 후보 Repository는
다음 요건을 만족하는 방향으로 설계한다.

1. 개발자가 직관적으로 이해할 수 있다.
2. 복잡한 Domain 지식이 필요하지 않다.
3. Repository exploration을 보여줄 수 있도록 여러 파일과 Module 관계가 있다.
4. Build와 Test가 존재한다.
5. 의도적인 Bug를 넣을 수 있다.
6. Performance 또는 Refactoring 사례를 만들 수 있다.
7. 프로젝트 Rule을 적용할 수 있다.
8. AGENTS.md의 장점을 보여줄 수 있다.
9. Context가 늘면서 생기는 문제를 설명할 수 있다.
10. Skill로 분리할 자연스러운 반복 작업이 있다.
11. Subagent의 역할 분리가 자연스러운 복합 작업이 있다.
12. Memory가 필요한 반복 학습 사례를 만들 수 있다.
13. Harness가 낡는 상황을 보여줄 수 있다.
14. Loop Engineering으로 개선할 반복 Failure가 있다.
15. 6시간 교육에서 계속 사용할 수 있는 동일한 프로젝트다.

교육생들의 기술 배경이 다양하므로 특정 고급 Domain 지식 없이는 이해할 수
없는 프로젝트를 피한다. 일부 개발자가 CUDA/GPU 경험이 있더라도 교육생
전체가 같은 전문성을 가진다고 가정하지 않는다.

## 28. 교육자료 Repository와 Demo Repository 구분

다음 두 Repository 개념을 혼동하지 않는다.

**A. `ai-dev-training` — 교육자료 제작 Repository**

기획 원본, Curriculum, Storyline, References, Slide contents, Speaker notes,
Demo plans와 지시가 있을 때의 최종 PPT 등을 관리한다.

**B. 교육용 Demo Repository — 시연할 Software Project**

교육 중 실제 Codex 행동을 보여주기 위한 Software Project다. `ai-dev-training`
안의 `demos/`에 둘지 별도 Repository로 분리할지는 이후 설계 단계에서
결정한다.

교육자료 Repository 자체의 발전 과정은 Harness Engineering의 Meta Example로
쓸 수 있지만, A와 B의 Story를 억지로 동일하게 만들 필요는 없다.

## 29. 제작 과정 기록의 후속 계획

가능하면 설계 변경을 `Decision`, `Problem`, `Change`, `Result`,
`Potential Training Example` 관점으로 기록해 나중에 교육 사례로 쓸 수 있는지
판단한다.

`plan/DECISIONS.md`는 향후 별도 설계 단계에서 만들 수 있다. 현재 MASTER_PLAN
작성 단계에서는 이 파일이나 다른 추가 Memory/Skill/Subagent 시스템을
생성하지 않는다. 실제 제작 과정에서 문제가 생겼을 때 필요한 구조를
추가한다.

## 30. 향후 Source of Truth 계층

향후 문서가 늘어날 경우 다음 계층을 사용할 수 있다.

1. **MASTER_PLAN.md:** 교육 목적, 철학, Story, Audience와 핵심 방향을 정의하는
   가장 높은 수준의 Source of Truth.
2. **INVARIANTS.md:** 향후 작업에서 깨뜨리면 안 되는 조건을 MASTER_PLAN에서
   추출해 보존한다.
3. **DECISIONS.md:** 새 결정과 결정 이유를 기록한다. MASTER_PLAN을 몰래
   변경하는 용도로 사용하지 않는다.
4. **Curriculum / Story / Demo / Slide 문서:** 위 기준을 실행하는 하위 산출물.

하위 문서가 상위 문서와 충돌하면 상위 문서를 따른다. INVARIANTS.md와
DECISIONS.md는 향후 필요가 확정될 때 별도로 설계하며 현재 만들지 않는다.

## 31. 기획 변경 정책

“이 방식이 더 좋아 보인다”는 이유만으로 MASTER_PLAN을 조용히 변경하지
않는다. 계획 변경이 필요하다고 판단하면 먼저 다음을 제안한다.

- **PROPOSAL:** 바꾸려는 내용
- **REASON:** 변경이 필요한 이유
- **IMPACT:** 영향을 받는 Story, Slide, Demo 등

사용자 승인 전에는 기존 MASTER_PLAN을 유지한다. 특히 다음 기준은 임의로
변경하지 않는다.

- 6시간 교육과 개발자 대상
- AI 활용 수준 편차와 역량 균질화라는 최우선 목표
- 교육생 직접 실습 없음, Demo·사례·Insight 중심
- Chatbot → Prompt → Context → Harness → Loop의 큰 흐름
- Problem → Improvement → New Problem이라는 Storytelling
- 하나의 프로젝트가 진화하는 방식
- 초급자와 숙련자가 동시에 가치를 얻는 원칙
- Verification 강조
- Harness가 끝이 아니라 Loop로 발전하는 구조

- Prompt Engineering
- Context Engineering
- Harness Engineering
- Loop Engineering
- Agent
- Subagent
- Skill
- Memory

이 문서는 교육 Story에서 필요한 의미를 기술하지만 업계 전체가 같은 정의를

정의는 OpenAI 공식 자료, 원 논문, 신뢰할 수 있는 기술 자료와 실제 Agent
Engineering 사례를 조사해 보강한다.

## 33. 예상 Slide 규모와 밀도

현재 예상 규모는 약 60–70장이다. Slide 수 자체는 목표가 아니며 Demo와 화면
전환에 따라 실제 발표 파일의 장수는 달라질 수 있다.

- Story 흐름에 맞는 분리를 우선하고 한 장에 많은 내용을 압축하지 않는다.
- Slide 수를 채우려고 내용을 의미 없이 쪼개지 않는다.
- 반대로 Slide 수를 맞추려고 Story의 중요한 연결 과정을 삭제하지 않는다.
- 최종 Slide Map 단계에서 6시간 발표 속도와 Demo 시간을 고려해 다시
  계산한다.

## 34. Slide와 Speaker Notes의 역할 구분

화면에 보여줄 내용과 강사가 말할 내용을 구분한다.

**Slide**에는 핵심 메시지, Diagram, Before/After, Prompt, Screenshot, 결과와
Insight를 둔다.

**Speaker Notes**에는 왜 이 사례를 보여주는지, 앞 Chapter와 어떻게
연결되는지, 어떤 오해를 막아야 하는지, Demo에서 무엇을 강조할지, 다음
Problem으로 어떻게 넘어갈지를 기록한다.

슬라이드 자체를 긴 문서처럼 만들지 않는다.

## 35. 교육 종료 시 수준별로 남아야 할 변화

다음 Persona는 공통 Story 안에서 서로 다른 가치를 얻는 관점을 구체화한다.
이 Persona들을 별도 교육 과정으로 분리하지 않는다.

**Persona A — Chatbot User:** ChatGPT에 질문만 하고 Codex 경험이 거의 없으며
별도 AI 학습 시간이 부족한 개발자.

**Persona B — Practical Codex User:** Codex로 코드를 수정하고 Prompt와
AGENTS.md를 사용해봤지만 구조적인 Harness는 아직 없는 개발자.

**Persona C — Advanced Agent User:** Agent, Skill, Context 관리 경험이 있고
이미 높은 수준의 AI 활용 역량을 보유한 개발자.

**초급 개발자**는 “AI에게 에러를 질문하는 것만이 AI 활용이 아니다”를
이해하고, Codex가 repository를 직접 조사할 수 있다는 점, 바로 고쳐달라고
하기보다 먼저 조사하게 할 수 있다는 점, Build/Test를 실행하고 결과를
검증해야 한다는 점, 반복 프로젝트 지시를 AGENTS.md 등의 Context로 관리할
수 있다는 점까지 자연스럽게 이해해야 한다.

**중급 개발자**는 Prompt에 모든 것을 넣는 방식의 한계, Context를 구조화해
필요할 때 제공하는 이유, 반복 Workflow를 Skill/Harness로 발전시키는 방식을
가져간다.

**숙련 개발자**는 Context isolation과 Subagent 설계, Memory lifecycle 관리,
Harness 품질 평가, 반복 Failure를 System Improvement로 전환하는 방법에
관한 질문을 갖고 돌아간다.

Persona A는 최소한 ChatGPT/Codex의 차이, repository 조사, 명확한 지시,
선행 조사, Build/Test 검증과 AGENTS.md라는 다음 단계를 얻어야 한다.
Persona B는 Context relevance, AGENTS.md 비대화, Progressive Disclosure,
Skill, Subagent 사용 시점, Context와 Memory의 차이, Harness 관점을 얻어야
한다. Persona C는 Harness Technical Debt, stale Context/Skill/Memory,
Harness Evaluation, 반복 Failure 개선, 두 종류의 Loop 구분과 AI Development
Environment 자체를 Engineering 대상으로 보는 관점을 얻어야 한다.

어느 Persona가 6시간의 상당 부분에서 가치를 얻지 못하는 구조라면 Curriculum
단계에서 보완한다. 이 문제를 해결하려고 Story 순서를 깨거나 고급 내용을
앞에 억지로 배치하지 않는다.

## 36. 교육의 마지막 메시지

교육은 “ChatGPT/Codex 기능을 많이 알게 되었다”로 끝내지 않는다. 교육생이
자신의 사고 범위를 다음 순서로 넓히게 한다.

`AI에게 무엇을 물어볼까? → AI에게 어떤 문제 해결 과정을 맡길까? → AI에게
어떤 Context가 필요한가? → AI가 안정적으로 일하려면 어떤 환경이 필요한가?
→ 이 시스템은 경험을 통해 어떻게 더 좋아질 수 있는가?`

최종 진화는 다음처럼 정리할 수 있다.

`Question → Task → Context → System → Feedback Loop`

또는 교육 전체의 Story로:

`Chatbot → Prompt Engineering → Context Engineering → Harness Engineering
→ Loop Engineering → AI-Native Development`

## 37. 최종 Meta Insight

처음부터 복잡한 AI 시스템을 구축하는 것이 목적이 아니다. 현재 방식에서
실제 Failure와 Friction이 발생할 때 문제를 해결하는 최소한의 구조를
추가한다.

> Best Practice를 모두 먼저 설치하는 것이 아니라, 현재 Failure와 Friction을
> 관찰하고 필요한 Engineering을 추가한다.

이것은 교육의 Storytelling 방식이자 Harness/Loop Engineering의 핵심
철학이다.

| Memory | 재사용 가치가 있는 Project 지식을 계속 다시 발견하는 일이 문제가 되어 도입한다. |
| Loop Engineering | 같은 목표의 검토 지적을 다음 수정으로 사람이 계속 연결해야 하는 문제에서 도입한다. |

이유를 설명하지 못하는 기술은 Story에서 등장하는 위치를 다시 검토한다.

## 43. 기술적 깊이의 세 Layer

각 개념을 다음 세 Layer로 설명할 수 있도록 설계한다.

1. **Intuition:** 처음 듣는 개발자도 이해할 수 있는 직관적인 설명. 예를
   들어 Context Engineering은 “AI가 지금 이 일을 하기 위해 무엇을 알아야
   하는가?”라는 질문으로 시작한다.
2. **Practical Engineering:** 실제 Codex 작업에서 적용하는 방법. 예로
   AGENTS.md, Context file, Skill, Task-specific instruction을 든다.
3. **Deeper Insight:** 숙련자가 생각할 Engineering 문제. 예로 Context
   relevance, isolation, stale Context, retrieval strategy, coordination
   overhead, Memory lifecycle을 다룬다.

모든 개념을 Layer 3까지 깊게 다룰 필요는 없지만 주요 Chapter가 초급 설명만
하고 끝나지 않도록 한다. 반대로 Layer 3이 Layer 1을 이해하기 어렵게
만들어서는 안 된다.

## 44. Demo와 이론의 비율

6시간이 이론 강의만으로 흐르지 않도록 각 주요 Engineering 단계에 가능한 한
하나 이상의 시각적 사례 또는 Demo를 연결한다.

- `Concept → Short Example → Demo / Visual Evidence → Insight`
- `Problem Demo → Why → Engineering Concept → Improved Demo → Insight`

Repository exploration, Prompt 차이, AGENTS.md 전후, Context 분리, Skill,
Subagent, Memory, Build/Test Verification, 반복 Failure와 Harness 개선은
가능하면 실제 Codex 화면이나 준비된 결과로 보여준다. Demo가 Story를
방해하지 않도록 개수와 순서는 향후 Demo Architecture 단계에서 우선순위를
정한다.
