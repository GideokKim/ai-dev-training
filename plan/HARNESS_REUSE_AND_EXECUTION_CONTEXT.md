## 목적과 보호 범위

S71에서 이해한 Harness를 다음 프로젝트에 재사용할 기반으로 먼저 보여준다.
적용 조건은 그 기반을 새 프로젝트에 연결할 때 확인할 사항으로 설명한다.
사용자가 삭제한 이전 S73의 독립 C++ 전이 장은 제거한다. 다른 C++ 설명은 유지한다.
공통 수행 틀과 프로젝트별 명세·Context·명령·권한의 연결이 이 구간의 핵심이다.
전체 Harness를 복사하기만 하면 어떤 프로젝트에서도 작동한다는 보장이 아니다.

ACT4는 축소하지 않는다. 기존19장·81분, 장별 역할·시간·Mode·근거를 모두 보존한다.
ACT3의 질문은 재사용할 구성과 적용 조건이고, ACT4의 질문은 실제 관찰에서
시스템을 왜 바꾸고 후속 기록을 어떻게 확인했는가다. 환경 목록을 한 문장으로
줄이겠다는 이전 제안은 채택하지 않는다. 아래의 ACT4 기존 구성 표를 유지한다.

## 각 장의 화면·운영 의도

### S72 — 만든 Harness를 다음 프로젝트의 기반으로

질문: “프로젝트가 바뀔 때마다 작업 방법까지 처음부터 다시 만들 필요가 있을까요?”

핵심: 검토해 둔 조사·변경·검증 절차와 도구 연결·보고 방식을 공통 기반으로 남겨 다음 프로젝트의 출발점으로 쓸 수 있다.

화면: 왼쪽 하나의 Harness 기반에서 오른쪽 프로젝트 A/B/C로 가지가 나뉜다. 성공률·속도 수치나 완료 체크 없이 동일한 기반의 재사용 관계만 보여준다.

경계: TEACHING MODEL — 재사용의 설계 가치다. 다른 프로젝트에서 실행·검증한 Demo나 시간·성능 개선 성과가 아니다.

다음 연결: “그 기반에서 무엇을 다시 쓰고, 무엇을 프로젝트에 맞게 연결해야 할까요?”

### S73 — 공통 기반에 프로젝트 기준을 연결한다

질문: “같은 작업 체계를 쓰더라도, 새 프로젝트에서 무엇을 연결해야 할까요?”

핵심: 조사·변경·검증의 흐름과 도구 연결·보고 틀은 재사용하고, 목표·명세·Context·실제 명령·허용 권한은 새 프로젝트에 맞춘다.

화면: 왼쪽 공통 수행 틀과 오른쪽 프로젝트 기준을 같은 높이의 두 영역에 놓고 더하기로 연결한다. 아래 한 줄은 기반 재사용과 적용 조건 연결의 관계를 회수한다.

경계: TEACHING MODEL — 공통 틀과 프로젝트별 조건을 나누는 설계다. 전체 Harness를 그대로 복사하면 작동한다는 보장·이식 성공·절감 측정은 없다.

다음 연결: “연결할 조건 중 실행 권한이 왜 필요한지, 앞의 실제 테스트 오류로 돌아보겠습니다.”

### S74 — 임시 폴더 오류의 원인은 실행 권한이었다

질문: “코드에 접근했는데도, 왜 일부 테스트는 실행되지 않았을까요?”

핵심: TRIAL-001의 별도 테스트는 임시 폴더가 필요했지만 읽기 전용 실행 환경이라 생성하지 못했다. Crop 결함과 별개의 실행 조건이다.

화면: 테스트 실행, 임시 폴더 생성 요청, 읽기 전용 권한에 막힘을 세 단계로 보여준다. 마지막은 붉은 중단 영역이며 실제 로그 Screenshot으로 표현하지 않는다.

경계: FROZEN WITH SCOPE — TRIAL-001의 과거 CLI 관찰. Crop 결함과 별개이며 Agent가 권한을 해결하거나 확대하지 않았다. 현재 Desktop 결과가 아니다.

다음 연결: “그렇다면 Agent가 작업할 조건은 Repository 안에서만 정해질까요?”

### S75 — Agent의 실행 조건은 어디에서 오는가?

질문: “같은 Repository를 열어도, 실행에 적용되는 조건은 모두 같을까요?”

핵심: Agent 실행에는 Repository의 코드·지침·문서와 별도로 전역 지침·Skills, 모델·설정, 허용 권한 같은 조건이 적용될 수 있다. 새 프로젝트에 연결할 때 적용 여부를 확인한다.

화면: 왼쪽 Repository 안의 코드/AGENTS.md/문서/Skill은 중앙 Agent로 실선 연결한다. 오른쪽 Repository 밖 조건은 점선과 적용 확인 라벨로 연결해 개념 관계와 실제 확인을 구분한다.

경계: TEACHING MODEL / REQUIRES PRODUCT CHECK — 적용 관계의 모델이며 정확한 로딩 순서·전체 설정 목록·통제 환경 비교가 아니다. 대상 제품·계정·권한은 별도 확인한다.

다음 연결: “이런 저장소 밖 지침이 실제 작업에도 포함됐던 기록을 보겠습니다.”

### S76 — 실제 성능 조사에도 저장소 밖 지침이 들어왔다

질문: “저장소에 넣지 않은 수행 지침이 실제 작업에도 관여했을까요?”

핵심: TRIAL-006 Resize 성능 조사에서는 전역 Skill 본문이 포함됐고 평가 상태 작성·추가 동작 검증 같은 관여가 기록됐다. Hook 설정·MCP 연결 경고는 별도 시작 관찰이다.

화면: 전역 Skill에서 실제 작업 기록으로 이어지는 두 영역과 아래 별도의 시작 경고 줄을 둔다. Skill 이름4개나 로그 전문을 본문에 나열하지 않는다. 실제 CLI 기록의 의미 재구성이다.

경계: FROZEN WITH SCOPE — 실제 전역 Skill 포함·일부 작업 관여를 보존한다. Hook 실행·MCP 작업 결과·전체 환경 감사·각 요소의 성능 인과효과·현재 Desktop 재현은 미입증이다.

다음 연결: “시작에 나온 경고와 실제 작업에 사용된 기록은, 같은 근거일까요?”

### S77 — 시작 경고와 실제 사용은 구분해서 확인한다

질문: “시작 경고가 있었다면, 그 도구를 작업에 썼다고 말할 수 있을까요?”

핵심: 시작 경고만으로 Hook 실행이나 MCP 작업 사용을 확정할 수 없다. 반면 전역 Skill의 평가 상태 작성·추가 검증 관여는 해당 작업 기록으로 확인했다.

화면: 왼쪽 점선 영역은 시작 경고와 MCP 호출 기록 없음, 오른쪽 실선 영역은 전역 Skill의 실제 작업 관여를 보여준다. 색·선·문구를 함께 사용하고 전부 미확인으로 되돌리지 않는다.

경계: FROZEN WITH SCOPE — Hook 설정 경고는 실행·소스 변경 증거가 아니다. MCP 시작/인증 오류는 작업 호출·결과 사용 증거가 아니다. 실제 관찰한 Skill 관여와 기록된 결과 범위는 유지한다.

다음 연결: “이 차이를 다음 프로젝트에서도 확인하려면 무엇을 함께 남기면 좋을까요?”

### S78 — 결과와 실행 조건을 함께 남긴다

질문: “다음 사람이 이 작업 체계를 쓸 때, 어떤 조건과 근거를 함께 볼 수 있어야 할까요?”

핵심: 무슨 작업을 했고 어떤 실행 조건을 확인했으며 어떤 테스트·측정 근거와 미확인이 남았는지 함께 기록하면 재사용할 기반의 적용 범위를 판단할 수 있다.

화면: 작업/실행 조건/확인 근거의 세 행을 하나의 편집 가능한 기록 틀로 보여준다. 실제 완료 보고서·Screenshot·새 실행 결과로 보이지 않도록 교육용이라고 표시한다.

경계: TEACHING MODEL — 권장 기록 항목의 예다. 실제 새 보고서·완전한 환경 감사·기록 품질 향상은 검증하지 않았다. 실제 평가·보고 기준 변경 과정은 ACT4에서 기존 분량대로 다룬다.

다음 연결: “이제 우리 팀에서 다음 프로젝트에도 남겨 쓸 기반 한 가지와 유지할 책임을 생각해 보겠습니다.”
