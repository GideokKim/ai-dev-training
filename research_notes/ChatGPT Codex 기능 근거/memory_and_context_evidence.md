# Memory and Context Evidence

Checked date for this note: 2026-09-25. Product behavior below is scoped to the
documented product surface and settings; it is not a promise that every account,
workspace, app, host, or version exposes the same behavior.

## 1. Persistence layers and past-task learning transfer

### Takeaway

ChatGPT Memory, Codex local Memories, repository instructions and documents,
the active task/thread context, and a deliberately engineered agent-memory
store have different scopes and controls. As of 2026-09-25, Codex has a
documented local-memory feature that can generate and reuse context from some
past chats, but it is off by default and eligibility, per-chat choices,
background timing, and quota conditions mean that not every lesson transfers.
For rules that must reliably apply to project work, OpenAI explicitly directs
teams to `AGENTS.md` or checked-in documentation; product memory is a recall
aid.

### Cited Findings

**M1 — ChatGPT user Memory**

- Source type: OFFICIAL — OpenAI Help Center, [Memory in ChatGPT](https://help.openai.com/en/articles/8590148-memory-in-chatgpt). Page indicated “Updated: 5 days ago” when checked, approximately 2026-09-20; checked 2026-09-25. Scope: ChatGPT personalization, with controls and available sources varying by plan, region, platform, and workspace. Confidence: High for documented behavior. Volatility: High for product controls and availability.
- Evidence: The Help Center distinguishes saved memories from information referenced from chat history; says ChatGPT does not keep every detail from past conversations; and states that memory can change as context changes. It also names other possible sources, including custom instructions, Library files, and connected apps, depending on account/workspace. These are personalization inputs, not a repository’s canonical project record. ([OpenAI Help Center](https://help.openai.com/en/articles/8590148-memory-in-chatgpt))
- Evidence: Users can review or delete remembered items and control Memory in settings; the deletion guidance says a saved item may also need removing from its originating chat and other sources. This makes retention and removal lifecycle part of the product behavior. ([OpenAI Help Center](https://help.openai.com/en/articles/8590148-memory-in-chatgpt))

**M2 — Codex local Memories**

- Source type: OFFICIAL — OpenAI Codex documentation, [Memories](https://developers.openai.com/codex/customization/memories). No publication or update date was displayed on the page; checked 2026-09-25. Scope: ChatGPT desktop app’s local Codex controls, Codex CLI/TUI, and IDE extension using its connected Codex host’s local store. It says ChatGPT web uses ChatGPT Memory and ChatGPT Work does not use the local Codex store. Confidence: High for the documented controls and storage model. Volatility: High; current feature and configuration documentation.
- Evidence: The document says local Codex memories are off by default. After enabling, Codex may create local memory files from eligible previous chats; active and short-lived sessions are skipped, generation runs in the background, and the update may not happen immediately. A low remaining rate-limit percentage can also cause a generation pass to be skipped. ([OpenAI Codex Memories](https://developers.openai.com/codex/customization/memories))
- Evidence: The app and Codex TUI expose `/memories` controls for whether the current chat may use existing memories and whether it may contribute to future memories; those chat-level controls do not change global settings. The IDE extension uses the connected host’s local store. ([OpenAI Codex Memories](https://developers.openai.com/codex/customization/memories))
- Evidence: The documented store is under the Codex home directory, usually `~/.codex/memories/`, and contains generated summaries, durable entries, recent inputs, and supporting evidence. OpenAI describes these as generated state, advises inspection before sharing the Codex home directory, and says not to rely on manual edits as the primary control surface. ([OpenAI Codex Memories](https://developers.openai.com/codex/customization/memories))
- Evidence: OpenAI says generated memory fields redact secrets, but the same document says not to store secrets and to review memory files before sharing them. This is not a guarantee that secrets can never be retained or exposed. ([OpenAI Codex Memories](https://developers.openai.com/codex/customization/memories))
- Evidence: Configuration can disable memory generation for chats that used external context such as MCP calls, web search, or tool search (`memories.disable_on_external_context = true`). This is a configurable exclusion, not a claim that all research/tool-using chats are excluded by default. ([OpenAI Codex Memories](https://developers.openai.com/codex/customization/memories))

**M5 — Active thread/runtime context**

- Source type: OFFICIAL — OpenAI engineering explanation, [Unrolling the Codex agent loop](https://openai.com/index/unrolling-the-codex-agent-loop/). Published 2026-01-23; checked 2026-09-25. - Evidence: In the described loop, the model’s tool calls are executed and their outputs are appended to the prompt for the next inference; a new user turn in the same conversation includes conversation history and prior tool calls. ### Inferences

- Direct answer to “Do task learnings transfer automatically in Codex?”: **Sometimes, if local Codex Memories are enabled and the chat is eligible and allowed to contribute.** The product may generate and later use memory without a manually written memory file, but it skips some sessions, works asynchronously, can skip on a rate-limit threshold, and permits chat-level opt-out. Do not say “Codex never remembers across tasks” as a current universal fact; do not say “Codex automatically carries every task learning forward” either. This conclusion combines M2’s product rules. ([OpenAI Codex Memories](https://developers.openai.com/codex/customization/memories))
- For predictable project behavior, explicitly persist requirements and decisions in versioned project docs and route Codex to them. This follows OpenAI’s direct instruction that required team guidance belongs in `AGENTS.md` or checked-in documentation, while Memories are a recall aid. ([OpenAI Codex Memories](https://developers.openai.com/codex/customization/memories); [OpenAI Codex AGENTS.md documentation](https://developers.openai.com/codex/agent-configuration/agents-md))
- Use four distinct teaching layers: (1) ChatGPT account/workspace personalization Memory; (2) Codex host-local cross-chat Memories; (3) repository-persistent, reviewable team context; (4) active task/thread context passed through prompts, files, and tool results. A custom agent may add a fifth, explicitly engineered persistence/retrieval layer. This taxonomy is a training model synthesized from M1–M6, not an OpenAI product taxonomy. ([OpenAI Help Center](https://help.openai.com/en/articles/8590148-memory-in-chatgpt); [OpenAI Codex Memories](https://developers.openai.com/codex/customization/memories); [OpenAI Codex AGENTS.md documentation](https://developers.openai.com/codex/agent-configuration/agents-md); [OpenAI Agents SDK sandbox memory](https://developers.openai.com/api/docs/guides/agents/sandboxes))
- A “Memory” Demo can safely show explicit project knowledge being recorded, retrieved, reviewed, and corrected. If demonstrating Codex’s native local Memories instead, show the feature status and settings, and allow for delayed generation; do not guarantee that a chosen prior chat has already become retrievable memory. ([OpenAI Codex Memories](https://developers.openai.com/codex/customization/memories))
- Because Codex’s documented store is local to the Codex home/connected host and ChatGPT web uses a separate ChatGPT Memory, do not promise automatic cross-product or cross-device synchronization. The documentation reviewed here does not specify such a sync contract. ([OpenAI Codex Memories](https://developers.openai.com/codex/customization/memories))

## 2. Context evidence: long input, retrieval, and Progressive Disclosure

### Takeaway

The evidence supports a bounded lesson: a model’s maximum context-window size
does not establish that it will use every fact in a long input equally well.
The original Lost in the Middle study observed strong position sensitivity in
its evaluated 2023 models and tasks; later research also shows that long-context
performance depends on task difficulty and lexical cues. None of these papers
establishes that every current ChatGPT/Codex model will show the same effect on
repository work. For teaching, treat relevance, retrieval, placement, and
task-specific verification as engineering concerns. Progressive Disclosure is
an information-routing pattern, not a goal of splitting files for its own sake.

### Cited Findings

**C1 — Context window is a capacity boundary, not a quality guarantee**

- Source type: OFFICIAL — OpenAI API guide, [Prompt engineering](https://developers.openai.com/api/docs/guides/prompt-engineering). No publication or update date was displayed; checked 2026-09-25. Scope: API prompting and model context. Confidence: High for the described API concept. Volatility: High for per-model capacities and current recommendations.
- Evidence: OpenAI defines the context window in tokens and explains that models can only process a bounded amount in a generation request. It separately advises adding relevant task context, for example retrieved data, rather than treating the prompt as unlimited storage. The page contains model-specific values; this note intentionally does not reuse its model-capacity figures as future training claims. ([OpenAI API guide, Prompt engineering](https://developers.openai.com/api/docs/guides/prompt-engineering))

**C2 — Original Lost in the Middle findings**

- Source type: ACADEMIC — Nelson F. Liu et al., [Lost in the Middle: How Language Models Use Long Contexts](https://aclanthology.org/2024.tacl-1.9/), published in *Transactions of the Association for Computational Linguistics* 12 (2024), pp. 157–173; preprint first appeared 2023-07-06. Checked 2026-09-25. Scope: controlled multi-document QA and synthetic key-value retrieval experiments using the models available to the authors in 2023. Confidence: High for the reported results and experimental scope. Volatility: Low for the historical paper; high for extrapolating to newer models/products.
- Evidence: In multi-document QA, the researchers varied the number/order of Wikipedia passages while exactly one passage contained the answer. Performance was often highest when the answer-bearing passage was at the beginning or end and degraded when it was in the middle. The tested settings used 10, 20, and 30 documents. ([Liu et al., TACL 2024](https://aclanthology.org/2024.tacl-1.9/))
- Evidence: For GPT-3.5-Turbo, the middle-position multi-document QA result could fall below its 56.1% closed-book baseline. A smaller GPT-4 (8K) subset still showed the U-shaped position trend despite higher absolute performance. These are task/model-specific results, not a statistic about current ChatGPT/Codex overall. ([Liu et al., TACL 2024](https://aclanthology.org/2024.tacl-1.9/))
- Evidence: In a synthetic key-value task, some models handled matching values well while others struggled with middle-position facts. Repeating the query before and after the data helped that synthetic retrieval task but minimally changed the multi-document QA trend. This warns against turning a single formatting trick into a general remedy. ([Liu et al., TACL 2024](https://aclanthology.org/2024.tacl-1.9/))

**C3 — Later long-context evidence tests different capabilities**

- Source type: ACADEMIC — Ali Modarressi et al., [NoLiMa: Long-Context Evaluation Beyond Literal Matching](https://arxiv.org/abs/2502.05167), submitted 2025-02-07; paper page identifies it with ICML 2025. Checked 2026-09-25. Scope: associative needle-in-a-haystack evaluation where question/needle have little literal keyword overlap; 12 evaluated models advertised at least 128K context. Confidence: High for reported benchmark results. Volatility: Low for historical results; high when inferring current model behavior.
- Evidence: The paper reports that performance falls as context length grows on its less-literal-match task. At 32K, 10 of the 12 tested models fell below half their strong short-context baseline; GPT-4o fell from 99.3% at the short-context baseline to 69.7%. These are NoLiMa benchmark scores, not generalized coding accuracy or current GPT-6/Codex results. ([Modarressi et al., NoLiMa](https://arxiv.org/abs/2502.05167))
- Evidence: The paper’s motivation is that simple needle benchmarks can reward literal word overlap and therefore overstate associative retrieval ability. Its contribution is a different benchmark design, not a proof that all long-context use fails. ([Modarressi et al., NoLiMa](https://arxiv.org/abs/2502.05167))

**C4 — “Long context” includes heterogeneous tasks**

- Source type: ACADEMIC — Omer Goldman et al., [Is It Really Long Context if All You Need Is Retrieval? Towards Genuinely Difficult Long Context NLP](https://aclanthology.org/2024.emnlp-main.924/), EMNLP 2024, pp. 16576–16586. Checked 2026-09-25. Scope: position paper/taxonomy for long-context NLP tasks. Confidence: High for the authors’ proposed taxonomy; it is a position paper, not a universal standard. Volatility: Low.
- Evidence: The authors argue that merely grouping tasks by total input length conflates materially different uses. They propose “Diffusion” (how difficult it is to find required information) and “Scope” (how much required information must be found) as two task-difficulty axes. ([Goldman et al., EMNLP 2024](https://aclanthology.org/2024.emnlp-main.924/))

**C5 — Progressive Disclosure and repository Context**

- Source type: INDUSTRY case / OFFICIAL OpenAI engineering report — [Harness engineering: leveraging Codex in an agent-first world](https://openai.com/index/harness-engineering/), published 2026-02-11. Checked 2026-09-25. Scope: one OpenAI team’s Codex-based internal product/repository. Confidence: High that this is the team’s reported practice; medium for transferring the pattern to other teams. Volatility: Medium.
- Evidence: The team reports that one large `AGENTS.md` crowded task/code/relevant documentation, made all guidance seem equally important, became stale, and was hard to verify. They instead used a short entry point as a table of contents for structured docs, with agents beginning from a stable map and following pointers to relevant deeper information. The article calls this progressive disclosure and describes automated link/freshness checks and doc-gardening. ([OpenAI, Harness engineering](https://openai.com/index/harness-engineering/))
- Evidence: The article frames repository-local, versioned artifacts as what an agent can inspect in-context during work; knowledge kept only in chat, private documents, or people’s heads is not available unless made discoverable. It reports an organizational design choice, not a controlled causal measurement of the map’s effect. ([OpenAI, Harness engineering](https://openai.com/index/harness-engineering/))
- Evidence: The OpenAI Agents SDK Sandbox guide gives a separate concrete progressive-disclosure implementation: inject a short memory summary, search the full memory when prior work is relevant, and open a rollout summary only when more detail is needed. This example is specifically an SDK sandbox memory capability, not Codex’s built-in local Memories. ([OpenAI Agents SDK sandbox memory](https://developers.openai.com/api/docs/guides/agents/sandboxes))

### Inferences

- Safe general statement: “Longer context windows increase what a model can receive, but do not by themselves prove that relevant information will be found and used robustly for every task.” This is supported by C2/C3, and stays within those results. ([Liu et al., TACL 2024](https://aclanthology.org/2024.tacl-1.9/); [Modarressi et al., NoLiMa](https://arxiv.org/abs/2502.05167))
- Avoid the unconditional statement “LLMs always forget the middle,” and avoid stating that a 2023 paper predicts current GPT-6/Codex behavior. The papers test selected models, model versions, and task designs; later models and tasks require fresh evaluation. ([Liu et al., TACL 2024](https://aclanthology.org/2024.tacl-1.9/); [Goldman et al., EMNLP 2024](https://aclanthology.org/2024.emnlp-main.924/))
- Recommended honest Demo: use a small controlled retrieval task with the same model/version, prompt, answer fact, and distractor text; move only the relevant fact among beginning/middle/end positions and include a “fact absent” control. Record the exact model/surface/date, context length, repetitions, and correct/incorrect/unsupported outputs. Describe only the observed results for that Demo. Do not infer internal attention mechanics from outputs or generalize to all coding tasks. This is a proposed demonstration protocol, not an experiment performed in this note. ([Liu et al., TACL 2024](https://aclanthology.org/2024.tacl-1.9/); [Goldman et al., EMNLP 2024](https://aclanthology.org/2024.emnlp-main.924/))
- For a training story, use the original paper as bounded research evidence and any current Codex test as a separate product-specific case. If current Codex does not reproduce the pattern in one trial, do not alter the data or claim the paper is disproven; the task, sample, version, and metric differ. Record what was and was not tested. ([Liu et al., TACL 2024](https://aclanthology.org/2024.tacl-1.9/); [Goldman et al., EMNLP 2024](https://aclanthology.org/2024.emnlp-main.924/))
- Progressive Disclosure Demo can show a short `AGENTS.md` router pointing to a project guide and task-specific sources. Its defensible claim is that it routes context by task and avoids loading the whole knowledge base up front; do not claim the pattern guarantees accuracy or prevents stale docs without demonstrating the relevant validation mechanism. ([OpenAI Codex AGENTS.md documentation](https://developers.openai.com/codex/agent-configuration/agents-md); [OpenAI, Harness engineering](https://openai.com/index/harness-engineering/))

### Gaps

- TODO: No primary academic evaluation located in this scoped pass demonstrates whether the currently offered GPT-6/Codex model family has the same positional performance curve on repository coding tasks. Do not present that as an established current product fact.
- TODO: The papers do not identify a universal context-length threshold at which a specific current Codex task becomes unreliable. Such a threshold must be measured on a defined model, task, and dataset.
- TODO: No controlled replication was performed for this project’s proposed Demo. The test design above is a recommendation; no result or live-demo outcome is asserted.

Use the categories as provenance labels. “Official” means an OpenAI product/API
document or a first-party engineering account; it does not make an emerging
engineering phrase a universal standard. Academic papers define their own
research constructs or propose visions; those are not automatically fieldwide
consensus. The training’s Harness Engineering and Loop Engineering meanings
are operational definitions for this course, and should remain separate from
broader usage.
