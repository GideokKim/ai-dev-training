## 전체에서 반복되는 실무 흐름

자료 묶음은 AI를 단순 질의응답 도구가 아니라 업무 과정의 보조자로 다룬다. 공통 작업 흐름은 다음과 같다.

1. 업무 목표와 문제를 구체화한다.
2. 환경, 기존 시스템, 데이터, 제약, 원하는 결과 형식을 AI에 제공한다.
3. 코드·조사·설계·테스트·문서의 초안이나 대안을 만든다.
4. 실행, 출처, 테스트, 측정, 비교 기준으로 결과를 확인한다.
5. 사람이 최종 선택·승인하고 결정 근거와 후속 조치를 남긴다.

각 모듈은 이 흐름을 서로 다른 업무에 적용한다. M1은 사용·보안 경계, M2는 요청 구성, M3은 조사와 보고, M4·M9는 설계와 의사결정, M5·M6은 코드·테스트·디버깅, M7은 학습, M8은 자동화와 성과 측정을 다룬다.

## 00\. AI 적용 분야

### 실제로 다루는 내용

AI 적용 지도를 전사 범위로 펼친다. ERP/SCM의 수요 예측·재고 최적화·공급망 위험 분석, HR의 인재·교육 추천, 보안 이상 탐지와 위협 대응, 문서 작성·요약·번역, 소프트웨어 개발, 데이터 분석, 회의록과 할 일 추출, 비전검사, 예지 보전, 자동 리페어, 고객 서비스, 추천 시스템, 지능형 자동화를 한 장에서 나열한다.

### 자료가 전달하는 실질 메시지

AI 활용 후보는 개발 부서에 한정되지 않으며, 사무 업무·기업 시스템·장비·제품까지 찾아볼 수 있다는 점을 보여준다. 실제 내용은 도입 효과의 검증이나 실행 계획이 아니라 적용 분야의 폭을 소개하는 지도다. 목록에 든 사례가 모두 실제 도입되었거나 성과가 입증되었다고 말하지는 않는다.

## M1\. 생성형 AI 기초 이해 및 도구 활용

### 실제로 다루는 내용

* 개발 방식의 변화를 검색·복사·수정에서 문제 정의·AI 초안 생성·검증·후속 개선으로 설명한다. MFC 카메라 프리뷰 사례에서는 CDialog, GigE, 30fps, Picture Control 같은 조건을 요청에 넣고 컴파일·메모리·스레드 안전성을 확인하도록 한다.
* AI 활용에 적합한 일로 정형 코드·보일러플레이트 생성, 패턴 변환, 문서화, 기술 비교, 오류 분석 가설을 든다. 도메인 알고리즘의 적합성, 실제 카메라/스테이지 타이밍, 장시간 양산 안정성, 사내 코드 이해, 보안 판단은 AI가 확정할 수 없는 일로 구분한다.
* 카메라 그랩 코드, OpenCV와 Halcon 비교, 로그 분석, API 문서, 아키텍처 검토에 대한 기존 방식과 AI 방식의 소요 시간 비교표를 제시한다. 슬라이드의 절감률은 강의 자료가 든 예시 수치이며 일반화된 실측 보증으로 제시된 것이 아니다.
* Copilot을 IDE 인라인 코드 제안, ChatGPT를 설계·리서치 대화, Claude를 긴 코드 분석, Gemini를 이미지·문서 등 멀티모달 사례에 배치하고, 동일한 OpenCV/MFC 함수 요청에 대한 응답 형태·장단점을 비교한다.
* VS2022 Copilot 설치·계정 연결·자동완성·채팅 패널·단축키, ChatGPT 병행 사용과 프로젝트별 대화 구분을 안내한다.
* 공개 코드·일반 기술 질문·가상 예제·공개 자료와 핵심 알고리즘·고객 이미지/수율 데이터·내부 인프라 정보·NDA 정보·개인정보를 나누어 입력 전 판단하도록 한다. 로그의 IP·고객명·경로를 지운 뒤 활용하는 예도 든다.
* 검증 없는 AI 코드 적용으로 cv::Mat 메모리 누수, 듀얼 카메라 Race Condition, 고객 웨이퍼 이미지 외부 전송이 발생하는 가상 장애를 제시하고, AI는 초안이며 커밋·양산 반영자는 책임을 지고 AI 사용 사실을 팀에 투명하게 알리라는 원칙을 제시한다.

### 실질적 결론

AI로 검색·초안 시간을 줄이는 데서 끝나지 않고 개발자의 역할을 문제 정의와 결과 검증으로 옮기라는 내용이다. 도구 선택은 작업에 따라 달라지고, 데이터 입력 허용 범위는 회사 정책에 따라야 하며, 최종 기술·보안 책임은 사람에게 남는다.

## M2\. 프롬프트 엔지니어링 기본

### 실제로 다루는 내용

* **요청의 기본 구조:** Instruction(구체적 작업), Context(기술 스택·실행 환경·제약), Input Data(실제 코드/자료), Output Indicator(결과물 형식)의 네 요소로 프롬프트를 만든다. 지시는 동사로 시작하고, 실제 코드와 성능·코딩 규칙 조건을 주며, 코드만 받을지 설명·변경점·Before/After 성능 비교까지 받을지 지정한다.
* **모호한 요청과 구체 요청의 대조:** `이 코드 최적화해줘`와 C++17/OpenCV/VS2022, 16K 이미지, 매 프레임 실행, buffer 재사용·parallel\_for\_, 수정 코드·변경점·예상 성능 비교를 적은 요청을 비교한다. 예시 표는 전자는 Python/4K 가정이나 일반 조언이 나올 수 있고, 후자는 실제 환경에 맞춘 구현을 요청할 수 있음을 보여준다.
* **Temperature:** 강의는 이를 지능이나 정확도가 아닌 다음 토큰 선택 다양성의 조절 값으로 설명한다. 0.0은 코드 생성·버그 수정, 0.5는 설계·리팩토링 대안, 1.0은 아이디어 발산의 예로 든다. 발표자 노트는 지원 여부가 API/제품마다 다르며 0이어도 완전히 결정론적이지 않을 수 있다고 덧붙인다.
* **Zero-Shot:** 예시 없이 바로 지시한다. 빠르고 간단하므로 단순 질문·용어 설명·포맷팅·간단 변환에 적합하지만 복잡한 분석에는 얕거나 부정확할 수 있다고 설명한다.
* **Few-Shot:** 원하는 형식의 예시를 프롬프트에 포함해 같은 패턴으로 수행하게 한다. 코드 리뷰 예시에서는 `Mat` 값 전달의 복사 비용을 지적하는 리뷰를 먼저 보여준 뒤 대상 코드도 같은 형식으로 검토시킨다. 결과가 예시의 품질과 적합성에 좌우된다는 단점을 함께 제시한다.
* **Chain-of-Thought / Guided CoT:** 복잡한 검토를 여러 관점·단계로 나눈다. 자료는 메모리(복사·누수)→성능(16K 병렬화)→가독성, 또는 메모리→성능→에러 처리(null/실패) 체크리스트를 순서대로 적용하고 항목마다 문제·심각도·수정 코드를 내게 한다. 도메인 체크리스트를 프롬프트에 주입하는 Guided CoT가 실무 리뷰에 유용하다는 것이 강의의 주장이다.
* **Structured CoT:** 분석 결과를 JSON/XML/태그 같은 정해진 구조로 나눠 일관되게 출력하는 방법으로 제시한다. 슬라이드 예시는 <step1_analysis>, <step2_hypothesis>, <step3_conclusion> 태그와 thought_process 배열을 사용한다.
* **Tree of Thoughts (ToT):** 한 경로만 따라가지 않고 여러 구현 대안을 만들고 장단점을 비교한 뒤 하나를 선택하는 방식이다. 강의는 아키텍처·최적화 선택에 연결하고, 3가지 구현 전략 제안→평가→선택→구현 연습을 제안한다.
* **업무별 개발 템플릿:** 설계는 Self-Discover + Decomposed로 코드 작성 전에 접근 방식, 모듈 로드맵, 입력→출력 데이터 흐름, 병목 예측, 인터페이스를 정리한다. 구현은 ToT + Guided CoT로 3가지 전략을 비교하고 체크리스트(메모리 정렬·루프 언롤링·캐시 지역성 등)를 적용해 선택안을 구현한다. 리뷰는 Structured CoT + Self-Correction으로 안정성·성능·가독성·비전 도메인 특화 관점에서 분석하고 우선순위와 Before/After 개선안을 낸다.
* **고정 Context와 예제:** 팀의 MFC/C++17/OpenCV 4.x/VS2022, grayscale 16K 이미지, RTX 5090/64GB, Google C++ Style·스마트 포인터·RAII·const reference를 공통 환경으로 정해 템플릿에서 재사용한다. CLAHE에 Plain/OpenMP/CUDA 세 전략을 비교하는 구현 요청, 16K 결함 검출 파이프라인 설계, `SaveImage(cv::Mat img, ...)`의 값 복사·`fopen/fclose` 사용을 지적하는 코드 리뷰가 구체 사례다.
* **Polished Output Trap과 AI Fluency:** 결과물이 매끄럽고 잘 포맷되어 있어도 검증된 결과로 착각하지 말라고 한다. 판단(논리·빠진 맥락·API 사실 확인), 위임(코드 전에 설계 협의, 컨벤션 준수), 반복(초안을 그대로 복사하지 않고 피드백으로 다듬기)을 점검 항목으로 든다.
* **지시→검증→개선 루프:** 16K Sobel 필터 코드에 buffer 재사용·parallel\_for\_·성능 측정을 요청한 뒤, 매 호출 할당 여부·약 512MB 이미지 고려·병렬 범위·empty Mat 오류 처리·컴파일/실행 가능성을 검사하고, 발견한 구체 문제를 다시 지시해 수정한다. 수업은 1회차와 3회차 품질을 각각 70%, 95%로 표시하지만, 이는 자료에 실린 예시 점수이며 측정 방법이나 독립 검증 결과는 함께 제시되지 않는다.
* **실습 구성:** 같은 코드를 모호한 요청과 네 요소 요청으로 비교하고, 같은 리뷰 코드를 Zero-Shot→Few-Shot→Guided CoT로 검토해 이슈 수와 유용성을 살핀다. 이어 설계·구현·리뷰용 템플릿 중 하나를 실무 코드에 적용하고, 2\~3회 개선 결과를 PR에 비교 첨부하는 과제를 준다.

### 실질적 결론

이 모듈은 프롬프트 엔지니어링을 **요청 구조화 + 작업에 맞는 기법 선택 + 팀 템플릿화 + 검증과 반복 개선**의 묶음으로 가르친다. 좋은 프롬프트를 마법 문구로 보지 않고 업무 맥락·제약·결과 형식을 주는 출발점으로 삼는다. Zero-Shot은 단순 작업, Few-Shot은 예시 패턴, Guided CoT는 복잡한 점검 목록, ToT는 대안 선택에 배치한다. 그 뒤 생성 결과의 누락·오류를 직접 확인하고 구체적인 피드백을 주는 검증 루프를 핵심 습관으로 둔다.

## M3\. 리서치·보고서 작성

### 실제로 다루는 내용

* 레거시 리서치의 병목을 조사 시간, 자료 과부하, 연구자 피로로 나누고 수작업 스크리닝과 AI 필터링을 비교한다. 슬라이드에 나오는 “몇 주에서 몇 시간”, 70–80% 필터링 등은 출처·측정 조건이 제시되지 않은 강의 사례값이다.
* 조사 프롬프트에는 독자(예: WSI 광학/소프트웨어 팀), 조사 목적, 질문, 비교 대상, 평가 기준, 원하는 출력 형식을 명시한다. OpenCV·Halcon·Cognex VisionPro·Aurora 비교 예시는 die alignment 시간, subpixel 정확도, C++/MFC 통합, 200대 장비 기준 런타임 라이선스, GPU 가속 등을 축으로 둔다. 예시 성능값은 견적/실측이 아니라 초안이며 라이선스는 “확인 필요”로 두도록 되어 있다.
* 논문·기술문서 요약은 대상 독자와 사용 목적에 맞춰 광학 구성, 검출 알고리즘, 검사 성능 같은 항목으로 나눈다. KLA Surfscan SP7 공개 문서 사례에서 정량 사양, 벤치마크 기준, 구현 난이도를 요약하되 수치는 공개 원문·SEMI 자료·논문으로 교차 확인하도록 한다.
* 경쟁사 벤치마킹은 직접 비교할 2–3개 업체와 5–7개 기준을 먼저 정한다. KLA·Onto·Camtek 또는 KLA·Hitachi·SCREEN 사례에서 광학 방식, 처리량(WPH), 결함 감도, AI/소프트웨어, 패키지/공정 범위, 가격을 표로 비교하고, 확인되지 않은 칸은 임의로 채우지 않고 “확인 필요”로 둔다. 목적은 기술 격차와 차별화 요소를 찾는 것이며 공개 자료·전시회·세일즈 정보를 함께 확인한다.
* 보고서는 전체 목차와 논리 구조를 먼저 잡고, 섹션별 초안을 만든 뒤 하나로 통합·검토한다. WSI 보고서 예시는 visible bright-field, bright-field+dark-field, UV+visible 같은 광학 대안을 비교하며, CTO·기술위원 독자가 결정을 내리는 데 필요한 결론과 근거를 앞세운다.
* RISEN 프레임워크를 포함한 재사용 템플릿을 소개한다. 템플릿은 기술 동향 조사, 기술 도입 판단, 논문/문서 선별, 기술 비교를 다루며, 프롬프트 라이브러리에 메타데이터·버전·분기별 리뷰를 붙여 재사용하려는 구성이다.

### 실질적 결론

AI는 자료 선별·요약·초안 작성을 도울 수 있지만 출처의 신뢰성·최신성·저작권·기밀성 판단과 기술 도입 결론을 대신하지 않는다. 보고서는 AI가 그럴듯하게 쓴 문장보다 추적 가능한 원자료와 검증된 비교 기준에 기대야 한다.

## M4\. 요구사항·아키텍처·ADR

### 실제로 다루는 내용

* 요구를 기능·비기능·인터페이스·제약·리스크 항목으로 나누고, 사용자·장비·운영자에게서 빠진 요구를 찾는다. 검수 시스템 예시는 “불량 검출” 같은 막연한 요구를 측정 가능한 완료 조건으로 바꾸며, Given/When/Then 형식으로 수용 기준을 적는다.
* 3,000줄 `CRecipeDlg` God Class 사례를 Editor, Validator, Storage, Loader, VersionMgr 책임으로 나누고 인터페이스·의존성을 정리한다. 한 번에 전면 재작성하기보다 기존 동작을 보존하면서 단계별 이관과 테스트를 계획한다.
* MFC/C++와 개발자 5명이라는 제약 아래 모놀리식, DLL 모듈, 별도 프로세스의 장단점을 비교하고, 강의 사례는 DLL 경계를 추천한다. MFC에서 WPF/Qt로 50개 화면·200대 장비를 전환하는 예시는 라이선스, TCO, 마이그레이션 위험, 양산 호환성을 따져 전환 시점을 결정하게 한다.
* UI, 하드웨어 제어, 알고리즘의 세 스레드 역할을 나누고, bounded queue(예: 3 슬롯), back-pressure, 제어 신호와 종료 순서를 설계한다. 단순히 스레드를 늘리는 것이 아니라 데이터 전달·정지·정리 순서를 명시하는 사례다.
* ADR의 다섯 항목(Status, Context, Decision, Alternatives, Consequences)을 설명하고, 100ms 이내 불량 판정 Pipeline 예시에서 후보 대안과 탈락 이유, 선택의 긍정·부정 결과를 기록한다. ADR은 `docs/adr` 등 저장소에서 버전 관리하고, AI 초안의 기술적 타당성을 검토한다.

### 실질적 결론

AI의 역할은 구조 개선안과 대안·ADR 초안을 만드는 것이다. 요구의 의미, 안전성, 운영 가능한 설계인지는 담당자와 팀이 판단해야 하며, AI가 낸 큰 설계를 통째로 채택하기보다 실제 코드에서 작은 경계를 바꾸고 빌드·회귀 테스트로 확인해야 한다.

## M5\. 코딩·리뷰

### 실제로 다루는 내용

* 함수 단위 코드 생성 실습은 `LoadImage → Calibrate → Enhance → ExtractROI` 파이프라인으로 구성한다. 각 함수의 입력·출력·실패 조건과 계약을 정하고, 16-bit 16K 이미지가 약 512MB를 차지하는 예에서 메모리 한도(예: 4GB)와 요청당 처리 목표(예: 500ms)를 함께 준다.
* 함수별 개선 후보로 remap 테이블 캐싱, 버퍼 재사용, ROI 병렬 처리를 다룬다. 캐시 유효성·메모리 소유권·실패 시 반환값을 검토하고, 제안 코드가 실제 제약을 만족하는지 측정한다.
* C 스타일 `malloc`/`goto` 코드를 C++17 RAII와 `cv::Mat` 기반으로 바꾸되, 한 번에 여러 개념을 바꾸지 않고 작은 단계마다 같은 입력으로 출력 비교와 회귀 검증을 한다.
* 프로파일링 예시는 전체 3.2초에서 400ms로 줄일 수 있다는 예상과 단계별 절감표를 제시한다. 이는 강의의 추정/예상치로 표시하고, 측정 장비·입력·반복 횟수에 따른 실측 결과로 오해하지 않도록 한다.
* PR 리뷰는 AI가 패턴 문제를 찾아도 비즈니스 로직, 실제 장비 타이밍, 동작 보존을 보증하지 않는다고 설명한다. Load/Calibrate/Enhance/Detect/Save의 5단계 통합 파이프라인 사례에서 공유 변수 문제를 중대 이슈로 지적하고, 수정 후 재검토하는 시연을 둔다.

### 실질적 결론

코드가 생성되었다는 사실은 요구 충족이나 성능 개선의 증거가 아니다. 작은 변경마다 빌드·테스트·diff와 측정을 확인해야 하고, 동작 보존·양산 반영·릴리스 승인 책임은 개발자와 리뷰어에게 남는다.

## M6\. 테스트·디버깅·문서화

### 실제로 다루는 내용

* 테스트 대상을 영향도·변경 빈도·복잡도·실패 위험으로 고른 뒤 단위·통합·종단간(E2E) 테스트를 구분한다. Recipe 시스템에서 파서·검증기 단위 테스트와 카메라/검사 파이프라인 통합 테스트를 연결하는 예를 든다.
* 정상·경계·오류 입력을 모두 고려한다. 이미지 사례는 1×1, 최대 크기, 비정사각형 16K, 빈 `Mat`, RGBA, float64를 포함하고, XML Recipe는 빈 파일·잘못된 형식·누락 필드를 포함한다. Google Test/Mock과 명시적 assertion으로 기대 결과를 검증한다.
* 디버깅 프롬프트에 증상, 환경, 발생 상황, 최근 변경을 제공하고, AI가 원인 가설 3개와 이를 확인할 로그·실험·코드, 수정안, 영향 범위, 재발 방지책을 제안하게 한다. 예시는 약 512MB 이미지의 누수, GDI 객체 증가, 이벤트/callback 수명 문제, 24시간 연속 실행을 다룬다.
* 문서는 독자와 범위를 먼저 정하고 설치→설정→실행→문제 해결→업데이트 순으로 구성한다. 10개 빈발 이슈를 FAQ/트러블슈팅으로 넣고 실제 장비에서 절차와 화면을 확인하는 것이 중요하다고 한다.
* 출력물별 검증을 두며, 항상 참이 되는 무의미한 assertion은 테스트가 있어 보이는 것과 실제 검증의 차이를 보여주는 반례로 든다. PR 체크리스트에는 추가된 테스트, 실행 결과, 문서 변경, AI 활용 내역과 사람 리뷰어를 연결한다. AI 생성 테스트에는 수정이 필요한 경우가 많다는 20–30% 수치도 나오지만, 측정 근거가 제시된 일반값은 아니다.

### 실질적 결론

AI가 낸 원인 설명은 증거가 아니다. 테스트 범위와 릴리스 승인, 장애 대응은 조직의 책임이며, 실제 장비·현장 절차와 맞지 않는 자동 생성 매뉴얼은 위험할 수 있다. 실행 가능한 검증과 사람이 확인한 운영 사실을 기준으로 닫아야 한다.

## M7\. 개발자 학습 가속화

### 실제로 다루는 내용

* 질문을 “무엇인가→어떻게 쓰나→왜 이런 선택을 하나”로 깊게 하고, 개념 설명→작동 예제→조건을 바꾼 변형 문제 순으로 학습한다. OpenCV `parallel_for_`를 TensorRT 실행 엔진의 작업 흐름에 대응시켜 기존 지식과 새 개념을 연결한다.
* 새 기술 학습은 핵심 개념 5개를 먼저 뽑고, 이미 아는 기술과의 비유/차이를 만들고, 도메인에서 실행할 수 있는 예제를 만들고, 로컬 환경별 빌드 안내를 작성하는 4단계로 제시한다. TensorRT 예시는 OpenCV의 `imread`/`Mat`/`filter2D` 흐름과 GPU buffer/Engine 실행/float 출력 흐름을 비교한다.
* 컴파일 오류는 메시지 해석→원인→수정→다음에 피할 습관으로 설명한다. C2784의 vector<Mat>와 Mat 타입 불일치, C2679의 cv::Mat 출력 문제 등에서 코드·컴파일러·환경·재현 조건·이미 시도한 방법을 프롬프트에 넣게 한다.
* 온보딩 자료는 코드 구조, 클래스 관계/호출 흐름, 먼저 볼 파일, 빌드·실행 단계, 사내 용어집을 생성한 뒤 시니어가 실제 저장소와 맞는지 검토하고 새 질문을 반영해 갱신하는 흐름이다. AI 도움의 성숙도를 1–4단계로 나눠 사용법을 진전시키는 도식도 있다.
* “2–3배 빠른 학습”, 800페이지 문서 대비 75분, 온보딩 3개월에서 1/3 등은 슬라이드의 효과 주장으로만 다룬다. 학습자 수준·기술·환경별 측정 방법이 제시되지 않아 일반 성과로 보증할 수 없다.

### 실질적 결론

학습 목표는 답을 빨리 복사하는 것이 아니라 학습자가 설명하고 적용하고 검증할 수 있게 되는 것이다. AI가 학습이나 온보딩 시간을 일정 비율 단축한다는 수치는 실제 팀의 전후 측정 없이 보장된 성과로 받아들이지 않는다.

## M8\. 업무 자동화 및 생산성 측정

### 실제로 다루는 내용

* 먼저 반복성과 정형성을 두 축으로 업무를 분류한다. 반복성·정형성이 모두 높은 빌드 스크립트와 단위 테스트는 즉시 자동화 후보, 반복성은 낮지만 정형적인 Visual Studio 프로젝트 설정은 템플릿/도구 후보, 반복되지만 맥락이 다른 코드 리뷰·문서화는 AI 초안·체크리스트 보조 후보, 반복성과 정형성이 모두 낮은 장비 현장 대응은 사람 중심으로 남기는 식이다.
* 자동화 우선순위 기준으로 빈도(주 3회 이상), 회당 시간(30분 이상), 오류율, 다른 업무의 병목이 되는 의존성을 제시한다. SDK/OpenCV 버전 업그레이드 호환성 시험, 정적 분석, 빌드 실패로 팀이 대기하는 상황을 예로 들고, 기준에 맞는 일상 업무를 골라보게 한다.
* 비전 시스템의 3계층 구조(하드웨어 종속 Driver/SDK, 중간의 HAL, 상단의 검사 로직과 UI)를 설명한다. HAL에서 ICamera·IGrabber 같은 공통 인터페이스를 분리하면 장비별 구현을 갈아 끼우기 쉽고 반복 구현은 AI 생성 후보가 될 수 있다는 논리다. 생성은 인터페이스·빌드·테스트 경계 안에서 검증해야 한다.
* 자동화 단위를 인터페이스로 나누고, 빌드·테스트·경고·링크 등 단계별 확인을 붙여 CI/CD로 연결하는 예를 둔다. 자동화 실패 시 중단하고 사람이 확인할 지점과 버전 관리·재현 가능성을 다룬다.
* 생산성 지표로 커밋 수·코드량만 보는 문제를 짚고 SPACE의 만족도·성과·활동·협업/커뮤니케이션·효율/몰입과 DORA의 전달 속도·안정성을 소개한다. 자료는 개인 관점에는 SPACE, 팀 전달 성과에는 DORA를 적용하는 구성을 제안하고, 지표는 팀의 현재 상태와 병목을 개선하는 나침반으로 써야지 팀 간 경쟁·개인 불이익의 도구로 쓰지 말라고 한다.
* 슬라이드 5 차트의 개발자 업무 시간 배분 값은 문서화/설계 논의 8, 배포/모니터링 8, 보안 점검 13, 코드 리뷰/유지보수 12, CI/CD/빌드 관리 12, 요구사항/테스트 케이스 14, 코드 작성/개발 16, 디버깅/트러블슈팅 17이다. 첫 번째 내장 Excel 시트에도 같은 값이 들어 있다.
* 같은 차트의 AI 자동화 절감 효과 값은 문서화/설계 논의 30, 배포/모니터링 50, 보안 점검 20, 코드 리뷰/유지보수 35, CI/CD/빌드 관리 45, 요구사항/테스트 케이스 40, 코드 작성/개발 55, 디버깅/트러블슈팅 30이다. 두 번째 내장 Excel 시트에도 동일하게 기록되어 있다.
* 발표자 노트는 첫 차트의 출처를 IDC 2024 조사, 절감 효과 차트를 GitHub Copilot 생산성 연구에 기반한 추정으로 설명한다. 노트는 실제 코딩 시간은 16%, 디버깅/트러블슈팅은 17%라고 읽으며, AI 절감치 예로 코드 작성 55%, CI/CD 45%, 배포 50%, 보안 점검 20%를 언급한다.
* 자동화 성숙도를 AI 도입 전후 비교와 수동 작업의 자동화 정도로 살피되, 정량 지표와 정성 지표를 같이 두라고 한다. 노트가 제안하는 개인·팀 KPI는 SPACE와 DORA를 참고하고, 복잡한 문제 해결·팀 코드 리뷰·자기주도 학습도 함께 보는 방식이다.

### 실질적 결론

자동화는 반복성·정형성·빈도·시간·오류·의존성에 근거해 후보를 선정하고, 인터페이스와 테스트 경계 안에 작게 넣는 방식으로 소개된다. 생산성은 코드량 하나로 환원하지 말고 개인의 만족·협업과 팀의 전달 속도·안정성을 함께 보며, 수치가 사람을 감시하거나 게임화하는 목표가 되지 않도록 하라는 내용이다.

### 차트와 삽입 파일에 대한 확인 한계

차트 캐시 데이터와 두 내장 Excel 파일의 셀을 확인했으며 값은 서로 일치한다. 다만 발표자 노트가 IDC 2024 및 GitHub Copilot 연구를 출처로 지칭할 뿐, 이 PPT 추출물에는 원문 인용·조사 조건·산식이 함께 들어 있지 않다. 따라서 이 수치들은 자료에 적힌 주장으로 보고, 현재 조직의 성과 예측이나 독립 검증된 일반값으로 사용하지 않는다.

## M9\. 시스템 설계 및 기술 의사결정 지원

### 실제로 다루는 내용

* 시스템 설계를 요구사항→제약→복수 대안→추천 근거→점진적 전환 계획으로 구성한다. 예시는 65인치 Cell, 세 종류 모델, Tact 6초, 16K 영상, MFC/C++ 10만 줄, 개발자 5명, 양산 장비 200대, RTX 5090/64GB, 12개월 출시를 제약으로 둔다.
* 설계 대안은 최소 세 가지로 만들고 현행 유지도 비교에 넣는다. 성능·확장성·리스크·마이그레이션·구축 기간을 기준으로 비교하며 총소유비용(TCO)에 초기 구축뿐 아니라 3년 운영과 전환·학습·양산 검증 비용을 포함한다.
* 16K 이미지 저장에서 로컬 NVMe SSD, 10GbE NAS, PostgreSQL BLOB를 비교한다. 강의 예시의 추천은 실시간 저장은 SSD, 검사 후 NAS로 비동기 전송, DB에는 메타데이터 저장하는 하이브리드 접근이다. 실제 채택 전에는 용량·속도·비용을 실측과 견적으로 확인하도록 한다.
* “검출 정확도 99.9%” 같은 사업 목표를 Recall·오검출률(FP)·해상도·추론 속도 등 기술 KPI로 분해하고, 현재값과 목표 간격, 개선 요소, 우선순위와 절충 관계를 정리한다. 예시에서는 Recall 상승이 FP 상승으로 이어질 수 있고 해상도 상승은 처리 시간에 영향을 줄 수 있다고 설명한다.
* R&D 후보에 ICE(Impact × Confidence × Ease) 점수를 붙여 토론을 구조화한다. 딥러닝 결함 분류(9×7×6=378), 16K 처리 최적화(7×9×5=315), 자동 레시피 튜닝(8×4×3=96), 다중 카메라 동기화(5×8×4=160), 클라우드 원격 모니터링(6×3×2=36) 사례의 점수와 근거를 표로 비교한다.
* 점수는 초안으로 취급하고 가중치 변경, 팀 역량, 시장 시점, 고객 전략을 반영해 사람이 순위를 결정한다. 결정은 ADR에 기록하고 3개월 또는 분기별로 재평가하도록 제안한다.

### 자료 안의 수치·정렬 불일치

R&D 우선순위 표는 다중 카메라 동기화 점수 160을 4위, 자동 레시피 튜닝 점수 96을 3위로 표시한다. 표의 정렬 설명이 `I×C×E` 내림차순이라면 두 항목의 순위가 뒤바뀌어 있다. 계산값과 최종 정렬을 함께 대조해야 하는 사례다.

### 실질적 결론

AI는 복수 대안과 비교표, KPI 분해와 우선순위 초안을 만들어 의사결정의 시작 비용을 낮춘다. 제약과 비교 기준을 사람이 제공하지 않으면 일반론이나 실행 불가능한 설계가 나오기 쉽다. 최종 설계·예산·우선순위 결정은 사람의 책임이며, AI가 제시한 정량치와 견적은 실제 측정·견적·조직 맥락으로 확인해야 한다.

## 추출 범위 및 확인이 남은 요소

* 확인 범위: 원본별 Markdown 추출물의 슬라이드 텍스트·표·발표자 노트와 모듈별 `content-curation.md`. 이 문서에는 그 내용을 업무 개념과 사례 단위로 재구성했다. M8의 차트 값과 내장 Excel 2개 시트의 표 값도 서로 대조했다.
* 전체 목록: `00. AI 적용 분야` 1장, M1 15장, M2 24장, M3 31장, M4 30장, M5 29장, M6 29장, M7 24장, M8 21장, M9 23장.
* 숫자·시간 절감률·기술 비교는 원본 강의에 적힌 사례값이며, 이 문서에서 독립적으로 사실 검증한 수치가 아니다.
* 원본 도식 렌더와 이미지의 시각 정보는 모든 장에 대해 장별로 재판독하지 않았다. 텍스트 추출에 표시된 주요 도식은 본문 설명과 모듈 분류 자료를 함께 사용했다. M8 차트 데이터와 내장 Excel의 값은 확인했으나, 차트 출처의 외부 원문·조사 방법은 이 PPTX에 없어 별도 검증하지 않았다.
* 슬라이드별 텍스트·표·노트 원문은 각 모듈 폴더의 개별 Markdown 추출물을 기준 자료로 사용한다. 이 파일은 원문 전사본이 아니라 내용을 이해하기 위한 실질 내용 요약이다.
