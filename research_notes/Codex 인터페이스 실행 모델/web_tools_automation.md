# Web Search, Tools, and Automation — STEP 03 §§28–30

**Checked:** 2026-09-25 (Asia/Seoul)  
**Scope:** Current documented OpenAI/Codex behavior, plus clearly labeled teaching inferences.  
**Confidence:** High for explicitly documented surfaces, controls, and integrations; medium for recommendations derived from them.  
**Volatility:** High. Product names, supported surfaces, availability, and admin controls are changing quickly. Recheck official docs before using product-specific claims in slides or a demo. OpenAI’s current product documentation is served from `learn.chatgpt.com` (some `developers.openai.com` pages redirect there).

## Web / Search / External Knowledge

### Takeaway

Codex can research external information through its built-in Web Search in local Codex chats, CLI, and IDE extension, but search mode and network access are separate controls. Search output is evidence to inspect, not authority: use version-matched official documentation, record source/version, and verify any code change in the target repository. ChatGPT explicitly presents web citations; current Codex docs document search activity in the transcript but do not promise that every Codex answer will include complete citations.

### Cited Findings

- **Codex local surfaces:** Local Codex chats use cached Web Search by default. CLI users can use `codex --search` for live search; searches appear as `web_search` items in the interactive transcript and `codex exec --json` output. The IDE extension uses the connected Codex host’s configured search mode and displays search activity in its transcript. [Web search in ChatGPT and Codex](https://learn.chatgpt.com/docs/web-search)
- Codex documents four modes: `cached` (default; OpenAI-maintained pre-indexed results), `indexed` (the search index gates external access), `live` (fetches current web data), and `disabled`. Cached mode lowers, but does not eliminate, prompt-injection risk. Full-access Codex runs default Web Search to live results; the configured mode and managed workspace restrictions can affect behavior. [Config basics](https://learn.chatgpt.com/docs/config-file/config-basic), [Web search in ChatGPT and Codex](https://learn.chatgpt.com/docs/web-search)
- The Web Search tool is hosted separately from sandboxed local command networking. Local Web Search does not use the permission profile’s network proxy or domain allowlist, and it can remain available when command network access is disabled. Its domain filter affects search only; it does not restrict shell traffic, apps, connectors, or MCP servers. [Web search in ChatGPT and Codex](https://learn.chatgpt.com/docs/web-search)
- Codex Cloud’s *agent internet access* controls a different path: agent-phase internet is blocked by default, setup scripts still have internet access, and an environment can be configured to allow agent internet access. The docs warn about prompt injection, exfiltration, malicious/vulnerable downloads, and license-restricted content, and recommend limiting domains/methods and reviewing the work log. [Agent internet access for Codex Cloud](https://learn.chatgpt.com/docs/cloud/internet-access)
- In ChatGPT web, search results and citations appear in the chat when Web Search is used; ChatGPT desktop logs search with other tool calls. The Codex documentation specifically promises transcript/activity records, not complete inline source citations. For API-built agents, Responses API Web Search can return sourced citations and a `sources` field containing the URLs consulted; the latter can be more complete than inline citations. [Web search in ChatGPT and Codex](https://learn.chatgpt.com/docs/web-search), [Web Search API guide](https://developers.openai.com/api/docs/guides/tools-web-search)
- OpenAI hosts a read-only OpenAI Docs MCP server for searching and reading documentation from `developers.openai.com`, `platform.openai.com`, and `learn.chatgpt.com`. Codex can add it by MCP configuration/CLI; the same MCP configuration is shared by Codex CLI and IDE extension on the same host. This is a path for current *OpenAI* docs, not a general-purpose substitute for all vendor documentation. [OpenAI Docs MCP](https://learn.chatgpt.com/learn/docs-mcp)
- OpenAI’s API Web Search tool supports domain filters (including allowed domains), and Codex’s local search configuration exposes `tools.web_search.allowed_domains` plus managed `allowed_web_search_modes`. A prompt can therefore request or configure official-domain-restricted research, subject to the actual host and workspace settings. [Web Search API guide](https://developers.openai.com/api/docs/guides/tools-web-search), [Web search in ChatGPT and Codex](https://learn.chatgpt.com/docs/web-search)
- OpenAI warns that Web Search and remote MCP results are untrusted and can carry prompt injection. Its agent-building guidance recommends trusted MCP servers, logging/reviewing tool calls, checking URLs, and adding validation/approval controls when external data can lead to actions. [Deep Research safety guidance](https://developers.openai.com/api/docs/guides/deep-research), [MCP server guide](https://developers.openai.com/api/docs/guides/tools-connectors-mcp)
- OpenAI’s glossary defines Codex **Context** to include files, previous messages, tool output, and instructions. The Responses API MCP guide likewise states that a server’s returned output is placed in the model’s context as an `mcp_call` item. [ChatGPT and Codex glossary](https://learn.chatgpt.com/docs/glossary), [MCP servers for the Responses API](https://developers.openai.com/api/docs/guides/tools-connectors-mcp)

### Inferences

- For current API/library behavior, a reliable research-first sequence is: name the product/library and version; search its official version-matched docs/release notes; record the exact source URL and date; compare with the repository’s lockfile, declared version, local wrappers, and current implementation; then run a small repository-level check before editing broadly. This is a teaching recommendation derived from live/cached mode controls, source-result visibility, and the fact that repository files and external tool output both enter context. It is not an automatic Codex conflict-resolution feature.
- When repository instructions, actual repository behavior, and external documentation disagree, state what each source establishes rather than silently choosing a winner. Use repository state to answer “what this project currently does”; use version-matched official docs to answer “what this version is documented to do”; use a reproducible test or ask the maintainer when they conflict about intended behavior. This recommendation is not an OpenAI product rule.
- “모르면 AI에게 먼저 조사시키자” is accurate when expressed with bounds: ask the agent to search an enabled/accessibly configured source, prefer primary and version-matched documentation, return links and uncertainty, and pause before code changes if sources conflict or the behavior cannot be reproduced. It does not mean the model always searches, always finds the right source, or verifies its own research correctly.
- Treat search output as context from an untrusted external party. An official source is stronger evidence for documented product/API behavior than a random page, but it does not prove the installed version, workspace configuration, or repository actually matches that documentation.

### Gaps

- The current Codex search page clearly specifies local chats, CLI, and IDE behavior. Codex Cloud documentation separately specifies environment internet access, but the reviewed pages do not clearly promise that Cloud tasks expose identical local `web_search` modes, citations, or domain filters. Verify the exact target surface before demonstrating this.
- The Codex product documentation does not promise full inline citations or a complete source ledger for every answer. If source traceability is a requirement, make source URLs/date/version an explicit deliverable and inspect the transcript; do not infer full provenance from seeing a search activity item.
- The linked historical Help Center article for the 2023-era “ChatGPT plugins beta” no longer resolves. The current “Plugins” product is documented separately below; no historical deprecation date is asserted here.

## Tools / MCP / Plugins

### Takeaway

MCP is a supported way to connect Codex to external tools and context; Plugins are installable workflow packages that may bundle skills, MCP connections, hooks, and UI. Neither a plugin install nor an MCP server grants blanket access: workspace availability, external-service authentication/scopes, action policy, and the active Codex host’s sandbox/approval policy all matter. Tool outputs become model context, so both their usefulness and their injection/data-handling risks matter.

### Cited Findings

- Codex supports MCP. The ChatGPT desktop app, Codex CLI, and IDE extension support MCP servers and share MCP configuration for the same Codex host. The documented local server types include local-process STDIO and Streamable HTTP (with bearer-token or OAuth authentication); hosted ChatGPT Work can use remote MCP tools supplied through plugins. [MCP in Codex and ChatGPT](https://learn.chatgpt.com/docs/extend/mcp)
- A private/on-premises MCP server can be reached through OpenAI’s Secure MCP Tunnel without exposing the MCP server publicly; the tunnel client makes outbound HTTPS connections and forwards requests locally. [Secure MCP Tunnel](https://developers.openai.com/api/docs/guides/secure-mcp-tunnels)
- The current OpenAI **Plugins** directory is a universal directory shared by ChatGPT and Codex on supported surfaces. A plugin can bundle Skills, MCP servers/connectors, and optional UI; Codex plugins can also bundle lifecycle hooks. Current Help says plugins are available in ChatGPT web/desktop/mobile, Codex desktop, and Codex CLI, but **not** in the IDE extension. Availability is surface-, plan-, workspace-, role-, and plugin-dependent. [Plugins](https://learn.chatgpt.com/docs/plugins), [Plugins in ChatGPT and Codex](https://help.openai.com/en/articles/20001256-plugins-in-chatgpt-and-codex)
- Current product terminology separates an **app/connector** (the link to an external service) from a **plugin** (a package that can contain one or more apps/connectors and skills). Installing a plugin does not itself complete authentication or grant access to the connected service. [Plugins in ChatGPT and Codex](https://help.openai.com/en/articles/20001256-plugins-in-chatgpt-and-codex)
- “Codex tools” is broader than plugin packaging: the runtime can use built-in capabilities such as shell and Web Search, configured MCP tools, and product-specific integrations. MCP exposes named functions/resources; Plugins package and distribute capabilities. This distinction follows the separate Codex MCP, Plugins, and API MCP documentation. [MCP in Codex and ChatGPT](https://learn.chatgpt.com/docs/extend/mcp), [Plugins](https://learn.chatgpt.com/docs/plugins), [MCP servers for the Responses API](https://developers.openai.com/api/docs/guides/tools-connectors-mcp)
- The current package called **Plugins** must not be conflated with the older “ChatGPT Plugins” beta terminology. Current OpenAI docs describe a new installable package/universal directory for ChatGPT and Codex; the retired Help Center page for the historical beta is no longer available at its former URL, so this note does not assert the beta’s full timeline or technical migration details. [Current Plugins documentation](https://learn.chatgpt.com/docs/plugins)
- Concrete current examples include GitHub for issue/PR/CI workflows; Linear for delegating an issue or `@Codex` comment to a Codex Cloud chat; GitHub/GitLab integrations for PR/MR code review; Google Drive/Notion for documents/knowledge; browser and web-search tools for public web context; and CircleCI or other installable integrations shown in the plugin directory. This is an availability snapshot, not a guarantee that a particular user/workspace has each integration enabled. [Plugins directory](https://learn.chatgpt.com/docs/plugins), [Codex in Linear](https://learn.chatgpt.com/docs/third-party/linear), [GitHub code review](https://learn.chatgpt.com/docs/third-party/github), [GitLab code review](https://learn.chatgpt.com/docs/third-party/gitlab)
- The MCP protocol is extensible: a trusted MCP server can expose tools for internal services or databases. The reviewed product docs do not imply that Codex has automatic/direct access to arbitrary databases or company systems; access exists only if an applicable connector/MCP server is configured and authorized. Private servers can use Secure MCP Tunnel. [MCP in Codex and ChatGPT](https://learn.chatgpt.com/docs/extend/mcp), [Secure MCP Tunnel](https://developers.openai.com/api/docs/guides/secure-mcp-tunnels)
- Permission is layered. Workspace controls determine whether a plugin/MCP server is available and what actions are allowed; the user/service account’s external-service authorization still limits accessible records/actions; Codex sandbox and approval rules then govern what the runtime can do. Codex MCP config can enable/disable servers and tools and select server-level or per-tool approval behavior (`auto`, `prompt`, `writes`, `approve`). [Plugin controls](https://learn.chatgpt.com/docs/enterprise/apps-and-connectors), [Codex configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference), [Plugins in ChatGPT and Codex](https://help.openai.com/en/articles/20001256-plugins-in-chatgpt-and-codex)
- The Responses API separately offers MCP tools with `allowed_tools` and `require_approval` controls; after an MCP call, its returned output is put into model context. OpenAI warns that a malicious or untrusted remote MCP service could exfiltrate sensitive context, and recommends carefully reviewing/limiting servers and approvals. API controls should not be presented as identical to Codex product approval UI. [MCP servers for the Responses API](https://developers.openai.com/api/docs/guides/tools-connectors-mcp)
- OpenAI’s public Docs MCP server is read-only and searches/reads OpenAI documentation; it does not call the API on the user’s behalf. This is a concrete example of “tool gives grounded documentation context without granting write actions.” [OpenAI Docs MCP](https://learn.chatgpt.com/learn/docs-mcp)

### Inferences

- A useful harness model is: **tool protocol/runtime call** (e.g. MCP tool) → **packaging/distribution** (e.g. Plugin) → **workflow instructions** (e.g. Skill) → **identity, action, approval, and sandbox controls**. This is a teaching model, not formal OpenAI terminology.
- Teach least privilege by describing capabilities separately: install/availability, data connection, provider identity/scopes, read/write action set, approval mode, and local/cloud execution permissions. “Plugin installed” is not the same as “all company data accessible.”
- Issue tracking, docs, browser, database, internal service, and CI are possible integration targets, not mandatory Harness components. A custom MCP integration is justified only when it supplies necessary data/actions that the repo, shell, or one existing integration cannot. For a short demo, one read-only external source may demonstrate contextual value; adding a multi-system integration can distract from the Problem → Harness → verification story. This is a design recommendation, not a product fact.
- Require external tool results to carry the source/record URL or stable ID when possible. Since tool output enters context, retain enough provenance to re-open the exact issue/doc/result and validate claims/actions independently.

### Gaps

- Current plugin availability is explicitly surface-specific: the current Help page says plugins are not available in the IDE extension, while an older March 2026 changelog entry described IDE-extension support. Prefer the newer/current Help and Plugins pages for present product behavior; recheck immediately before slide/demo use because the docs and rollout are volatile. [Current Help Center surface availability](https://help.openai.com/en/articles/20001256-plugins-in-chatgpt-and-codex), [March 2026 changelog](https://learn.chatgpt.com/docs/changelog)
- Availability of an actual internal database or company-service connector depends on the organization’s approved MCP/app deployment, identity, network, and data policy. No such company configuration was provided in this research assignment; do not treat the protocol’s technical extensibility as authorization.
- The exact historical distinction/decommission dates for legacy ChatGPT Plugins could not be confirmed from the primary Help Center URL because it currently returns 404. Keep “legacy beta” as a terminology distinction only unless another primary archived source is recovered.

## Automation / Repeated Workflow

### Takeaway

Codex/ChatGPT can reuse Skills, scripts/tools/hooks, delegated tasks, schedules, and CI/event integrations, but these are different mechanisms. Codex desktop supports scheduled work against a local project or isolated worktree; ChatGPT event-triggered Scheduled Tasks currently support specific Gmail, Slack, and GitHub events on web/mobile. GitHub Actions can run Codex on repository events; GitLab integration documents MR code review in beta, not a general-purpose GitLab event-triggered task service. None of these mechanisms by itself is the feedback-driven improvement loop defined by the course.

### Cited Findings

- **A. Reusable instruction — Skills:** A Skill packages task-specific instructions plus optional resources/scripts, can be invoked explicitly or selected when its description matches, and is intended to make recurring workflows more consistent. Skills may be combined with plugins for external tools; a Skill alone is not a scheduler. [Build skills](https://learn.chatgpt.com/docs/build-skills), [Skills & Plugins](https://learn.chatgpt.com/docs/skills-and-plugins)
- **B. Script/tool automation — scripts, MCP, Hooks:** Codex Hooks can run scripts or MCP tools at lifecycle points such as `PreToolUse`, `PostToolUse`, `Stop`, and `SessionEnd`; documented examples include prompt logging, secret-pattern scanning, and validation on turn stop. Non-managed hooks must be reviewed/trusted. Hooks automate a step at a known point; they do not automatically define an evaluation-and-improvement policy. [Hooks](https://learn.chatgpt.com/docs/hooks)
- **C. Agent delegation:** Codex supports subagents for assigning focused parts of a larger task, returning their findings to the parent thread. Delegation partitions work within a task; it does not itself repeat on a schedule or improve the harness. [Codex CLI documentation: subagents](https://developers.openai.com/codex/cli/features)
- **D. Scheduled work in Codex desktop:** Create/manage scheduled tasks from ChatGPT or Codex desktop chat. A scheduled desktop task can work in a local project directory or a dedicated Git worktree. If it needs local files, keep the machine powered on, the app running, and the project on disk. A worktree isolates scheduled changes from unfinished local work; running against the main checkout may modify files in use. Codex CLI and IDE extension do not expose the Scheduled management interface. [Scheduled tasks](https://learn.chatgpt.com/docs/automations)
- Web Scheduled Tasks can use uploaded files, connected tools, Skills, and Plugins available to that chat, but they do not retain a local folder/worktree between runs. A task in an existing chat can return to that chat’s context; a standalone task starts a new chat/run. OpenAI recommends testing the prompt manually and reviewing early scheduled outputs. [Scheduled tasks](https://learn.chatgpt.com/docs/automations)
- **D. Event-triggered Scheduled Tasks:** On eligible plans, ChatGPT web/mobile can run a scheduled task on supported Gmail new-message, Slack new-channel-message, or GitHub pull-request activity events. Triggers and time schedules cannot be combined in one event-triggered task. These ChatGPT event triggers are documented as unavailable in Codex desktop, Codex CLI, and the IDE extension; workspace/admin/app authorization also gates availability. [Scheduled tasks](https://learn.chatgpt.com/docs/automations), [ChatGPT Work and Codex](https://help.openai.com/en/articles/20001275-chatgpt-work-and-codex)
- **GitHub repository event / CI workflow:** The official `openai/codex-action@v1` runs Codex through `codex exec` in GitHub Actions. The documentation shows a PR-triggered workflow (`opened`, `synchronize`, `reopened`), can save outputs and post a review comment, and says permissions/sandbox should be specified. This is an externally configured CI workflow, not a claim that Codex CLI automatically subscribes to arbitrary GitHub events. [Codex GitHub Action](https://learn.chatgpt.com/docs/github-action)
- Codex’s native GitHub integration also supports `@codex` PR tasks, configured automatic code review, and review of diffs in connected Codex Cloud repositories. The GitLab integration documents `@codex review` and automatic merge-request reviews, and labels support beta. These are code-review integrations, not evidence that the ChatGPT Scheduled Task event trigger supports GitLab or arbitrary GitLab events. [GitHub code review](https://learn.chatgpt.com/docs/third-party/github), [GitLab code review](https://learn.chatgpt.com/docs/third-party/gitlab)
- For programmatic Codex jobs/CI, OpenAI’s App Server page says to use the Codex SDK; the Codex GitHub Action is another documented GitHub-specific route. A self-hosted pipeline can connect its own events to a workflow, but that orchestration is configured outside the Codex app. [Codex App Server](https://learn.chatgpt.com/docs/app-server), [Codex GitHub Action](https://learn.chatgpt.com/docs/github-action)
- **E. Feedback-driven improvement:** Codex can run checks, create/edit repository artifacts, use Skills and MCP tools, and scheduled/CI systems can invoke further work. The cited product docs do not establish a built-in, universally safe mechanism that scores outcomes, decides how to rewrite Harness instructions/tools, validates that rewrite, and promotes it without human review. [Codex GitHub Action](https://learn.chatgpt.com/docs/github-action), [Hooks](https://learn.chatgpt.com/docs/hooks), [Scheduled tasks](https://learn.chatgpt.com/docs/automations)
- Scheduled tasks run unattended with their configured/default sandbox and approval settings; if organization policy permits, their approval policy can be `never`. Admin-enforced requirements can restrict approval/sandbox modes. This makes worktree isolation, narrow access, output review, and an explicit stop condition relevant when a scheduled task can change files or use write-capable integrations. [Scheduled tasks](https://learn.chatgpt.com/docs/automations), [Agent approvals and security](https://learn.chatgpt.com/docs/agent-approvals-security)

### Inferences

- Keep the five categories distinct in teaching: **Skill** repeats instructions; **script/tool/hook** automates a defined operation; **delegation** splits a current task; **schedule/event/CI** decides when another run starts; **feedback-driven improvement** evaluates outcomes and deliberately changes the next run’s Harness. The first four can supply machinery for the fifth, but do not constitute it by themselves.
- Automation is not Loop Engineering. A bounded improvement loop needs a comparable target task/evaluation, recorded result or failure, a proposed and reviewable Harness change, rerun against the same or equivalent case, and a decision to keep/revert the change. This is a course-level operational recommendation, not a Codex feature guarantee.
- A realistic repeatable demonstration could use a non-production repository and one known task: run an eval/check, capture a failure, propose a focused Skill/AGENTS/script adjustment, review the diff, rerun the same check, and compare results. A timer or GitHub event can start a run, but the evidence-based evaluation and reviewed Harness edit are what make it a loop. This is a candidate teaching pattern, not a Demo selection.
- A coding agent can edit its own instructions/configuration if those files are in scope and write permission is granted. That technical possibility is not evidence of safe autonomous self-improvement. Keep write access bounded, preserve before/after diffs, evaluate changes, and require human acceptance for wider policy or permission changes.
- The clearest current event-trigger story is surface-specific: ChatGPT web/mobile Scheduled Tasks for supported app events; Codex desktop schedules for local project follow-up; GitHub Action for repository CI; Codex GitHub/GitLab integrations for their documented PR/MR review workflows. This is more accurate than teaching “Codex watches any repo event” as a general capability.

### Gaps

- Product availability, supported plans, admin switches, and event types are subject to rollout changes. Recheck the Scheduled Tasks and GitHub/GitLab integration docs immediately before a demo.
- The reviewed material documents GitLab **MR review** beta behavior but does not document general Codex scheduled-task triggers for arbitrary GitLab events. Do not claim native GitLab webhooks for general Codex work from this evidence.
- Product docs expose schedules, Skills, hooks, CI runners, and check/eval mechanisms as separate parts. They do not document an out-of-the-box end-to-end self-modifying Harness loop with guaranteed quality or safety; any such workflow would require external orchestration, explicit evaluation, permissions, rollback/review, and organization policy.
- No company CI system, GitLab settings, permitted integrations, data classification, or evaluation criteria were supplied. These are organizational deployment decisions, not facts inferable from OpenAI product docs.
