# Cost, Complexity, and Minimum Effective Harness

조사 기준일: 2026-09-25. STEP 03 §§48–50 범위의 근거 노트다. 목적은 Prompt → Context → Harness → Loop로 갈수록 얻는 이점뿐 아니라 token/context/tool-call 비용, latency, coordination, 유지보수, eval 비용, overengineering 위험을 확인하는 것이다. 이 노트는 Demo를 선택하지 않고, 보편 threshold를 만들지 않는다. “Minimum Effective Harness”는 evidence-based universal taxonomy가 아니라 관찰된 Failure/Friction에 대응해 최소 구조를 추가한다는 교육용 heuristic으로만 다룬다.

## 비용과 latency는 어디서 발생하는가?

### Takeaway

Agent 비용은 단일 model call이 아니라 root agent와 subagent의 여러 model calls, input/output/reasoning tokens, tool definitions, conversation history, tool results, retries, sandbox compute, third-party service charges가 합쳐진 결과다. Latency도 token generation, request count, model choice, parallelism, tool calls, cache behavior의 함수이며, 구조를 늘리면 일부 latency는 줄어도 token/coordination/maintenance 비용이 늘 수 있다.

### Cited Findings

- OpenAI Agents API observability docs say an agent may make several model calls to complete a task, and each model call can consume input tokens, cached input tokens, output tokens, and reasoning tokens. Input tokens include agent instructions, tool definitions, conversation history, user input, files/images, and tool results; subagents also make model calls and their usage should be inspected with root-agent work. The same docs say to account for retries, tool, sandbox compute, and third-party service charges, and to compare cost at the quality/latency needed. Scope: Agents API usage accounting; not a universal Codex Desktop bill. Confidence: HIGH. Volatility: MEDIUM-HIGH. — [Observability and usage](https://developers.openai.com/api/docs/guides/agents-api/observability)
- OpenAI observability docs say recorded usage can be `null`, can change as accounting arrives, and is not the final bill. Cached tokens are still included in input tokens, and reasoning tokens are included in output tokens. Scope: Agents API usage records. Limitation: best-effort accounting, not final invoice. Confidence: HIGH. Volatility: MEDIUM. — [Observability and usage](https://developers.openai.com/api/docs/guides/agents-api/observability)
- OpenAI prompt caching docs say prompt caching reuses matching prompt prefixes, can reduce latency and input-token cost on cache hits, and is enabled by default for supported models. For GPT-5.6 and later, minimum cacheable prompt length is 1,024 tokens and cache writes cost 1.25x the standard uncached input-token rate while subsequent reads cost 0.1x that rate. It also says maintaining a session does not guarantee a cache hit. Scope: OpenAI API prompt caching behavior. Confidence: HIGH. Volatility: HIGH for model-specific pricing and cache rules. — [Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)
- OpenAI latency guide says generating tokens is almost always the highest latency step, and as a heuristic cutting 50% of output tokens may cut about 50% of latency. It also says reducing input tokens does reduce latency but is “not usually a significant factor”; cutting 50% of the prompt may yield only a 1–5% latency improvement unless contexts are massive. Scope: broad LLM application latency guidance. Confidence: HIGH for heuristic guidance. Volatility: MEDIUM. — [Latency optimization](https://developers.openai.com/api/docs/guides/latency-optimization)
- OpenAI latency guide says reducing requests can avoid round-trip latency, and “Don’t default to an LLM” lists hard-coding, pre-computing, UI, and classical algorithms as faster alternatives for constrained tasks. Scope: LLM application design, not specifically Codex. Confidence: HIGH. Volatility: LOW-MEDIUM. — [Latency optimization](https://developers.openai.com/api/docs/guides/latency-optimization)
- OpenAI cost optimization docs recommend reducing requests, minimizing tokens, and selecting smaller models to reduce cost/latency; Batch API and flex processing can lower costs for asynchronous or lower-priority workloads at the cost of slower response or occasional resource unavailability. Scope: OpenAI API cost optimization. Confidence: HIGH. Volatility: MEDIUM-HIGH for product/pricing. — [Cost optimization](https://developers.openai.com/api/docs/guides/cost-optimization)
- OpenAI deployment checklist recommends comparing task success, latency, input/output/reasoning/cache-write tokens, and cost per successful task. It also notes Pro mode can improve reliability by applying more model work before returning a final answer, but increases latency and token usage. Scope: API deployment and model/agent setup. Confidence: HIGH. Volatility: HIGH for model modes. — [API deployment checklist](https://developers.openai.com/api/docs/guides/deployment-checklist)
- OpenAI tool search docs say deferred tool search avoids loading all tool definitions into model context up front and may reduce overall token usage and cost; it is designed to preserve cache for optimal cost/latency. Scope: OpenAI API tool search. Confidence: HIGH. Volatility: MEDIUM-HIGH. — [Tool search](https://developers.openai.com/api/docs/guides/tools-tool-search)
- Codex Subagents docs say subagents run in separate agent threads and parent receives summaries; subagents can move noisy exploration/logs out of main context and parallelize independent tasks, but each subagent does its own model/tool execution and can consume more tokens than a single agent. They also warn to be cautious with simultaneous writes due to conflicts and coordination costs. Scope: Codex subagent product docs as of checked date. Confidence: HIGH. Volatility: HIGH. — [Codex Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents)
- A 2026 arXiv study on multi-agent inference-time parallelism reports that multi-agent systems typically require multiple model invocations and complex coordination, and GAIA experiments showed parallelism can improve accuracy and reduce end-to-end latency at the cost of increased token consumption. Scope: GAIA benchmark, not Codex coding workflows. Confidence: MEDIUM-HIGH for that benchmark, LOW for direct coding generalization. Volatility: LOW for paper result, MEDIUM for relevance. — [A Two-Tier Perspective on Inference-Time Parallelism](https://arxiv.org/abs/2608.05791)
- `On Randomness in Agentic Evals` collected 60,000 trajectories on SWE-Bench-Verified across three models and two scaffolds; the workshop PDF reports 25.58B tokens and 1.88M tool calls. Single-run pass@1 estimates varied by 2.2–6.0 percentage points depending on selected run, with standard deviations exceeding 1.5 points even at temperature 0. Scope: SWE-Bench-Verified agentic evals, not production repositories. Confidence: HIGH for paper scope. Volatility: LOW. — [arXiv abstract](https://arxiv.org/abs/2602.07150), [OpenReview PDF](https://openreview.net/pdf/030b57388f7aa9e3a7ecb15e20541a8f2ed92f1b.pdf)

### Inferences

- Token cost is not only “the prompt.” Instructions, tool definitions, retrieved context, files, tool outputs, conversation history, subagent work, retries, and eval reruns all consume budget or wall time. A Harness that improves reliability can still be too expensive for a small or one-off task.
- Parallel agents trade wall-clock latency for additional tokens, tool calls, and integration work. The useful question is not “Can this be parallelized?” but “Will independent workstreams reduce elapsed time enough to justify extra compute and merge/review effort?”
- Evaluation loops have a measurable operating cost: repeated runs may be necessary to detect small effects, but repeated runs multiply tokens, tool calls, and human review. This supports using eval loops for recurring/high-risk failures rather than every trivial prompt change.

### Gaps

- No reliable universal conversion exists from token count or tool calls to “training productivity.” Cost per useful outcome must be measured in the project’s own workflow.
- Current ChatGPT/Codex seat quotas, Enterprise credit-based pricing, and model-specific Codex usage accounting can change and were not fully enumerated here.
- The available parallel-agent study is not a Codex coding study. It supports trade-off reasoning, not a recommended agent count.

## 언제 Prompt에서 Context, Harness, Loop로 넘어가야 하는가?

### Takeaway

공식 문서와 연구는 고정 threshold를 주지 않는다. 근거가 허용하는 안전한 운영 기준은 task가 작고 성공 기준이 단순하면 Prompt로 충분하고, 반복 context 재설명·관련성 문제·절차 불일치·검증 누락·반복 failure가 관찰될 때 Context, Harness, Loop를 추가한다는 것이다.

### Cited Findings

- OpenAI Codex Goals guide says a normal prompt is the right tool for a one-off edit, and Goals should not be used for a one-line edit, simple explanation, short code review, or a question where one answer and stop are desired. Goals are strongest when the task has a durable objective, evidence-based finish line, and path that may require several turns of investigation. Scope: Codex Goals, not all Harness mechanisms. Confidence: HIGH. Volatility: MEDIUM-HIGH. — [Using Goals in Codex](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex)
- OpenAI Codex Remote engineering blog says Plan mode asks Codex to propose an implementation path before changing code and is useful when a task is underspecified, risky, or likely to touch several systems. It says Goals solve durable-outcome problems, while Plan answers “How should we approach this?” Scope: OpenAI engineering blog/practice guidance, not formal product requirement. Confidence: MEDIUM-HIGH. Volatility: MEDIUM. — [Mastering remote engineering work from your phone](https://developers.openai.com/blog/mastering-codex-remote-for-engineering)
- OpenAI latency guide says “Don’t default to an LLM” and suggests hard-coding, pre-computing, UI, and classical methods for highly constrained outputs or inputs. Scope: LLM application latency design. Confidence: HIGH. Volatility: LOW-MEDIUM. — [Latency optimization](https://developers.openai.com/api/docs/guides/latency-optimization)
- OpenAI prompting guide says prompt quality often depends on how well the model is prompted, and recommends keeping overall tone/role in system messages and task-specific details/examples in user messages; it also recommends running prompt tests/evaluation cases every time prompts are published. Scope: API prompting guidance. Confidence: HIGH. Volatility: MEDIUM. — [Prompting](https://developers.openai.com/api/docs/guides/prompting)
- OpenAI Build Skills docs say ChatGPT and Codex start with each Skill’s name and description, then load full `SKILL.md` when they decide to use it. The initial skill list uses at most 2% of the model context window or 8,000 characters when context window is unknown, and for large skill sets Codex may omit some skills from the initial list and show a warning. Scope: Skills behavior as documented. Confidence: HIGH. Volatility: HIGH. — [Build skills](https://learn.chatgpt.com/docs/build-skills)
- OpenAI Academy says Skills turn existing reusable workflows into instructions ChatGPT can follow consistently, reducing repeated explanation. Scope: high-level educational/product page, not controlled study. Confidence: MEDIUM. Volatility: MEDIUM. — [Using skills](https://openai.com/academy/skills/)
- OpenAI GPT-6 Astra guidance says many Skill descriptions are too long, too many skills cause Codex to shorten descriptions to fit, and guidance helpful for older models may overconstrain Astra. Scope: current model-specific OpenAI developer guidance, checked 2026-09-25. Confidence: HIGH for guidance, volatility HIGH because model guidance changes. — [Rethinking skills and prompts for GPT-6 Astra](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)
- OpenAI model guidance says “Start with the smallest prompt that passes your evals, and add blocks only when they fix a measured failure mode.” Scope: current model guidance, not universal research law. Confidence: HIGH. Volatility: HIGH. — [Model guidance](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-5.4)
- MASTER_PLAN states the course should not build complex AI systems from the start; it should add the minimum structure needed when actual Failure and Friction occur, and not install all best practices upfront. Scope: project Source of Truth, not external research. Confidence: HIGH for project intent. Volatility: LOW unless plan changes by governance. — [MASTER_PLAN.md](../../plan/MASTER_PLAN.md)
- DECISIONS.md states Skills, Subagents, Memory, automated verification, and feedback loops have not been authorized merely by governance setup; they should be considered only after actual friction is observed and recorded, with recurrence, cause, expected benefit, added complexity, affected artifacts, and validation criteria recorded before implementation. Scope: project decision log. Confidence: HIGH for project rule. Volatility: LOW unless decision changes. — [DECISIONS.md](../../plan/DECISIONS.md)

### Inferences

- Prompt → Context threshold: add durable context when the same project facts, rules, or workflow constraints are repeatedly re-explained or when forgetting them creates observed errors. Do not move everything into context just because the repository has many documents.
- Context → Harness threshold: add Skills, tools, subagents, workflows, or verification only when context alone leaves work inconsistent, repetitive, unsafe, or hard to verify. A simple prompt remains cheaper for a one-off edit or explanation.
- Harness → Loop threshold: use Loop mechanisms when a failure recurs or carries enough risk that the system should learn from it. Loop is not “run agent forever”; it is failure observation, cause analysis, change, and re-evaluation.
- “Minimum Effective Harness” can be used as a course heuristic: add the smallest structure that fixes a measured failure without hiding its new costs. It is not an established external taxonomy and should not be presented as an industry standard.

### Gaps

- No primary source found a universal numeric threshold such as “after N prompts create a Skill” or “after M failures build an eval loop.” The evidence supports project-specific decision criteria, not global cutoffs.
- The target course Demo repository and real observed friction do not exist yet, so no Demo-specific threshold can be selected.

## Overengineering risks: when structure makes the system worse

### Takeaway

Too many instructions, skills, context files, memory entries, evals, automations, or agents can create context bloat, conflicts, stale knowledge, false confidence, longer latency, duplicated work, and maintenance burden. The remedy is not “avoid structure,” but keep every structure tied to a failure mode, owner, review path, and evidence that it still helps.

### Cited Findings

- OpenAI GPT-6 Astra guidance says older hand-holding/scaffolding may be unnecessary for more capable models, long `AGENTS.md`/Skills/prompts should be revisited, and “read the whole project before each edit” style instructions can waste context/time for small edits. Scope: OpenAI current model guidance. Confidence: HIGH. Volatility: HIGH. — [Rethinking skills and prompts for GPT-6 Astra](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)
- OpenAI Testing Agent Skills guide says skill changes can regress behavior: the skill may not trigger, skip required steps, or leave extra files behind. It proposes evals that inspect traces, artifacts, required steps, and efficiency goals such as unnecessary commands or excessive token use. Scope: Codex/agent Skill eval guidance, not a controlled study. Confidence: HIGH for practical guidance. Volatility: MEDIUM-HIGH. — [Testing Agent Skills Systematically with Evals](https://developers.openai.com/blog/eval-skills)
- OpenAI Build Skills docs say large skill sets may cause omissions from the initial list and warning, because the skill name/description list shares context with everything else. Scope: Skills discovery/loading. Confidence: HIGH. Volatility: HIGH. — [Build skills](https://learn.chatgpt.com/docs/build-skills)
- OpenAI deployment checklist says teams should compare direct tool calling against multi-agent workflows by success, required evidence, total tokens, latency, and cost; it also says short, sequential, or same-mutable-resource tasks often fit a single agent better. Scope: Agents API deployment. Confidence: HIGH. Volatility: MEDIUM-HIGH. — [API deployment checklist](https://developers.openai.com/api/docs/guides/deployment-checklist)
- METR’s 2025 randomized controlled trial studied 16 experienced OSS developers with moderate AI experience completing 246 tasks in mature projects they knew well; allowing AI tools increased completion time by 19% in that setting. Scope: early-2025 AI tools, experienced OSS developers, known mature projects. Confidence: HIGH for that setting. Volatility: LOW for study result, HIGH for current-tool generalization. — [METR RCT paper](https://arxiv.org/abs/2507.09089)
- `On Randomness in Agentic Evals` recommends multiple independent runs and power analysis for small improvements, but its own reported 60,000 trajectories used 25.58B tokens and 1.88M tool calls. Scope: SWE-Bench-Verified experiments; illustrates eval cost as well as variance. Confidence: HIGH for study scope. Volatility: LOW. — [OpenReview PDF](https://openreview.net/pdf/030b57388f7aa9e3a7ecb15e20541a8f2ed92f1b.pdf)
- Codex Memories docs distinguish ChatGPT Memory from local Codex Memories and advise keeping mandatory team instructions in `AGENTS.md` or checked-in docs; Memory is a recall layer, not the sole source for always-applicable rules. It also documents settings such as excluding external context conversations from memory generation. Scope: Codex local memory docs. Confidence: HIGH. Volatility: HIGH. — [Codex Memories](https://learn.chatgpt.com/docs/customization/memories)
- ChatGPT Memory Dreaming post says saved memory can become stale, inaccurate, or irrelevant over time and frames memory evaluation around useful context, user preferences/constraints, and freshness. Scope: ChatGPT memory system/product research, not Codex local memory. Confidence: MEDIUM-HIGH for ChatGPT Memory scope. Volatility: HIGH. — [Dreaming: Better memory for ChatGPT](https://openai.com/index/chatgpt-memory-dreaming/)
- OpenAI Harness Engineering case says the team introduced structure around repository knowledge, custom linters, structural tests, review, and recurring cleanup, but it is a reported engineering case rather than a universal procedure or controlled experiment. Scope: OpenAI internal case. Confidence: MEDIUM-HIGH for case details. Volatility: MEDIUM. — [Harness Engineering](https://openai.com/index/harness-engineering/)

### Inferences

- Too many Skills or instruction files can make the model select the wrong workflow, miss the right one, load irrelevant context, or follow stale/conflicting instructions. This is a maintenance burden, not merely a prompt-writing issue.
- Too many Memory entries can turn past context into hidden stale context. Memory review, scope, refresh, and retirement cost should be counted as part of Harness cost.
- Too many evals can slow iteration and consume substantial tokens/tool calls. Eval suites should prioritize high-risk, repeated, or representative failures and remain themselves reviewed for relevance.
- Too many automations can hide responsibility. Automation is justified when the trigger, allowed actions, verification surface, failure reporting, and human checkpoint are clear.
- The course’s “minimum structure in response to observed Failure/Friction” principle is technically aligned with the external evidence: structure has cost, and the right amount depends on measured task need, not maturity aesthetics.

### Gaps

- No official or academic source was found that defines “Minimum Effective Harness” as a standard taxonomy. Use it only as this project’s heuristic label if adopted later by Storyline/material design.
- No universal threshold was found for maximum number of Skills, instruction files, Memory entries, eval cases, subagents, or automation hooks. Practical thresholds must come from project-specific usage, observed failures, and evaluation cost.
- Current Codex product cost/latency behavior depends on model, plan, seat, workspace, surface, pricing, prompt cache, and usage accounting. Demo claims need final recheck in the target environment.
