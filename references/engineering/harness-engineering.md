# Harness Engineering

## Research Question

Harness Engineering은 model capability와 어떻게 다르고 어디까지 주장할 수 있는가?

## Why It Matters

Harness는 Context를 넘어 tools, commands, checks, reusable instructions를 엮는 단계다.

## Findings

- **Type: ACADEMIC FINDING / Confidence: HIGH / Freshness: see Checked date for cited SRC IDs in SOURCES.md / Source: SRC-0206** — SWE-agent shows scaffold/interface changes can change benchmark outcomes under fixed conditions.
- **Type: INDUSTRY PRACTICE / Confidence: MEDIUM / Freshness: see Checked date for cited SRC IDs in SOURCES.md / Source: SRC-0137** — OpenAI Harness Engineering case links usefulness to environment, decomposition, tools, stale instructions.
- **Type: ACADEMIC FINDING / Confidence: MEDIUM / Freshness: see Checked date for cited SRC IDs in SOURCES.md / Source: SRC-0218** — harness definition work exists, but no universal workplace taxonomy is established.
- **Type: HEURISTIC / Confidence: HIGH / Freshness: see Checked date for cited SRC IDs in SOURCES.md / Source: SRC-0001** — Minimum Effective Harness means smallest structure addressing observed failure/friction.

## What the Evidence Does NOT Prove

Harness does not fix every model limit. Model upgrade does not fix bad setup, missing tests, stale instructions, or security gaps.

## Implication for Training

Harness를 problem-driven minimum system design으로 설명한다.

## Demo Implication

Introduce harness pieces only when a preceding failure/friction requires them.

## Risks / Caveats

Harness Technical Debt is bounded analogy only.
